# 1. 전송 계층의 역할
## 1.1 전송 계층의 두 가지 역할
- **전송 계층**: **목적지에 신뢰할 수 있는 데이터를 전달**하기 위해 필요
	- 물리 계층, 데이터 링크 계층, 네트워크 계층의 3계층이 있으면 목적지에 데이터를 보낼 수 있음
    - 하지만 데이터가 손상되거나 유실되었을 때 책임 X
    - **오류 점검 기능**: 오류가 발생하면 데이터를 재전송하도록 요청
    - **전송된 데이터의 목적지가 어떤 애플리케이션인지 식별하는 기능**: 어떤 애플리케이션에 전달해야 하는지 모르면 곤란하기 때문에
    
## 1.2 연결형 통신과 비연결형 통신
- **연결형 통신**: 신뢰할 수 있고 정확한 데이터를 전달하는 통신
	- 신뢰성/정확성: 데이터를 목적지에 문제없이 전달하는 것
    - 신뢰성/정확성이 먼저이기 때문에 여러 번 확인하고 보냄
    - TCP: 연결형 통신 프로토콜
- **비연결형 통신**: 효율적으로 데이터를 전달하는 통신
	- 효율성: 데이터를 빠르고 효율적으로 전달하는 것
    - 효율성이 먼저이므로 확인 절차 없이 일방적으로 보냄
    - ex) 동영상
    - UDP: 비연결형 통신 프로토콜

# 2. TCP의 구조
## 2.1 TCP
![](https://velog.velcdn.com/images/emprimula/post/09bab379-292f-4642-886b-3b49199a3a30/image.jpg)
- **TCP 헤더**: TCP로 전송할 떄 붙이는 헤더
	- 목적지까지 데이터를 제대로 전송하기 위해 필요한 정보를 가지고 있음
- **세그먼트**(segment): TCP 헤더가 붙은 데이터
	- TCP 헤더도 순서대로 정보가 나열되어 있음
    - TCP 헤더도 다양한 정보가 많이 있음
- **연결**(connection): 데이터를 전송하기 위한 **가상의 독점 통신로**로 이것을 확보해야 함
	- 데이터를 전송하기 전에 해야 하는 작업
    ![](https://velog.velcdn.com/images/emprimula/post/801ff80c-3924-4597-b3a1-ecf689efd991/image.png)
![](https://velog.velcdn.com/images/emprimula/post/754c967f-c51a-4f39-91b5-94a50301a9da/image.png)
- 코드 비트: TCP 헤더의 107번째 비트부터 112번째 비트까지 6비트로 연결의 제어 정보가 기록되는 곳
 	- 초기값 0 => 비트 활성화되면 1
    - 연결 확립 위해 **SYN**. **ACK** 필요
    - SYN: 연결 요청
    - ACK: 확인 응답
    
## 2.2 3-way 헨드셰이크

**3-way 핸드셰이크**

- 연결은 SYN과 ACK를 사용하여 확립할 수 있음
	- 신뢰할 수 이있는 연결을 하려면 데이터를 전송하기 전에 패킷을 교환하는데 3번 확인
![](https://velog.velcdn.com/images/emprimula/post/64e98396-84fd-4889-918c-c3371e190090/image.png)

- **3-way 핸드셰이크**: 데이터를 보내기 전에 연결을 확립하기 위해 패킷 요청을 3번 보내는 것
	- 헨드셰이크: 데이터 통신에서 확실하게 데이터가 전송되었는지 확인하면서 이뤄지는 통신 수단

**4-way 핸드셰이크**

- 연결을 끊을 땐 FIN과 ACK을 사용
	- FIN: 연결 종료
![](https://velog.velcdn.com/images/emprimula/post/61393333-6803-4eff-adae-f45acd89ebaa/image.png)

# 3. 일련번호와 확인 응답 번호의 구조

## 3.1 일련번호와 확인 응답 번호
![](https://velog.velcdn.com/images/emprimula/post/81cab243-8597-490d-a1bf-5a2969a28e67/image.png)

- 일련번호(sequence number): TCP가 데이터를 분할해서 보내는데 일련번호는 송신 측에서 수신 측에 '이 데이터가 **몇 번쨰 데이터**인지' 알려 주는 역할
	- 전송된 데이터에 일련번호 부여 => 수신자는 원래 데이터의 **몇 번째 데이터**를 받았는지 알 수 있음
- 확인 응답 번호(acknowledgement number): 수신 측이 **몇 번째 데이터**를 수신했는지 송신 측에 알려 주는 역할
	- 확인 응답: 예를 들어 10번 데이터를 수신하면 11번 데이터를 송신 측에 요청하는 것(다음 번호의 데이터를 요청할 때도 사용함)
![](https://velog.velcdn.com/images/emprimula/post/c6a494ac-14e7-4dca-8840-6173232d7d47/image.png)

- 재전송 제어: 일련번호와 확인 응답 번호를 사용해서 데이터가 손상되거나 유실된 경우 데이터를 재전송하게 함

## 3.2 윈도우 크기
- 위의 통신은 **세그먼트(데이터)** 하나를 보낼 때마다 확인 응답을 한 번 반환하는 통신 => 한 번 보낼 때 한 번 응답 반환은 효율 낮음
=> 세그먼트를 연속해서 보내고 난 다음에 확인 응답을 하면 효율이 높아짐
- **버퍼**(buffer): 받은 세그먼트를 일시적으로 보관하는 장소
	- 세그먼트를 연속해서 보내도 수신 측은 대응할 수 있고 확인 응답의 효율이 높아짐
    - **오버플로**(overflow): 수신 측이 세그먼트를 대량으로 받아처 처리하지 못하는 경우(대량으로 데이터가 전송되어 보관되지 못하고 넘침)
	- 그래서 오버플로가 발생하지 않게 **버퍼의 한계 크기**를 알고 있어야 함
- **윈도우 크기**(window size): 버퍼의 한계 크기
	- **얼마나 많은 용량의 데이터를 저장해 둘 수 있는지** 나타내는 것
    - 확인 응답을 일일이 하지 않고 연속해서 송수신할 수 있는 데이터 크기
    - 윈도우 크기의 초기값은 **3-way 핸드셰이크**를 할 때 판단

# 4. 포트 번호의 구조
## 4.1 포트 번호
- 전송된 데이터의 목적지가 어떤 애플리케이션인지 구분할 필요가 있음
![](https://velog.velcdn.com/images/emprimula/post/871dea5e-bad2-4ba7-a16d-b73e2046fba1/image.png)
- 출발지 포트 번호(source port number), 목적지 포트 번호(destination port number) 사용 => 이 포트 번호로 애플리케이션 구분
	- 0 ~ 65535번 사용 가능
    - **0 ~ 1023 **번: 주요  프로토콜 => **잘 알려진 포트**(well-known ports)
    - 1024: 예약되어 있지만 사용 X
    - **1025 ~**: **랜덤 포트** => 클라이언트 측의 송신 포트로 사용
- 포트 번호를 붙이지 않고 통신하면 컴퓨터에 데이터가 도착해도 애플리케이션까지 도달 X
- 웹 브라우저로 접속할 떄 웹 브라우저는 임의의 포트가 **자동으로 할당됨**
	=> 그래서 서버 측에서는 포트 번호를 정해 둬야 하지만 클라이언트는 정해지 않아도 괜찮음

# 5. UDP의 구조

## 5.1 UDP

- **UDP**: **비연결형 통신 프로토콜**
	- TCP처럼 시간 걸리는 확인 작업 X
    - **효율성**을 중요하게 여기는 프로토콜 => TCP 같은 신뢰성/정확성을 요구하면 효율 떨어짐
    - 장점: **데이터를 효율적으로 빠르게 보내는 것**
    - 스트리밍 방식으로 전송하는 동영상 서비스 같은 곳에 사용
    - TCP로 동영상을 보내면 동영상 원활하게 못 봄
    
## 5.2 UDP 헤더
![](https://velog.velcdn.com/images/emprimula/post/34d1e041-ecd7-418b-9ae0-5f60ab7bb071/image.png)

- **UDP 데이터그램**: UDP 헤더가 붙은 데이터
- 실제로는 가로로 정보가 나열되어 있음
- UDP 헤더: 올바른 목적지의 애플리케이션으로 데이터를 전송하기 위해 필요한 정보가 기록되어 있음
- **브로드캐스트**(broadcast): 랜에 있는 컴퓨터나 네트워크 장비에 데이터를 일괄로 보내는 것
	- TCP의 경우 데이터를 전송할 때 확인 응답을 하나씩 보내야 힘 => 불특정 다수에게 보내는 브로드캐스트 방식에 적합 x
    - UDP에서 브로드캐스트는 **목적지에 관계없이** 랜에서 일괄로 보냄
    - TCP는 목적지를 지정하지 않으면 안 되기 때문에 **일괄 통신 X**
