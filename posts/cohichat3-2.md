# 좋은 프로그램을 만든다는 것 - 테스트와 품질 관리

기간 자체도 길고, 고민이 많았기 때문에 지연된 것이라 분량이 매우 많다. 그래서 이번 회고록은 게시글을 3개로 나눠 작성하게 되었다.

- 1부: 협업과 성장 (팀워크 & 프로세스)
- **2부: 좋은 프로그램 만들기 (테스트 & 품질)** ← 지금 여기
- 3부: 설계와 구현 이야기 (기술 선택의 고민들)

---

## 1. 포맷터와 린터의 필요성을 체감한 순간

### 협업에서의 자동화

1부에서 언급했듯이, 포맷터와 린터는 **협업에서 자동화할 수 있는 것을 자동화**하는 첫걸음이었다. 코드 스타일에 대한 논쟁을 줄이고, 더 본질적인 설계와 로직에 집중할 수 있게 만들어 주었다.

📌 **작성한 문서**: [코드 컨벤션 Wiki](https://github.com/CheHyeonYeong/cohi-chat/wiki/%EC%BD%94%EB%93%9C-%EC%BB%A8%EB%B2%A4%EC%85%98)

- **포맷터**: IntelliJ의 `codestyle`
- **린트**: `checkstyle`

인텔리제이 컴파일 시점에서 빨간 밑줄로 표시되는 컨벤션 규칙들을 보면서, **코드 품질 관리를 자동화**할 수 있다는 것을 체감했다. 이는 단순히 스타일 통일을 넘어서, **팀원 모두가 같은 기준으로 코드를 작성**할 수 있게 만드는 기반이 되었다.

## 2. TDD의 범위를 다시 정의하다

### TDD 도입 과정에서의 혼란

이번 프로젝트에서 TDD를 도입하면서 **테스트 주도 개발 방법론**을 처음 제대로 적용해 보았다. TDD는 테스트 코드를 먼저 작성한 후 코드를 작성하는 방법으로, RED → GREEN → BLUE 사이클을 따른다.

📌 **작성한 문서**: [테스트 전략 Wiki](https://github.com/CheHyeonYeong/cohi-chat/wiki/%ED%85%8C%EC%8A%A4%ED%8A%B8-%EC%A0%84%EB%9E%B5)

**TDD 사이클 예시**:
```
📌 Task: TDD 사이클 완성 (Red-Green-Refactor)
목표: 회원가입 기능을 Red → Green → Refactor 순서로 구현

산출물:
- Commit 1: 🔴 실패하는 테스트 (Test의 개괄 짜기)
- Commit 2: 🟢 통과시키는 최소 코드 (Test에 맞춰서 코딩하기)
- Commit 3: 🔵 리팩토링 (예쁘게 만들기)

완료 기준:
- PR에서 TDD 사이클이 명확히 보임
- 각 단계별로 "왜 이렇게 했는지" 설명 있음
```

### 문제점: 테스트 범위에 대한 고민

코드 없이 테스트 코드부터 작성한다는 점에서 많은 고민이 생겼다:
- 성공 케이스는 어디까지 작성해야 하는가?
- 실패 케이스는 어디까지 작성해야 하는가?
- Repository, Service, Controller, 통합 테스트를 모두 작성해야 하는가?

처음 작성한 TDD 가이드는 **단위 테스트와 Service Test 위주**로 작성되어 있었다. 통합 테스트, Repository, Controller에 대한 가이드와 부가 설명이 부족했고, 이것이 테스트 전략의 불완전함으로 이어졌다.

### Unit → Integration → E2E로 확장

테스트는 단순히 "기능이 동작하는지" 확인하는 것이 아니라, **어떤 계층에서 무엇을 검증할 것인가**에 대한 전략이 필요했다:

- **Unit Test**: 개별 메서드의 로직 검증
- **Integration Test**: 여러 컴포넌트 간의 상호작용 검증
- **E2E Test**: 사용자 시나리오 기반 전체 플로우 검증

각 계층마다 검증하는 대상과 범위가 달라야 하는데, 처음에는 이 구분 없이 "일단 테스트 코드를 작성"하는 데 급급했다.

## 3. 경계값 테스트를 왜 놓치기 쉬운가

### 문제 상황: 동작하는 기능 테스트

내가 작성한 테스트는 **"동작하는 기능 테스트"**에 가까웠다. 설계 시선의 부재 때문에 **설계 관점으로 테스트 케이스를 설정하지 못했다**.

예를 들어:
- 회원가입이 성공하는지만 테스트
- 로그인이 되는지만 테스트
- 예외 상황은 "일단 하나만" 테스트

경계값이나 엣지 케이스는 "귀찮으니까 나중에"라는 생각으로 미뤘다.

### 왜 이런 일이 발생했을까?

- **Why 1**: 왜 경계값 테스트를 놓쳤을까? → 기능 동작에만 집중
- **Why 2**: 왜 기능 동작에만 집중했을까? → 설계 관점이 부재
- **Why 3**: 왜 설계 관점이 부재했을까? → 유스케이스나 시나리오를 생각하지 않음
- **Why 4**: 근본 원인 → **기능으로 설계하지 않고, "일단 돌아가게" 구현**

### 개선 방향: 유스케이스와 시나리오 기반 설계

**기능으로 설계하지 않고 유스케이스 or 시나리오를 생각하고 거기에 맞춰서 설계했어야 했다.**

예시:
```
[잘못된 접근]
- 회원가입 API가 200을 반환하는가?

[올바른 접근]
- 사용자가 이메일로 회원가입을 시도한다
  ✓ 유효한 이메일 형식일 때
  ✓ 이미 존재하는 이메일일 때
  ✓ 이메일이 비어있을 때
  ✓ 이메일이 최대 길이를 초과할 때
  ✓ 특수문자가 포함될 때
```

유스케이스 기반으로 생각하면 자연스럽게 **경계값과 예외 상황**을 놓치지 않게 된다.

### 배운 점

**Keep**: 기본적인 테스트 작성 습관  
**Problem**: 경계값, 엣지 케이스 누락, 설계 관점 부재  
**Try**: 유스케이스 먼저 정의 → 시나리오 도출 → 테스트 케이스 작성

---

아, 제가 오해했네요! Mockito 경고가 "테스트 설계 문제"가 아니라 **Java 21과 Mockito 호환성 이슈**에 대한 경고였군요.

그럼 이 부분을 수정할게요:

## 4. Mockito 경고는 왜 무시하면 안 되는가

### 문제 상황: "Mockito 경고는 무시해도 되는데?"

테스트 코드를 작성하다 보면 Mockito에서 경고가 뜬다. Java 21에서 Mockito를 사용할 때 발생하는 호환성 이슈였다.

🔗 **관련 이슈**: [Mockito GitHub Issue #3037](https://github.com/mockito/mockito/issues/3037)

처음엔 "테스트는 돌아가니까 괜찮겠지"라고 생각하고 무시했다. 하지만 **오류를 그냥 무시하는 것보다 하나씩 다 해결하는 태도**가 필요하다고 깨달았다.

### 왜 경고가 뜨는지 의문을 가지는 태도의 필요성

경고가 뜨면:
1. "왜 이 경고가 뜨는가?"
2. "이게 실제 문제가 될 수 있는가?"
3. "어떻게 해결할 수 있는가?"

이런 질문들을 던지지 않고 그냥 넘어가면, **나중에 더 큰 문제**로 돌아올 수 있다.

Java 21과 Mockito 호환성 이슈의 경우:
- 지금은 경고만 뜨지만
- 특정 상황에서 테스트 실패 가능
- 버전 업그레이드 시 문제 발생 가능

### 왜 이런 일이 발생했을까?

- **Why 1**: 왜 경고를 무시했을까? → "일단 돌아가니까"
- **Why 2**: 왜 그런 태도였을까? → 경고의 의미를 찾아보지 않음
- **Why 3**: 근본 원인 → **의문을 가지지 않고 넘어가는 습관**

### 해결 과정

1. GitHub Issue를 찾아봄
2. 다른 사람들도 같은 문제를 겪고 있음을 확인
3. 해결 방법 탐색 (Mockito 버전 업그레이드, 대안 라이브러리 등)

### 배운 점

**Keep**: 테스트 코드 작성  
**Problem**: 경고 무시, 의문 없이 넘어감  
**Try**: 모든 경고에 대해 "왜?"를 물어보고 근본 원인 파악하기

> "경고를 무시하는 순간, 잠재적 문제도 함께 무시하게 된다."

## 5. 테스트 코드에서 AI를 쓰며 겪은 한계와 가능성

### 문제 상황: AI가 만든 테스트 코드의 함정

테스트 코드 작성이 어려워서 AI(Claude, ChatGPT)에게 도움을 받았다. 하지만 **내가 테스트 코드에 대한 이해 없이 테스트 코드를 짜 달라고 하면** 문제가 많았다:

1. **너무 과한 코드가 나온다**
   - 단순한 테스트인데 불필요하게 복잡한 구조
   
2. **제대로 된 검증이 되지 않는다**
   - 겉보기엔 그럴싸한데 실제로는 아무것도 검증 안 함
   
3. **가독성 좋은 방법이 있는데 돌아서 간다**
   - `@Mock` 안 쓰고 상수로 박아버리면 훨씬 단순하고 깔끔하게 테스트할 수 있는데
   - AI 코드를 보고 역으로 이해하려니까 `@Mock`을 쓰는 방법에만 묶여 있었음

### 예시: 단순한 방법 vs AI가 제안한 방법

```java
// AI가 제안한 방법 (과한 Mock 사용)
@Mock
private UserRepository userRepository;

@Mock
private PasswordEncoder passwordEncoder;

@Test
void 회원가입_성공() {
    // given
    User user = mock(User.class);
    when(user.getEmail()).thenReturn("test@test.com");
    when(userRepository.save(any())).thenReturn(user);
    when(passwordEncoder.encode(any())).thenReturn("encoded");
    
    // when & then
    ...
}

// 더 단순한 방법 (상수 사용)
@Test
void 회원가입_성공() {
    // given
    String email = "test@test.com";
    String password = "password123";
    
    // when & then
    ...
}
```

### AI 활용의 한계

**AI는 도구일 뿐, 설계 판단은 내가 해야 한다.**

AI가 만든 코드를 그대로 사용하면:
- 불필요한 복잡도 증가
- 테스트의 의도가 가려짐
- Mock 남용으로 테스트 유지보수 어려움

### 올바른 AI 활용법

1. **기본 개념을 먼저 학습**하고 AI 사용
2. AI 코드를 **비판적으로 검토**하기
3. "이게 정말 필요한가?" 질문하기
4. 더 단순한 방법이 있는지 고민하기

### 배운 점

**Keep**: AI를 학습 도구로 활용  
**Problem**: AI 코드 무비판적 수용, Mock 과다 사용  
**Try**: AI 제안을 단순화하고, 필요한 부분만 선택적으로 사용

## 6. 귀찮음을 흐린 눈 하지 말아야 하는 이유

### 문제 상황: "이 정도면 괜찮겠지"

테스트를 작성하다 보면 귀찮은 순간들이 온다:
- "이 경계값까지 테스트해야 해?"
- "이 예외 상황은 거의 안 일어나는데..."
- "Mockito 경고는 나중에 고치지 뭐"

이런 생각으로 넘어간 것들이 쌓이면서, **설계의 허점**이 생기고 **진짜 동작만 하는 프로그램**으로 향하게 된다.

### 왜 귀찮은 것을 넘기면 안 되는가?

1. **작은 허점이 큰 버그로**
   - 경계값 테스트를 안 한 부분에서 실제 버그 발생
   
2. **기술 부채 누적**
   - "나중에 고치지"가 쌓이면 결국 안 고침
   
3. **설계 품질 저하**
   - 귀찮다고 넘긴 부분이 설계의 약점

### 개선 방향: 체계화와 이슈 관리

**귀찮다고 넘기지 않고, 허점이 생기면 새로 이슈로 나눠서 처리하거나 체계화**하는 것이 필요하다.

예시:
```
[잘못된 접근]
- "이건 나중에 고치자" → 안 고침

[올바른 접근]
- 즉시 이슈 생성: "경계값 테스트 추가 필요"
- 우선순위 설정하고 체계적으로 처리
- 기술 부채 관리
```

### 배운 점

**Keep**: 문제 인식  
**Problem**: 귀찮다고 넘김, 기술 부채 누적  
**Try**: 즉시 이슈화하고 체계적으로 관리

> "귀찮음을 흐린 눈 하는 순간, 설계의 품질도 함께 떨어진다."

## 7. "테스트가 어렵다"는 말의 진짜 의미

### 깨달음: 테스트가 어려운 이유는 설계 때문

프로젝트를 하면서 계속 "테스트 짜기 어렵다"고 생각했다. 하지만 진짜 문제는 **테스트가 어려운 게 아니라 설계가 안 된 것**이었다.

### 설계의 부재

**지금은 설계를 안 하고 기능 동작하는 거에 초점이 맞춰져서 설계 시각의 부재가 컸다.**

- "일단 이 API 만들고..."
- "일단 이 기능 돌아가게 하고..."
- "일단 이걸 구현하고..."

"일단"으로 시작하면 설계는 뒷전이 된다.

### 제대로 된 설계가 있다면

**제대로 된 설계를 한다면:**
1. 그 설계에 맞는 **시나리오**가 나올 것이고
2. 시나리오에 맞는 **테스트**가 나올 것이다

예시:
```
[설계 없이 구현]
- 회원가입 API 만들기
- 뭘 테스트해야 하지...?
- 일단 성공 케이스만...

[설계 기반 구현]
- 유저 회원가입 유스케이스 정의
  1. 이메일 중복 체크
  2. 비밀번호 유효성 검증
  3. 사용자 생성
  4. 환영 이메일 발송
- 각 단계별 시나리오 도출
- 시나리오 기반 테스트 작성
```

설계가 먼저 있으면 테스트는 자연스럽게 따라온다.

### 왜 이런 일이 발생했을까?

- **Why 1**: 왜 테스트가 어려웠을까? → 뭘 테스트해야 할지 모름
- **Why 2**: 왜 몰랐을까? → 시나리오가 명확하지 않음
- **Why 3**: 왜 시나리오가 없었을까? → 설계를 안 함
- **Why 4**: 왜 설계를 안 했을까? → 기능 구현에만 급급
- **Why 5**: 근본 원인 → **"일단 돌아가게" 만드는 것을 우선시**

### 설계 우선 개발로의 전환

**설계 → 시나리오 → 테스트** 순서를 지키면:
- 테스트 작성이 쉬워진다
- 경계값이 자연스럽게 도출된다
- 코드 품질이 올라간다
- 유지보수가 쉬워진다

### 배운 점

**Keep**: TDD 사이클 경험  
**Problem**: 설계 시각 부재, 기능 구현 우선

## 시리즈 2 종합 회고

### Keep (계속할 것)
- 포맷터/린터 자동화
- TDD 사이클 경험
- AI를 학습 도구로 활용
- 경고와 허점을 이슈화하는 습관

### Problem (개선 필요)
- 설계 시각 부재
- 동작하는 기능 테스트에 그침
- 경계값 테스트 누락
- 경고 무시하는 태도
- AI 코드 무비판적 수용
- "귀찮음"으로 넘기는 습관
- 기능 구현 우선, 설계 후순위

### Try (다음엔)
- 설계 → 시나리오 → 테스트 순서 지키기
- 유스케이스 기반으로 테스트 케이스 도출
- 모든 경고에 대해 "왜?"를 묻기
- AI 제안을 비판적으로 검토하고 단순화
- 허점 발견 시 즉시 이슈화
- Unit/Integration/E2E 테스트 전략 명확히
