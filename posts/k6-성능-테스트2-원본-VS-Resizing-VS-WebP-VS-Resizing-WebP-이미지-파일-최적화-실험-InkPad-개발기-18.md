# 이미지 파일 최적화 성능 실험
**원본 / 리사이징 / WebP 변환 / 리사이징+WebP**

## 테스트 환경 

| 항목         | 내용                                     |
| ---------- | -------------------------------------- |
| 테스트 도구     | k6 (부하 테스트 시나리오 작성 및 실행)               |
| 테스트 대상 API | `/api/posts` (이미지 포함 게시글 업로드)          |
| 요청 방식      | `multipart/form-data`, JSON + 이미지      |
| VUs        | 30명                                      |
| 테스트 시간     | 5분                                   |
| 네트워크 환경    | 로컬 환경 (Docker + Spring Boot)           |
| 이미지 크기     | 원본 약 2.5MB, 리사이징 약 800KB, WebP 약 400KB |

> **실험 방법**
- 원본: 이미지 원본 그대로 전송
- resize: 사이즈만 줄임 (400으로)
- WebP: 포맷만 변경 (용량 감소)
- resize+WebP: 사이즈 축소 + 포맷 최적화

## 분석 결과 요약
1. 리사이징의 압도적 효과
- 단독 리사이징만으로 84.0% 성능 향상을 달성
- 고부하 상황에서 네트워크 병목이 얼마나 심각한지
- 전송량 감소 → 네트워크 병목 해소 → 응답시간 단축
2. 원본 이미지의 심각한 한계
- 73%의 요청 실패 발생 (11/402 실패)
- 평균 23초의 극도로 느린 응답시간
- 사용자 경험 관점에서 사실상 사용 불가능한 수준
3. WebP 단독 적용의 제한적 효과
- WebP 변환만으로는 23% 개선에 그쳤으나, **실패율은 0%**로 안정성은 확보
4. 조합 전략의 균형점
- 리사이징+WebP는 69.5% 향상으로 성능과 파일 크기 최적화의 좋은 절충점을 제공

## 성능 특성 비교 요약

### 처리량(Throughput) 혁신적 개선
- 원본: 1.25 req/s (실패율 2.73%)
- 리사이징만: 7.68 req/s (515% 증가, 실패율 0%)
- 리사이징+WebP: 3.94 req/s (216% 증가, 실패율 0%)
- WebP만: 1.60 req/s (28% 증가, 실패율 0%)

### 시스템 안정성
- 원본: 11건의 요청 실패로 시스템 불안정
- 모든 최적화 방식: 100% 성공률로 시스템 안정성 확보

### 응답시간 예측성
- 리사이징: 90% 백분위 5.29s로 일관된 성능 제공
- 원본: 90% 백분위 32.7s로 예측 불가능한 성능

## 왜 리사이징이 예상보다 효과적이었을까?
1. 네트워크 병목의 극복
- 고부하 상황에서 대용량 이미지 전송이 주요 병목임을 확인
- 파일 크기 감소가 처리량을 6배 이상 증가
2. 메모리 압박 해소
- 30명의 동시 사용자 환경에서 서버 메모리 사용량 급격한 감소로 시스템 안정성이 향상
3. 타임아웃 방지
- 원본 이미지는 일부 요청이 60초 타임아웃에 걸려 실패했지만, 최적화된 이미지는 모든 요청이 성공
4. WebP의 제한된 효과 원인
- 실시간 변환 오버헤드: 압축 처리 시간이 여전히 상당함
- CPU 집약적 작업: 고부하에서 CPU 병목 발생
- 네트워크 vs 처리시간: 파일 크기 감소보다 처리 시간 증가가 더 큰 영향
