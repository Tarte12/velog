## 1. 에러코드 및 Json 응답 정의
_25.08.23 오후 1시 진행_

### 에러코드 형식

1. 모든 응답에 대한 응답 코드는 200 , OK 로 내려줄 것 

| CODE(고유코드 + 순차 번호) | HTTP | Error Message |
| --- | --- | --- |
| P001 | 200 | 로그인정보에 오류가 있습니다. |
| P002 | 200 | 페이지를 찾을수 없습니다. |

### Json 응답 정의

1. 성공 형식

```
`{ success: true, data, meta }`

```

2. 실패 형식

```json
{
	"success": false,
	"error": {
		"code": "P001",
		"message": "서버 과부하",
	}
}
{ success: false, error: {code, message, details[] }, meta}
```

* 실패 시 data : null과 같은 data field 생성 자체 x

* 사용 http delete method 사용 고민 **(8월 25일 까지)**
→ http url에 행위가 들어가는 것은 표준에서 벗어남
→ delete method를 사용하면 url 확장할 필요 없음
(BE에서 delete에 해당하는 method를 추가하면 되기에)

## 2. 결제 시나리오 검토

### #0 시나리오 (kakao pay) - 검토 완료

**[ 1. 결제 요청 준비 및 결제 준비 단계 ]**

- 진행자 : `FE`, `BE`, `kakao`
- API : 주문 생성 API, 결제 시도 API (ready)
- 진행 :

```purescript
FE -> BE ( 주문 생성 API request )
	# 결제 금액, 주문번호, 사용자 ID 등 결제에 필요한 최소 정보를 BE로 전달
	
BE -> kakao ( 결제 시도 API request )
	# kakao에 결제 진행을 위한 페이지 요청
	
kakao -> BE ( 결제 시도 API response )
	# 결제 진행 페이지 URL 응답

BE -> FE ( 주문 생성 API response )
	# 결제 진행 페이지 URL 응답
	
FE ( response 처리 )
	# 결제 진행 페이지 URL로 redirect
```

**[ 2. 사용자 결제 진행 (kakao pay UI)**

- 진행자 : `FE`, `kakao`
- API : `NONE`
- 진행 :

```purescript
kakao
	# 결제 진행
	
kakao -> FE
	# 결제 완료 시, 결과와 pg_token을 실어 응답
	# 결제 취소, 실패 시, 결과 응답

FE
	# kakao 응답으로 다음 진행 결정
	# 결제 완료 확인 시, ***[ 3. 결제 승인 단계 ]*** 진행
	# 결제 실패 취소 확인 시, 별도 알림 생성하여 사용자에게 알림

```

**[ 3. 결제 승인 단계 ]**

- 진행자 : `FE`, `BE`, `kakao`
- 🚧 API : 결제 완료 API (approve) ? 혹은 별도 요청 API 필요?
- 진행 :

```purescript
FE -> BE ( ~~별도 요청 API가 필요한 부분으로 보임~~ 결제  완료 API (approve) 호출 )
	# pg_token과 필요시 부가 정보를 담아 결제 승인 요청
	
BE -> kakao ~~( 결제 완료 API (approve)를 이때 호출하는 게 아닌지 )~~
	# 최종 결제 승인 요청
	
kakao -> BE
	# 최종 결제 완료/실패 여부 반환

BE -> FE
	# 서버 응답에 따라 결제 성공 화면 또는 실패 안내
	
FE ( 결제 완료 상품 데이터 조회 API )
```

### 결제 요청 API

#### response(성공)

#### Header

```json
HTTP/1.1 200 OK
Content-Type: application/json
X-Request-Id: req-129
X-Server-Timezone: UTC
X-Server-Time-Format: ISO-8601
Cache-Control: no-store
Pragma: no-cache

```

- `X-Request-Id` : 요청에서 받은 값을 그대로 응답에 echo → FE/BE 로그 추적
- `Cache-Control: no-store`, `Pragma: no-cache` 👉 결제 관련 응답은 절대 캐시되면 안 되므로 응답 전용으로 추가

#### Body

```json
{
  "success": true,
  "data": {
  "next_redirect_app_url": "https://kakaopay.example.com/redirect/app/T123...",
  "next_redirect_mobile_url": "https://kakaopay.example.com/redirect/mobile/T123...",
  "next_redirect_pc_url": "https://kakaopay.example.com/redirect/pc/T123...",
  "android_app_scheme": "kakaopay://...",
  "ios_app_scheme": "kakaopay://..."
```

#### 실패 사유가 없는 이유

- **PG별 차이**: **NaverPay**는 `return_url`에 `resultCode/resultMessage`를 전달해 주지만, **KakaoPay**는 `fail_url`만 전달하여 사유를 알 수 없음
- 따라서 결제수단별로 **PG 거래 조회 API**(서버→PG)를 호출해 최종 상태/사유를 따로 확인해야 함
- **확장**: 조회 API를 구현하게 될 경우, `error.details` 배열에 추가 키를 덧붙이면 됨

```json
{ "field": "provider_code",    "reason": "F4002" },
{ "field": "provider_message", "reason": "Insufficient limit" }
```

- **최소안**: 사유가 필요하지 않다면 **단일 실패 응답**으로 처리
