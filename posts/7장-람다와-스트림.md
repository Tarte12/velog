# ITEM 42 익명 클래스보다 람다를 사용하라

> **핵심**
> 자바 8 이전에는 익명 클래스로 함수를 표현했지만, 지금은 **람다**로 함수를 표현하는 게 훨씬 간결하고 가독성이 높다

```java
// ❌ 옛날 방식 (익명 클래스) - 너무 장황함
Collections.sort(words, new Comparator<String>() {
    public int compare(String s1, String s2) {
        return Integer.compare(s1.length(), s2.length());
    }
});

// ✅ 람다 방식 - 간결하고 명확함
Collections.sort(words, 
    (s1, s2) -> Integer.compare(s1.length(), s2.length()));

// ✅ 더 나은 방법 - 메서드 참조 사용
words.sort(comparingInt(String::length));
```

**람다 등장 이유**
- "하나짜리 메서드""를 **간단한 함수 형태**로 표현하기 위해
1. 불필요한 문법 제거
2. 함수만 남김
3. 전략 패턴의 '전략 객체' 훨씬 쉽게 전달 가능

**주의**
1. 람다는 되도록 1줄, 길어도 3줄 이내로 쓰자
2. 3줄이 넘어간다면 줄이려고 노력하거나 쓰지 않는 방향으로 리팩토링하자
3. 람다는 `this`가 **바깥 인스턴스**를 의미하므로, 자신을 참조하려면 **익명 클래스**를 사용해야 함 
	- 자기 자신을 참조해야 하는 예시
```java
// 이벤트 리스너가 자기 자신을 등록 해제해야 하는 경우
public void oneTimeListener() {
    eventBus.register(new EventListener() {
        @Override
        public void onEvent(Event e) {
            handleEvent(e);
            eventBus.unregister(this);  // 자기 자신을 등록 해제
        }
    });
}
```

# ITEM 43 람다보다는 메서드 참조를 사용하라
> **핵심**
> 람다보다 **메서드 참조가 더 간결할 때**가 있음 (100%는 아님)

- `Integer` 클래스에서 람다와 기능이 같은 정적 메서드 `sum`을 제공
**예시**
```java
// ❌ 람다 사용
map.merge(key, 1, (count, incr) -> count + incr);

// ✅ 메서드 참조 - 더 간결함: sum이라는 정적 메서드 활용
map.merge(key, 1, Integer::sum);
```

**메서드 참조 유형 5가지**

|유형|예시|같은 기능의 람다|
|---|---|---|
|정적|Integer::parseInt|str -> Integer.parseInt(str)|
|한정적 인스턴스|Instant.now()::isAfter|t -> then.isAfter(t)|
|비한정적 인스턴스|String::toLowerCase|str -> str.toLowerCase()|
|클래스 생성자|TreeMap::new|() -> new TreeMap()|
|배열 생성자|int[]::new|len -> new int[len]|


# ITEM 44 표준 함수형 인터페이스를 사용하라
> **핵심**
> 직접 함수형 인터페이스를 만들지 말고 `java,util.function` 패키지의 **표준 함수형 인터페이스**를 사용해라

**기본 인터페이스 6개**

| 인터페이스               | 의미                |
| ------------------- | ----------------- |
| `Supplier<T>`       | T를 제공하는 함수        |
| `Consumer<T>`       | T를 받아서 처리(반환 없음)  |
| `Function<T,R>`     | T → R 변환          |
| `Predicate<T>`      | T 검증해서 boolean 반환 |
| `UnaryOperator<T>`  | T → T             |
| `BinaryOperator<T>` | (T,T) → T         |

**에시**
```java
// LinkedHashMap에서 오래된 엔트리 제거
map.merge(key, 1, Long::sum);  // BinaryOperator 활용

// 스트림 필터링
words.stream()
     .filter(word -> word.length() > 5)  // Predicate 활용
     .collect(toList());
```

# ITEM 45 스트림은 주의해서 사용하라 
> **핵심**
> 스트림을 **남용하면** 오히려 코드 읽기 어려워지니까 적절하게 사용 필요

#### 스트림?
- 데이터 원소들의 **시퀀스**(흐름)
	=> 그러니까 데이터를 파이프라인에 플려보내면서 처리하는 방식
    **비유**
    - 일반 for문: 공장 라인에서 물건 하나씩 꺼내서 직접 처리
    - stream: 컨베이어 벨트에 물건 올려놓고 자동으로 처리
```
[데이터] → filter → map → sorted → collect → [결과]
           ↓        ↓      ↓         ↓
         거르기   변환   정렬    모으기
```
- 이 위에서 filter/map/sort 같은 연산을 단계별로 수행하는 구조
- for-loop을 대체하는 선언적 방식

**스트림은 “값의 흐름”을 다루는 도구**
- for-loop = 명령형, 흐름을 제어
- stream = 선언형, “무엇을 할지”만 선언

**lazy evaluation(지연 평가)**
- 중간 연산은 실행되지 않고, 종단 연산이 실행되는 순간
- 필요한 것만 계산됨 → 불필요한 반복 줄어듦

#### 스트림 파이프라인 구조
- **소스(Stream Source)**: 리스트, 배열, 파일, 난수...
- **중간 연산(Intermediate)**: filter, map, sorted, distinct 등
	-> 스트림을 "변환"
    -> **지연 연산(lazy)**: 실제로 실행되지 않음
- **종단 연산(Terminal)**: collect, count, sum, forEach
	-> 여기에서 "실행"
- 예시
```java
long count = words.stream()
    .filter(w -> w.length() > 3)   // 중간
    .map(String::toUpperCase)      // 중간
    .count();                      // 종단

```
**장점**
1. 가독성 - 무엇을 하는지 명확함
```java
// ❌ for문 - 어떻게(How) 하는지에 집중
List<String> emails = new ArrayList<>();
for (User user : users) {
    if (user.isActive()) {
        emails.add(user.getEmail());
    }
}

// ✅ 스트림 - 무엇을(What) 하는지에 집중
List<String> emails = users.stream()
    .filter(User::isActive)     // "활성 사용자만"
    .map(User::getEmail)        // "이메일을"
    .collect(toList());         // "모은다"
```
2. 지연 평가 - 효율적 <= 아직도 이게 왜 효율적인지 모르겠음
```java
List<User> users = getMillionUsers();  // 100만 명

// 중간 연산은 실행 안 됨! (설계만 함)
Stream<String> stream = users.stream()
    .filter(User::isActive)      // 아직 실행 X
    .map(User::getName)          // 아직 실행 X
    .limit(10);                  // 아직 실행 X

// 종단 연산에서 한 번에 실행! (필요한 만큼만)
List<String> top10 = stream.collect(toList());  // 여기서 실행!
// → 100만 명 다 처리 안 하고, 10명만 찾으면 멈춤!
```
3. 병렬 처리 쉬움
```java
// 순차 처리
long count = users.stream()
    .filter(User::isActive)
    .count();

// 병렬 처리 - .parallel() 한 줄만 추가!
long count = users.stream()
    .parallel()  // 이것만 추가!
    .filter(User::isActive)
    .count();
```
#### 스트림 사용 주의사항
**스트림은 "읽기 좋은 코드"를 만들지만**
- 모든 곳에 쓰면 오히려 읽기 어려움
- 디버깅 어려움
- 상태 많이 쓰면 스트림과 안 맞음
	-> 스트림은 "순수 함수"를 기대해서 안 맞음
```java
// ❌ 나쁜 예 - 외부 상태 변경 (부작용)
int sum = 0;  // 외부 변수
users.stream()
    .forEach(user -> sum += user.getAge());  // 컴파일 에러!
// → sum은 final이어야 함. 수정 불가!

// ❌ 억지로 하려면 배열 써야 함 (나쁜 코드)
int[] sum = {0};
users.stream()
    .forEach(user -> sum[0] += user.getAge());  // 작동하지만 나쁨!

// ✅ 좋은 예 - 외부 상태 안 건드림
int sum = users.stream()
    .mapToInt(User::getAge)  // 순수 함수
    .sum();                  // 순수 함수
```
- 복잡한 for-loop는 스트림보다 명령형 코드가 나음
```java
// ❌ 스트림으로 하기 어려운 경우들

// 1. 중간에 멈춰야 할 때
// for문 버전 - 명확함
for (User user : users) {
    if (user.getName().equals("희수")) {
        return user;  // 찾으면 바로 종료
    }
}

// 스트림 버전 - 비효율적
users.stream()
    .filter(user -> user.getName().equals("희수"))
    .findFirst()  // 이게 최선이지만 전체를 순회할 수도 있음
    .orElse(null);

// 2. 여러 컬렉션을 동시에 업데이트해야 할 때
List<User> activeUsers = new ArrayList<>();
List<User> inactiveUsers = new ArrayList<>();

// for문 버전 - 자연스러움
for (User user : users) {
    if (user.isActive()) {
        activeUsers.add(user);
    } else {
        inactiveUsers.add(user);
    }
}

// 스트림 버전 - 복잡함
Map<Boolean, List<User>> partitioned = users.stream()
    .collect(partitioningBy(User::isActive));
List<User> activeUsers = partitioned.get(true);
List<User> inactiveUsers = partitioned.get(false);

// 3. 예외 처리가 필요할 때
// for문 버전 - 자연스러움
for (String file : files) {
    try {
        processFile(file);
    } catch (IOException e) {
        log.error("Failed: " + file, e);
        continue;  // 다음 파일 계속 처리
    }
}

// 스트림 버전 - 어색함
files.stream().forEach(file -> {
    try {
        processFile(file);
    } catch (IOException e) {
        log.error("Failed: " + file, e);
        // continue 못 씀!
    }
});
```

=> **장점이 확실할 때만 스트림을 쓰자**

**스트림 사용 예시**
1. 좋은 예시
```java
// ✅ 스트림을 적절히 사용
Map<String, Long> freq = words
    .collect(groupingBy(String::toLowerCase, counting()));

freq.values().stream()
    .filter(count -> count >= minGroupSize)
    .forEach(g -> System.out.println(g.size() + ": " + g));
```
2. 나쁜 예시
```java
// ❌ 스트림 과용 - 읽기 어려움
words.collect(
    groupingBy(word -> word.chars().sorted()
        .collect(StringBuilder::new,
            (sb, c) -> sb.append((char) c),
            StringBuilder::append).toString()))
    .values().stream()
    .filter(group -> group.size() >= minGroupSize)
    .forEach(/* ... */);
```
**스트림은 언제 사용하는 게 좋을까?**
- 원소들 일괄 변환
- 원소들 필터링
- 원소들 하나의 연산으로 결합 (합계, 최댓값 등)
- 원소들 컬렉션에 모을 때
- 특정 조건을 만족하는 원소를 찾을 때

**스트림을 언제 피해야 할까?** (왜 피해야 하는지 와닿지 않는데?)
- 지역 변수를 수정해야 할 때
- `return`,`break`,`continue`를 사용해야 할 때
- 체크 예외를 던져야 할 때
# ITEM 46 스트림에서는 부작용 없는 함수를 사용하라
> **핵심**
> 스트림 연산에 사용하는 함수는 **부작용**(side effect)가 없어야 함

**부작용 유무 차이** => **외부 상태 변경하는지 여부**
**나쁜 예시** 
```java
// ❌ 외부 상태(freq)를 변경함 - 나쁜 코드!
Map<String, Long> freq = new HashMap<>();
words.forEach(word -> {
    freq.merge(word.toLowerCase(), 1L, Long::sum);
});
```
**좋은 예시**
```java
// ✅ 순수 함수만 사용 - 좋은 코드!
Map<String, Long> freq = words
    .collect(groupingBy(String::toLowerCase, counting()));
```
**Collectors의 주요 메서드** 
- Colletors는 "안전하게" 결과를 수집(부작용이 없음)
```java
// toList, toSet, toMap
List<String> topTen = freq.keySet().stream()
    .sorted(comparing(freq::get).reversed())
    .limit(10)
    .collect(toList());

// groupingBy - 그룹화
Map<String, List<Word>> byFirstLetter = words.stream()
    .collect(groupingBy(word -> word.substring(0, 1)));

// joining - 문자열 연결
String result = words.stream()
    .collect(joining(", "));
```


# ITEM 47 반환 타입으로는 스트림보다 컬렉션이 낫다
> **핵심**
> 공개 API에서 시퀀스를 반환할 땐 **스트림, 반복문 모두 지원해야**함
> 가장 좋은 방법은 **Collection 반환**

- **Collection**: List, Set의 상위 인터페이스로, 스트림과 for-each 모두 지원
```java
// Collection 계층 구조
Iterable (인터페이스)
    └── Collection (인터페이스)
            ├── List (인터페이스)
            │    ├── ArrayList (구현)
            │    └── LinkedList (구현)
            └── Set (인터페이스)
                 ├── HashSet (구현)
                 └── TreeSet (구현)

// Collection을 반환하면 사용자가 선택 가능!
public List<User> getUsers() {  // List는 Collection의 하위 타입
    return userRepository.findAll();
}

// 사용자 1 - 스트림 사용
long count = getUsers().stream()  // ✅ 가능!
    .filter(User::isActive)
    .count();

// 사용자 2 - for-each 사용
for (User user : getUsers()) {    // ✅ 가능!
    System.out.println(user.getName());
}

// 사용자 3 - 인덱스 접근
List<User> users = getUsers();
User first = users.get(0);        // ✅ 가능!
```

**예시**
```java
// ✅ Collection 반환 - 스트림과 for-each 모두 가능
public List<String> getUsers() {
    return userRepository.findAll().stream()
        .map(User::getName)
        .collect(toList());
}

// 사용자는 원하는 방식 선택 가능
// 방법 1: 스트림
getUsers().stream().filter(/* ... */);

// 방법 2: for-each
for (String user : getUsers()) {
    // ...
}
```
**메모리 고려사항**
- 가능하면 **그냥 Collection을 return**해라
- 결과가 **작으면** -> `ArrayList`,`HashSet` 반환
- 결과가 **크면** -> 전용 컬렉션 구현
- 결과가 **너무 크면** -> 스트림이나 Iterable 반환 (Stream이 Iterator를 지원하지 않는다는 것은 무슨 말임? => 지원 안 해서 for-each를 못 쓴다고 함)

# ITEM 48 스트림 병렬화는 주의해서 적용하라
> **핵심**
> **무작정** `.parallel()` **붙이지 마라**

**parallel() 한 줄만 추가해도 병렬화 가능**
```
long count = 
    IntStream.range(2, n)
        .parallel()
        .mapToObj(BigInteger::valueOf)
        .filter(i -> i.isProbablePrime(50))
        .count();
```
**문제점**
1. 성능 향상 보장 X
2. 스트림 연산이 "상태 의존적"이면 병렬화 X 
	-> 이전 단계 결과에 의존하면 병렬 처리가 불가능함 (순서 보장이 안 되고 동시성 문제 발생)
```java
// ❌ 상태 의존적 - 병렬화 불가
List<Integer> numbers = Arrays.asList(1, 2, 3, 4, 5);
List<Integer> results = new ArrayList<>();

numbers.parallelStream()
    .forEach(n -> {
        // 이전 결과에 의존!
        int last = results.isEmpty() ? 0 : results.get(results.size() - 1);
        results.add(n + last);  // 위험!
    });
// → 순서 보장 안 됨, 동시성 문제 발생

// ✅ 상태 독립적 - 병렬화 가능
List<Integer> results = numbers.parallelStream()
    .map(n -> n * 2)  // 각 원소가 독립적!
    .collect(toList());
// → 안전하게 병렬 처리 가능
```
3. Random, IO 같은 건 병렬에 최악

**병렬화 효과적?**: 데이터 구조의 **분할 가능성**이 핵심

**병렬화 효과적인 경우**
```java
// ✅ ArrayList, 배열, IntStream.range 등은 병렬화 효과 좋음
public static long pi(long n) {
    return LongStream.rangeClosed(2, n)
        .parallel()  // 이 경우는 효과적!
        .mapToObj(BigInteger::valueOf)
        .filter(i -> i.isProbablePrime(50))
        .count();
}
```
**병렬화 피해야 하는 경우**
```java
// ❌ Stream.iterate나 limit 사용 시 병렬화 효과 없음
Stream.iterate(2, n -> n + 1)
```
