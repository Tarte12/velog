> ### 서론
- final이 아닌 Object 메서드들을 언제 어떻게 재정의해야 하는가?
- item 8에서 다룬 finalize 제외
- Comparable.compareTo의 경우 Object 메서드는 아니지만 성격이 비슷하여 같이 다룸

** Object 클래스**
- **모든 클래스의 조상** => 자바에서 어떤 클래스를 만들든 `extends Object`가 자동으로 들어간다고 볼 수 있음
- ** 상속**해서 사용하도록 설계
- Object의 **equals, hashCode, toString, clonde, finalize**는 모두 **재정의(overriding)**을 염두하고 설계
- 따라서 재정의를 위한 일반 규약 존재

| 메서드          | 역할                          | 현실 비유            |
| ------------ | --------------------------- | ---------------- |
| `equals()`   | 두 객체가 “같은 값”을 가지는지 비교       | 주민등록번호가 같은지 확인   |
| `hashCode()` | 객체를 해시 테이블에 넣기 위한 번호(주소 아님) | 우편번호처럼 분류용       |
| `toString()` | 객체를 문자열로 표현                 | 명함에 이름 적는 것      |
| `clone()`    | 객체 복제                       | 복사기              |
| `finalize()` | GC 직전 정리                    | (거의 폐기됨, 이제 안 씀) |

# Item 10 equls는 일반 규역을 지켜 재정의하라
## equals
- 두 개의 인스턴스의 논리적 동치성을 확인하기 위해 사용
=> **"같은 객체인가?"가 아니라 "같은 값인가?"를 묻는 함수**
	- `==`는 **참조(주소)** 비교
    - `equals()`는 **논리적 값** 비교
- 주의: equls를 직접 사용하지 않아도 다른 클래스 함수에서 사용함
	- Ex) Collection의 contain 함수
    
## 언제 재정의해야 할까?
### 구현하지 않을 경우
- 각 인스턴스가 본질적으로 고유할 경우 => `Thread`, `Socket`, `Random`
- 인스턴스의 논리적 동치성을 검사할 일 X
- 상위 클래스의 equls가 하위 클래스와 동일하게 동작해도 괜찮음
- private, default class

> **두 인스턴스가 다른 객체더라도 같은 데이터를 담고 있다면 같다고 취급해야 할 때 재정의**

### 구현할 때 만족해야 하는 조건
- 어노테이션으로 생성된 equals는 다음을 만족함
#### 반사성
- x!=null일 때 x.equals(x)는 true
#### 대칭성
- x!=null, y!=null일 때 ((x.equals(y)==true) ==(y.equals(x)==true))는 true
#### 추이성
-  x!=null, y!=null, z!=null일 때 (x.equals(y)==true), (y.equals(z)==true)라면 x.equals(z)==true 
#### 일관성
- x!=null, y!=null일 때 x.equals(y)는 언제나 동일한 값을 반환
#### Non-null
- x!=null일 때 x.equals(null)은 언제나 false

# Item 11 equls를 재정의하려거든 hashCode도 재정의하라
## hashCode
- 주의: 논리적 동치인 두 클래스에 대해 동일한 해시값이 계산되어야 함
- HashMap, HashSet 등을 사용할 때 필요한 함수
- HashMap, HashSet은 내부적으로 아래처럼 동작
	1. 객체의 hashCode() 값을 버킷으로 나눠 저장
    2. 같은 버킷 안에서는 equals()로 실제 비교
따라서, 
- equals()가 같다면 hashCode()도 같아야 함
- 그렇지 않으면 HashSet, HashMap에서 논리적 중복이 발생
> hashCode()는 컬렉션에 넣을 때 필요한 "주소표"

- 해시코드 계산 방법: 인스턴스의 모든 값에 대해 hashCode() 함수를 재귀적으로 호출하는 것
- Lombok의 `@EqualsAndHashCode`를 애용하자

# Item 12 toString을 항상 재정의하라
## ToString
- 디버깅, 로깅 시 toString()을 사용하면 사람이 객체를 읽기 쉽게 표현 가능 => 가독성을 위한 재정의
- 구현하지 않을 경우 `클래스명@16진수 HashCode`가 반환되므로 큰 의미없는 정보만 반환
- Lombok의 `@ToString`, AutoValue의 `@AutoValue`가 자동 생성해 주고, 필드 변경 시 따로 수정해 주지 않아도 되므로 직접 작성하지 않고 라이브러리를 사용하자

```java
@Override
public String toString() {
    return String.format("User[id=%d, name=%s]", id, name);
}
```

# Item 13 clone 재정의는 주의해서 진행하라
- 가끔 특정 객체를 복제해야 할 경우, `Cloneable` 인터페이스를 구현/확장한 경험이 있을 것
- `Cloneable`은 Object 클래스의 protected `clone()` 함수를 사용하기 위해 사용되는데 
=> `clone()`을 상속하는 것보다 **`복사 생성자` 혹은 `복사 팩터리`f**를 사용하는 것이 좋은 방식
- `clone()` 함수의 상속 자체가 OOP와 잘 맞지 않음

### clone이 망가진 함수인 이유
1. **대부분의 경우 연쇄적인 clone()만으로 원하는 결과 낼 수 없음**
2. **위의 이유로 문서가 모호함**
3. **내부적으로 아무 함수도 없는 Cloneable 인터페이스를 상속해야 함**
4. **전통적인 인스턴스 생성 방식을 사용하지 않음**

### 복사 생성자 or 복사 팩터리
```java
public Yum(Yum yum) { ... };

// OR

public static Yum newInstance(Yum yum) { ... };
```
**인스턴스를 받아서 복사하는 방법**
- 전통적인 생성자를 사용하여 인스턴스 생성
- Cloneable/clone의 불완전한 규약과 디자인을 상속하지 않아도 됨
- final 필드 사용 가능
- 인수 받을 수 있음

# Item 14 Comparable을 구현할지 고려하라
## Comparable
- 정렬 기준을 정의하는 인터페이스
### 예시 상황
- 정렬이 필요한 컬렉션(`TreeSet`, `TreeMap`, `Collections.sort`)
- 사용자 정의 클래스 간의 우선순위 비교(예: `User`의 나이순 정렬)
```java
public class User implements Comparable<User> {
    private int age;

    @Override
    public int compareTo(User o) {
        return Integer.compare(this.age, o.age);
    }
}
```
- Compareable/CompareTo는 대부분 Collection 인터페이스를 사용하기 위해 구현
-  sort(), TreeSet, TreeMap에도 기본적으로 사용됨
- 반사성, 대칭성, 추이성 지켜야 함 (equals처럼 "값의 크기 비교"에 대한 규약을 지켜야 함)
- 주의: <, >, - 로 비교 X
- if문을 여러 개 사용하는 것보다 Comparater 클래스의 정적 함수를 사용하여 정적 Comparator를 생성 후 이를 사용하는 것을 권장

# 요약: 객체의 기본 행위 규약
| 메서드       | 의미         | 대표 상황            | 자동 생성                     |
| --------- | ---------- | ---------------- | ------------------------- |
| equals    | 논리적 동일성 비교 | VO, DTO, record  | Lombok/@EqualsAndHashCode |
| hashCode  | 해시 컬렉션 관리  | HashMap, HashSet | Lombok/@EqualsAndHashCode |
| toString  | 디버깅, 로깅    | 로그, 예외 메시지       | Lombok/@ToString          |
| clone     | 객체 복제      | 복제 필요 시          | 직접 구현 권장 X                |
| compareTo | 정렬/순서 정의   | sort(), TreeSet  | Comparable 구현             |
