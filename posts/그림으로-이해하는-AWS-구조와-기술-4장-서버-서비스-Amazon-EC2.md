## 4.1 Amazon EC2
### 4.1.1 Amazon EC2

Amazon EC2(Amazon Elastic Compute Cloud) : 컴퓨팅 용량 제공 서비스 -> 서버에 필요한 세트를 클라우드에서 빌릴 수 있음
임대 서버 : 이미 만들어진 서버 기계 or 서버 기능을 빌리는 것
클라우드 : 도구를 빌려 '자신의 서버'를 만드는 것
- EC2는 매니지드 서비스 X
=> 따라서 운영은 AWS가, OS를 포함해 필요한 SW는 사용자가 직접 설치하고 운영

### 4.1.2 클릭 한 번으로 최적의 서버를 만들 수 있다
- EC2는 서버를 직접 만드는 것이긴 하나, 관리 콘솔에서 생성하기 때문에 기술적 지식은 부실해도 괜찮음
- 다양한 서버 시스템의 조합(인스턴스 유형), OS 및 SW 조합(AMI)이 준비되어 있어 선택만 하면 되는 구조
(인스턴스 유형이랑 AMI가 머지...)
- 물리적 기계 필요 X -> 초기 투자 비용 줄일 수 있음
- 자유도가 높고 관리하기는 번거로움
=> 매니지드 서비스가 아니기 때문, AWS가 강제로 업데이트를 하지 않아 사용자가 관리해야
- '어떻게 구성할까?', '어느 정도의 성능이 필요할까?' 설계적 관점 필요

#### <EC2 서버 생성 장점>
1. 누구든지 바로 사용 가능
2. 여러 가지 선택 가능
3. 백업 취득 쉬움(가상화 기술)
4. 어디에서든 접속(클라우드)
5. 물리적으로 다른 여러 장소에 설치 가능(리전과 가용 영역)

### 4.1.3 바로 생성할 수 있고 바로 삭제할 수 있다
- '테스트용 서버', '서버 지식 없는 사람이 서버를 만들고 싶을 때'
=> 누구든지 쉽게 서버를 생성할 수 있기 때문에
- 불필요한 리소스 유지 필요 X
- 불확실성이 많은 경우 유용
=> 바로 생성하고 바로 삭제할 수 있는 장점 덕분

#### <바로 생성/삭제할 수 있는 장점>
1. 고장 : 같은 서버 복제가 쉬움 -> 바로 복구 가능
2. 부하 증가 : 같은 구성의 서버 복제 -> 부하 분산 쉬움
3. 접속 줄었을 경우 : 서버 사양 스케일 다운 -> 비용 축소
4. 일시적 사용 

### 4.1.4 인스턴스 유형 및 OS 선택
- EC2로 서버를 생성할 때 인스턴스 유형을 선택하여 구성 가능
=> 어떤 OS를 사용할 것인지, SW를 설치할 것인지, 어떤 AMI를 선택할 것인지
#### <서버를 생성할 때>
1. 미리 설치할 내용 선택 : OS, SW 설치 및 설정 끝난 인스턴스 사용 VS OS만 설치된 상태 사용
2. 인스턴스 선택 : 저사양 VS 고사양
3. 다른 것과 조합할 것인지 : Only EC2 VS 다른 기술과 함께 AWS 사용

## 4.2 EC2 사용 절차 : 가상 서버 사용
- EC2 대시보드를 열어 인스턴스를 생성하면 EC2 사용 가능
- 대시보드에서 인스턴스 유형 선택 or 보안 그룹 설정 가능

### 4.2.1 EC2 운영
- 서버 관리자의 업무
1. 서버 설치, 서버의 HW 및 주변 환경 구축 물리적 작업
2. 서버 OS에 로그인하여 작업하는 소프트웨어적 작업
=> 물리적 작업 : EC2 관리 콘솔에서 작업 가능
=> 소프트웨어적 작업 : 어떤 환경이든 관계 없이 SSH를 이용해 원격으로 로그인 하여 작업
- SSH : 서버를 원격에서 작업하기 위한 프로토콜
(프로토콜은 뭐지)

### 4.2.2 EC2 서비스 기능
#### <주요 기능>
1. 인스턴스 : AWS 클라우드에 생성한 가상 서버
2. AMI : 가상 이미지 -> 인스턴스를 생성하는 기준이 되는 금형 같은 것
3. 키 페어 : 인스턴스에 접속할 떄 인증을 위해 사용하는 키
4. EBS : AWS 클라우드에서 사용할 수 있는 스토리지 -> 인스턴스 스토리지로 사용
5. 보안 그룹 : 가상 방화벽
6. Elastic IP : 정적 IPv4

### 4.2.3 EC2의 사용 절차
#### <가상 서버 구축 절차>
1. AWS에 로그인
- 리전 선택, 관리 콘솔 열기
- EC2 대시보드 열기
2. EC2 인스턴스 생성
- AMI 선택
- 인스턴스 유형 선택
- 네트워크와 IP 주소 할당
- 스토리지 추가
- 보안 그룹 설정
- 키 페어 선택
3. EC2에 접속
- SSH로 EC2 접속
4. SW 설치, 설정

### 4.2.4 인스턴스 설정 항목
1. AMI : EC2 인스턴스 가상 이미지 -> SW 구성을 작성한 템플릿
2. 인스턴스 유형 : EC2 인스턴스 장비 사양 -> CPU, 메모리, 장비 유형 결정
3. 리전 : 서버를 설치할 지역
4. 네트워크 : EC2 인스턴스를 배치할 네트워크
5. 서브넷 : 설치할 네트워크 범위
6. IAM 역할 : 인스턴스의 접속 권한 정책 설정 -> 다른 서비스에 접속하고 싶을 떄 할당
7. 스토리지 용량과 종류
8. 태그(EC2 인스턴스의 레이블) : 인스턴스에 임의의 태그 부여 가능
9. 보안 그룹 : 프로토콜별로 포트 혹은 IP 주소, 아니면 양쪽 모두 필터링 설정

## 4.6 Amazon EBS : Amazon EC2의 스토리지 볼륨

### 4.6.1 EBS란?
- Amazon EBS(Amazon Elastic Block Store) : 영구적인 블록 스토리지 볼륨, EC2 인스턴스와 조합하여 사용
- 스토리지 : 데이터 기록 장소, 대표적인 스토리지는 HDD, SSD
- 블록 스토리지 볼륨은 바이트 블록 단위로 디스크에 저장하는 일반적인 방식
- AWS 서비스인 Amazon S3는 오브젝트 스토리지 방식 채댁
- EBS는 HDD와 SSD 선택 가능
- HDD : 대용량 지원, SSD보다 가격이 싸지만 성능 낮음
- SSD : 가격이 조금 비싸지만 IOPS(1초간 처리할 수 있는 입출력 수)가 빠름
- 고성능은 SSD, 저비용은 HDD 채택

### 4.6.2 EBS 볼륨 유형
- HDD, SSD 모두 IOPS 성능을 보장하는 유형과 스루풋에 최적화된 유형 등의 볼륨 유형 있음 -> 성능과 요금을 비교해 보고 선택 가능

### 4.6.3 EBS의 기능과 요금 : EBS에 여러 편리 기능 존재
1. 탄력적 볼륨 : 볼륨 크기 간단 조정 가능
2. 스냅샷 : 어떤 시점의 데이터를 통으로 저장하는 기능
3. 데이터 라이프 사이클 매니저 : 일정에 따른 스냅샷 생성, 삭제 기능
4. 최적화 인스턴스 : 특정 스턴스 유형을 최적화 인스턴스로써 읽기 쓰기를 고속화하는 기능
5. 암호화 : 데이터 볼륨, 부팅 볼륨 및 스냅샷 암호화 기능

- 요금 : 단가 X 저장 시간
- 사용 여부와 관계 없지 저장하고 있는 용량 만큼 비용 부과
- 서버를 정지해도 요금 부과

## 4.7 SSH를 사용한 접속과 키 페어 : 공개키 암호 방식을 이용한 접근 관리용한 접근 관리
- EC2도 서버에 설치한 SW의 SSH로 관리 -> 키 페어 방식 사용
- 키 페어 파일을 분실 -> 서버 자체를 다시 만들어야 하므로 조심해야 함

### 4.7.1 SSH로 접속하기
- 서버 성능을 올리거나 내리거나 백업하는 등 서버의 전반적인 작업은 관리 콘솔에서 수행
- 서버에서 설치한 소프트웨어를 조작하려면 SSH 방식을 사용해 원격 접속으로 조작하는 것이 일반적격 접속으로 조작하는 것이 일반적
=> 따라서, 서버에서 SSH를 사용하기 위한 프로그램(데몬)을 기동하고, 클라이언트에는 조작하기 위한 SW를 설치해야 함
- 서버에 SSH를 사용하기 위한 프로그램을 설치하지 않아도 OS에 이미 설치되어 동작하고 있음
- 클라이언트는 Putty나 Tera Team 같은 소프트웨어 주로 사용

### 4.7.2 키 페어
- 키 페어 : 로그인할 때 인증으로 사용, 공개키와 비밀키로 된 한 쌍을 말함
- 공개키 방식이라고 불리며 자물쇠를 잠그는 키와 자물쇠를 여는 키를 공캐키와 비밀키로 조합하여 사용하는 방법
- 공개키 : 자신 외에도 공개된 키
- 비밀키(개인키) : 자신만 알고 있는 키
- 두 가지 키는 한 세트이며, AWS는 이 두 키를 파일 하나로 취급
- SSH로 서버(인스턴스)에 접속할 때, 인스턴스쪽에서 키 페어에 포함되어 있는 '공개키'를 지정
- 클라이언트쪽 소프트웨어에는 내려받은 '키 페어 파일'을 '비밀키'로 설정하여 사용
- 키 페어는 생성했을 때만 내려받기가 가능하며 재발행 불가
- 잊어버렸을 경우에는 서버 재구축 필요
- 다른 리전에서는 사용할 수 없지만 같은 리전의 서비스라면 공통의 키 페어 사용 -> 추가 비용 X

## 4.8 Elastic IP 주소 : 고정 공인 IP 주소를 부여
- AWS에는 고정 IP 주소로 Elastic IP(탄력적인 IP) 주소를 제공
- Elastic IP 주소는 AWS 계정에 속해 있기 때문에 인스턴스를 삭제해도 계속 사용할 수 있음

### 4.8.1 Elastic IP 주소란
- Elastic IP 주소 : AWS가 제공하는 정적인 공인(public) IPv4 주소이다.
- EC2 인스턴스는 정지 후 다시 시작하면 공인 IP 주소가 바뀌게 됨 -> 서버로서 사용하는 데에 문제가 됨
- 고정 IP 주소를 인스턴스와 연결해야 함
=> 고정 IP로 사용되는 것이 Elastic IP

### 4.8.2 Elastic IP 주소의 확보와 부여
- Elastic IP 주소는 AWS 계정에 연결되어 있음
- IP 주소를 부여한 인스턴스를 삭제해도 확보한 IP 주소는 그대로 AWS 계정에 소유 가능
- 보유하고 있는 IP 주소는 다른 인스턴스나 네트워크에 부여 가능 네트워크에 부여 가능

### 4.8.3 Elastic IP 주소의 요금
- 기본적으로 인스턴스에 부여된 IP 한 개는 무료
- 추가로 IP를 연결하면 IP는 시간에 비례하여 요금이 부과됨
- 소유한 IP가 중지된 인스턴스나 분리된 네트워크에 연결된 경우에도 시간당 요금이 부과
- 따라서 사용하지 않는 IP 주소는 해지하는 것이 좋음

## 4.9 Elastic Load Balancing : 트래픽을 분배하는 분산 장치
- AWS는 로드 밸런서로 ELB를 제공 -> 트래픽을 잘 분산하여 서버 안정적 운영 가능

### 4.9.1 ELB란?
- ELB : AWS가 제공하는 로드 밸런서
- 로드 밸런서 : 서버에 집중되는 접속(트래픽)을 서버 여러 대나 네트워크에 분배되는 방식
- 서버 한 대에 집중되는 부하를 분산시키기 때문에 부하 분산 장치라고도 함

### 4.9.2 ELB의 종류
1. ALB(Application Load Balancer)
- HTTP 및 HTTPS에 가장 적합한 로드 밸런서
- OSI 모형의 애플케이션 계층에서 동작
- 대상의 URL 디렉터리 단위로 분배하는 것이 가능 : 요청되는 명령어의 내용을 보고 판단하기 때문에
- 인스턴스와 로드 밸런서 사이의 통신은 암호화 가능
- 분배 대상으로 정적 IP 주소를 설정하고 그 IP를 가진 호스트 기기로 전송 불가
2. NLB(Network Load Balancer)
- OSI 모형의 전송 계층에서 동작
- 패킷이라고 불리는 단편 데이터밖에 볼 수 없어 ALB만큼 상세하게 분석 불가
- 분배 대상의 정적 IP 주소 설정 가능
- 서버 접속 클라이언트 IP 주소를 그대로 서버에 전송하도록 설정 가능
3. CLB(Classic Load Balancer)
- 오래된 유형의 로드 밸런서
- 지원하는 프로토콜이 많은 것이 장점
- 앞으로 구축할 시스템에는 사용하지 않는 것을 권장

### 4.9.3 ELB의 요금
- 요금 = 사용 요금 + LCU 요금
- 사용 요금(사용 단가 X 시간)
- LCU 요금(LCU 사용량 X LCU 단가 X 시간)
- LCU 4가지 항목
1. 새 연결 수
2. 활성 연결 수
3. 처리된 바이트
4. 규칙 평가

## 4.10 스냅샷 : 서버 데이터 백업
- 스냅샷을 작성해 Amazon EBS 볼륨 데이터를 Amazon S3에 백업할 수 있음
- 생성된 스냅샷은 바로 사용 가능한 복제본
- 백업용으로 많이 사용

### 4.10.1 스냅샷이란
- 스냅샷 : 어떤 시점의 서버 디스크 상태를 통으로 보존한 파일 or 폴더의 집합
- 통으로 보존하기 떄문에 SW, OS, 설정 정보 모두 포함된
- 목적 : SW, OS 갱신 작업 등을 할 떄 무언가 문제가 발생하면 바로 되돌릴 수 있도록 백업하기 위해 사용 + 개인이 AWS에서 AMI를 만들기 위해 스냅샷을 사용
- AWS는 Amazon EBS 볼륨의 데이터를 스냅샷으로 보존 가능
But, 최초는 통으로, 두 번째 이후부터 차분(증분) 보존
- 스냅샷을 삭제하면 해당 스냅샷 고유의 데이터만 삭제됨
- 이것은 최초 데이터를 삭제할 경우 두 번째 스냅샷을 취득했을 때, 변경되지 않은 부분(고유 데이터)만 두 번째 스냅샷으로 합쳐진 후 삭제됨

### 4.10.2 EBS 스냅샷을 생성하는 방법
- 스냅샷은 관리 콘솔에서 볼륨 단위(스토리지 전체)로 선택하여 생성
- 생성한 스냅샷을 기반으로 EBS 볼륨을 생성하면, 새로운 볼륨은 원래 볼륨에 복제됨
- AMI를 작성하고 싶을 때도 스냅샷으로 작성
- 데이터 수명 주기 관리자를 사용하면 스냅샷의 생성, 삭제 자동화 가능
- 스냅샷을 정기적으로 생성하면 서버 망가졌을 때 대응 가능

## 4.11 오토 스케일링 : 수요에 맞춰 EC2 대수를 증감
- 유연성이 높다는 것은 AWS의 장점 -> 인스턴스를 쉽게 늘리거나 줄일 수 있음
- 오토 스케일링 : 인스턴스의 증감을 자동으로 실행하는 것

### 4.11.1 오토 스케일링
- 오토 스케일링 : 서버의 액세스 상태에 따라 서버 대수를 늘리거나 줄이는 기능, EC2 외의 서비스를 지원하는 오토 스케일링도 존재
- AWS는 EC22 Auto Scaling을 단독으로 사용할 뿐만 아니라 CloudeWatch에서 서버의 부하 정보 데이터를 참고하여 스케일링에 참고 가능

### 4.11.2 감시와 인스턴스 수의 설정
- Auto Scaling 그룹(인스턴스의 집합)을 생성하고 그룹에 인스턴스(서버)의 최소 대수와 최대 대수를 설정해서 오토 스케일링을 시작할 수 있음
- 이러면 이 범위 안에서 인스턴스 수가 증감
- Auto Scaling 그룹은 서버 시작에 필요한 AMI와 키 페어, 보완 그룹 등을 설정해야 함
#### <인스턴스 증감 방법>
1. EC2 인스턴스가 정지한 경우에 분리하고 새로운 EC2 인스턴스를 생성하는 방법
2. 일정에 맞춰 스케일링하는 방법
3. CPU와 네트워크 부하를 참고하여 특정 임계 값을 넘을 때 인스턴스 수를 자동적으로 증감하는 방법
- 오토 스케일링 요금 자체는 무료 But CloudWatch를 사용할 경우 모니터링에 관련된 요금 부과
