# 2. 현재 구조 분석 요약
## 2.1 Account 도메인 
### 개요
- Account 도메인은 **회원 인증(JWT), 사용자 기본 정보 관리**를 담당
- 인증은 **JWT Access Token 기반**이며, 서버는 세션 상태를 유지하지 않는 **Stateless 구조**를 따름

### 주요 기능
#### 회원가입
> Client
 → POST /account/login
 → username 기반 사용자 조회
 → 비밀번호 검증
 → JWT Access Token 발급
 → 응답 Body + HttpOnly Cookie에 토큰 저장

- username은 애플리케이션 레벨에서 중복 검사
- email은 DB Unique Constraint 기반으로 검증
- 가입 성공 시 별도 로그인 처리 없음

#### 로그인 및 인증 유지
> Client
 → GET /account/@me
 → JWT 검증
 → CurrentUser 주입
 → 사용자 정보 반환

> Client
 → PATCH /account/@me
 → JWT 검증
 → 수정 가능한 필드만 업데이트

- Access Token만 사용 (Refresh Token 없음)
- 토큰에는 `username`, `display_name`, `is_host` 포함
- 인증 정보는 이후 모든 보호 API에서 Dependency로 주입됨

#### 인증된 사용자 정보 조회/수정
> Client
 → DELETE /account/logout
 → Cookie 삭제

> Client
 → DELETE /account/unregister
 → User 데이터 삭제
 - 인증 여부만 확인하며, 별도의 권한(Role) 계층은 없음

#### 로그아웃/탈퇴
> Client
 → DELETE /account/logout
 → Cookie 삭제

> Client
 → DELETE /account/unregister
 → User 데이터 삭제

- 로그아웃 시 서버 상태 변경 없음
- 회원 탈퇴는 Soft Delete 구조가 있음에도 실제로는 Hard Delete 수행


## 2.2 Calendar/Booking 도메인 - 현재 구조 요약
### 개요
- Calendar/Booking 도메인은 Host가 예약 가능 시간을 정의하고, Guest가 이를 예약하는 구조로 구성
- 모든 요청은 Account 도메인의 인증 정보를 전제로 동작

### 주요 기능
#### Host Calendar 관리
> Host
 → POST /calendar
 → Host 여부 확인
 → Calendar 생성

> Host
 → POST /calendar
 → Host 여부 확인
 → Calendar 생성

- Host 1명당 Calendar 1개
- 권한 검증은 Endpoint에서 직접 수행

#### TimeSlot(예약 가능 시간) 관리
> Host
 → POST /time-slots
 → 기존 TimeSlot과 시간/요일 겹침 여부 검증
 → TimeSlot 생성
 
- 요일 + 시간 범위 기반 예약 가능 시간 정의
- DB 종류(SQLite / PostgreSQL)에 따라 검증 로직 분기
- 중복 검증은 애플리케이션 레벨 로직

#### 예약 생성 (Guest)
> Guest
 → POST /bookings/{host_username}
 → Host 및 Calendar 존재 여부 확인
 → 자기 자신 예약 방지
 → 과거 날짜 예약 방지
 → TimeSlot 유효성 검증
 → 동일 예약 중복 여부 확인
 → Booking 생성 및 DB 저장

- 예약 단위: 예약 날짜 + TimeSlot
- 예약 생성은 DB 기준으로 먼저 확정됨

#### 예약 조회 
**Host 기준**
- 월 단위 예약 조회
- Google Calendar 이벤트와 병합 반환
**Guest 기준**
- 본인 예약 목록 페이징 조회
#### 예약 수정/상태 변경/취소
- Host: 일정 변경, 상태 변경
- Guest: 예약 내용 수정, 예약 취소
- 공통:
	- 과거 예약 수정/취소 불가
    - 변경 사항 DB 반영 후 외부 연동 처리
#### 예약 파일 업로드
> Guest
 → POST /bookings/{booking_id}/upload
 → 본인 예약 여부 확인
 → 과거 예약 차단
 → 파일 저장

- 로컬 파일 시스템 저장 방식 사용

## 2.3 외부 연동 - 현재 구조 요약
### 개요
- 외부 연동은 Google Calendar API를 통해 예약을 외부 일정으로 동기화하는 역할
- 외부 연동은 부가 기능으로 취급
### 연동 흐름
#### 예약 생성 시
> Booking 생성
 → DB Commit
 → Background Task 실행
 → Google Calendar Event 생성
 → Event ID를 Booking에 저장

#### 예약 수정 시
> Booking 수정
 → DB Commit
 → Google Calendar Event 업데이트 (비동기)

#### 예약 취소 시
> Booking 상태 변경(CANCELLED)
 → DB Commit
 → Google Calendar Event 삭제 (비동기)

# 3. 주요 의사 결정 및 선택 근거
## 3.1 Service 계층 도입
**선택**
- Endpoint에 몰린 유스케이스 흐름을 `Service`로 이동 (`AccountService`/`BookingService`/`CalendarService`)

**근거(현재 코드 기반)**
- 현재는 endpoint가 권한/검증/DB/외부연동까지 모두 수행 → 변경 영향 범위가 큼
- Java 마이그레이션 시 Controller는 “입출력”, Service는 “유스케이스 흐름”으로 책임을 고정하면 팀 작업 분담이 쉬움
- (테스트) “create_booking 같은 유스케이스”를 단위로 검증하고, Google 연동은 mocking 가능한 경계로 분리 가능

## 3.2 트랜잭션 정책 명시
**선택**
- “예약 저장 성공”을 유스케이스 성공으로 두되, 외부 연동은 별도 정책으로 관리
- (예: google_sync_status 같은 상태/재시도 큐/재처리 배치 등 중 최소 1개는 선택)

**근거(현재 코드 기반)**
- 현재도 DB commit 이후 외부 호출이라 불일치는 설계상 허용되는 상태
- 다만 불일치가 발생했을 때 탐지/재처리 기준이 없음(print로 종료)
- Java에서는 이 “허용되는 불일치”를 상태/정책으로 표현해 운영 가능하게 만드는 게 목표

## 3.3 동시성/무결성 제어 전략
**선택**
- Booking에 DB 제약 추가: (`time_slot_id, when`) UNIQUE

**근거(현재 코드 기반)**
- 현재 Booking 중복은 select count() → insert라 동시에 들어오면 레이스 가능
- UNIQUE는 SQLite에도 가능하고, 가장 비용 대비 효과가 큼(“같은 슬롯/날짜 중복 예약” 확실히 차단)

## 3.4 외부 연동 처리 방식
**선택**
- 비동기 처리 유지
- 연동 책임은 “도메인(예약)” 밖으로 이동 (예: GoogleSyncService + 이벤트/큐/작업자)

**근거(현재 코드 기반)**
- 현재도 비동기 사용(BackgroundTasks)으로 응답 지연을 줄이는 의도는 좋음
- 문제는 endpoint 내부에 로직이 결합되어 있고 실패 정책이 없음
- Java에서는 실패/재처리/로그/모니터링 포인트를 명확히 하기 위해 구조 분리
