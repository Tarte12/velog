### 객체 지향 프로그래밍
- `객체`를 만들고 -> 객체를 조립해 프로그램을 만드는 기법

#### 객체
- 다른 것과 식별 가능한 것
- 객체 = 속성(필드) + 동작(메서드)
- `현실 세계`의 객체를 `소프르웨어 객체`로 설계하는 것 -> `객체 모델링`

#### 객체의 상호작용
- 객체는 다른 객체와 서로 상호작용하며 동작
- 메서드 -> 객체들 사이의 상호작용 수단
- 메서드 호출을 통해 객체들은 `데이터`를 서로 주고받음
- 매개값: 메서드가 **실행할 때** 필요한 값
- 리턴값: 메서드의 **실행 결과**, 호출한 곳으로 반환하는 값

#### 객체 간의 관계
- **집합 관계**: 완성품과 부품
- **사용 관계**: 다른 객체의 필드를 읽고 변경하거나 메서드 호출
- **상속 관계**: 부모와 자식

#### 객체 지향 프로그래밍의 특징

**캡슐화**
- 필드와 메서드를 하나로 묶어 **실제 구현 내용을 외부에 감추는 것**
- 외부의 잘못된 사용으로 객체가 손상되는 걸 방지하기 위해 필드와 메서드 보호
- 자바의 경우 **접근제한자**를 통해 캡슐화된 멤버의 노출 여부 결정

**상속**
- 부모 역할의 상위 객체와 자식 역할의 하위 객체 존재
- 부모 클래스 -> 자식 클래스 
- **필드, 메서드**를 자식 클래스에 물려주어 사용할 수 있게 함
- 코드의 재사용성을 높여 줌
- 유지 보수 시간을 최소화시킴

**다형성**
- 사용 방법은 같지만 실행 결과가 다양하게 나오는 성질
- 다형성 구현 위해 `자동 타입 변환`, `재정의` 기술이 있어야 함 -> 상속과 인터페이스 구현으로 얻어짐

**Q1. 매개변수명이 달라도 되지 않을까?**
- 매개변수 이름을 다르게 하면 this 안 써도 되는 건 맞음
```
public class Car {
  String model = "Hyundai";
    String color;

  int speed;
    
  #생성자 
  public Car(String m, String c, int s) {
      mode = m;
      color = c;
      speed = s;
  }
}
```
- 이렇게 쓰면 `this.model` 안 써도 바로 할당할 수 있음
- **매개변수명과 필드명을 같게 짓는 게 직관적**이라 this를 써서 통일시키는 것

```
public Car(String model, String color, int speed) {
    this.model = model;
    this.color = color;
    this.speed = speed;
}
```
**Q2. this가 정확하게 무엇을 의미하는 걸까?**
- `this`: 현재 객체 자기 자신을 의미
- 어떤 객체가 생성되었을 떄, 그 **객체 자기 자신을 가리키는 참조값**이 `this` 안에 들어있는 것
```
Car c1 = new Car("Hyundai", "white", 100);
Car c2 = new Car("BMW", "black", 120);
```
- `c1` 생성 -> `this.model = model;`은 `c1.model ="Hyundai"`로 동작
- `c2` 생성 -> `this.model = model;`은 `c2.model ="BMW`로 동작
=> **this는 "현재 내가 누구냐"에 따라 바뀌는 자기 참조

#### 생성자 오버로딩
- 생성자 오버로딩: 매개변수를 달리하는 **생성자를 여러 개 선언** (매개변수의 타입, 개수, 순서가 다름)
- 매개변수의 타입, 개수, 순서가 동일한데 매개변수명만 바꾸는 것은 생성자 오버로딩 X
```
public class Car {
    String model = "Hyundai";
    String color;

    int speed;

    public Car() {
    }

    public Car(String model) {
        this.model = model;
    }

    public Car(String model, String color) {
        this.model = model;
        this.color = color;
    }

    public Car(String model, String color, int speed) {
        this.model = model;
        this.color = color;
        this.speed = speed;
    }
}
```
#### 다른 생성자 호출
- 생성자 오버로딩이 많아지면 생성자 사이에 중복 코드 발생
- 이 경우에 공통 코드를 한 생성자에 집중시키고 나머지 생성자는 `this()`를 사용해 공통 코드 생성자를 호출하는 방법으로 개선할 수 있음
- `this`는 생성자의 첫 줄에 작성되며 다른 생성자를 호출하는 역할
```
public class Car {
    String model;
    int speed;

    // 1. 기본 생성자
    public Car() {
        this("Unknown", 0); // 3번 생성자 호출
        System.out.println("기본 생성자 호출");
    }

    // 2. 모델만 받는 생성자
    public Car(String model) {
        this(model, 0); // 3번 생성자 호출
        System.out.println("모델명만 받는 생성자 호출");
    }

    // 3. 모델과 속도를 받는 생성자
    public Car(String model, int speed) {
        this.model = model;
        this.speed = speed;
        System.out.println("모델과 속도 모두 받는 생성자 호출");
    }
}

```

#### 메서드 오버로딩

- 다양한 매개값 처리를 위함

### 인스턴스 멤버
- 필드, 메서드는 선언 방법에 따라 **인스턴스 멤버, 정적 멤버**로 구분
- **인스턴스 멤버** 중 `필드`는 객체가 생성될 때마다 새로 **Heap 영역**에 생성, `메서드`는 클래스가 로드될 때 **Method 영역**에 할당되며, 객체가 생성되면 객체에 소속되어 공유해서 사용
- 객체 없이 사용할 수 없게 **제한**
- 정적 멤버는 **Method 영역**에 생성되어 모든 객체에 공유

- 인스턴스(instance) 멤버: 객체에 소속되어 객체를 생성해야 사용 가능
- 정적(static) 멤버: 클래스에 고정되어 객채 없이 사용 가능
```
public class Dog {
    String name;          // 인스턴스 필드
    void bark() {         // 인스턴스 메서드
        System.out.println(name + "가 짖어요!");
    }
}

```

#### this
- 객체 내부에서 인스턴스 멤버에 접근하기 위해 this 사용
- 객체는 자신을 this라고 함

### 정적 멤버
- Mehod 영역의 클래스에 고정적으로 위치하는 멤버로 **객체 생성할 필요 없이** 클래스를 통해 사용 가능

```
public class MathUtil {
    static double PI = 3.14159;  // 정적 필드
    static int square(int x) {   // 정적 메서드
        return x * x;
    }
}

// 사용
MathUtil.square(5);

```

#### 정적 멤버 선언
- `static` 키워드로 정적 멤버 선언
- 공용적 필드는 `정적 필드`로 선언하는 것이 좋음
- 인스턴스 필드를 이용하지 않는 메서드는 `정적 메서드`로 선언하는 것이 좋음

#### 정적 멤버 사용
- 클래스가 메모리로 로딩되면 정적 멤버를 바로 사용할 수 있음
- 클래스명과 도트`.` 연산자로 접근하여 사용

#### 정적 블럭
- 일반적으로 정적 필드는 필드 선언과 동시에 초기값을 주지만 정적 블럭을 이용해 초기화 가능
- 정적 블럭은 클래스가 메모리로 로딩될 때 자동 실행

#### 인스턴스 멤버 사용 불가
- 정적 메서드, 정적 블럭은 내부에 인스턴스 필드나 인스턴스 메서드 사용 불가
- 객체 자신 참조인 this 사용 불가
- main() 메서드도 정적 메서드이므로 객체 생성 없이 인스턴스 필드와 메서드를 바로 사용할 수 없음

### final 필드와 상수
- final 필드와 상수를 선언해 **값 변경을 막고 읽기만 허용** 가능
- 주로 설정값, 변경되지 말아야 하는 값에 사용

```
public class Earth {
    static final double RADIUS = 6371.0;
}

```

#### final 필드 선언
- final 필드는 초기값이 저장되면 최종값이 됨
- **실행 도중 수정 X**
- 필드에 초기값을 주는 방법은 2가지
1. 필드 선언 시 초기값 대입
2. 생성자에서 초기값 대입

#### 상수 선언
- 불변의 값
- 상수는 **static이면서 final**인 특성을 가져야 함
- 상수는 객체마다 저장할 필요 X, 여러 개의 값을 가지면 X
- 일반적으로 상수는 선언과 동시에 초기값을 주지만 정적 블럭을 통해 초기화 가능

### 패키지

### 접근제한자
- 필드와 메서드가 **외부로 노출되지 않도록**하여 객체의 무결성을 유지하기 위함
- 자바는 접근제한자 사용
- `default`는 접근제한자가 아니라 접근제한자가 붙지 않은 상태

- public: 모두 접근 가능
- protected: 같은 패키지 or 자식 객체만
- default: 같은 패키지
- private: 객체 내부

### getter/setter
- 객체의 필드를 외부에서 읽고 변경 => 객체의 무결성이 깨질 수 있음
- 외부의 직접적인 접근을 막고 **Setter 메서드**를 통해서만 필드값 변경이 가능하게
- 외부에서 객체의 필드를 읽을 때도 **Getter 메서드**를 통해서 필드값을 읽어야 함
- private 필드에 **간접 접근**

### 1. Bean?
**Bean = 스프링 컨테이너가 관리하는 객체**
- 평범한 자바 객체인데, **스프링이 직접 생성하고 주입(Inject)까지 해 주는 객체**
```
@Component
public class MemberService {
   ...
}
```
-`@Component` 붙여 놓으면 스프링이 이 객체를 Bean으로 등록해서 직접 생성하고 관리해 줌
- 그리고 다른 클래스에서 `@Autowired` or `생성자 주입`으로 가져다가 쓸 수 있음
- @Autowired/생성자 주입: 스프링 컨테이너가 만든 객체(Bean)을 다른 객체(Bean) 내부에 자동으로 주입해 주는 것

### 2. Bean을 스프링이 관리했을 때 좋은 점은?
- 개발자가 `new MemberService()` 이렇게 객체를 직접 만들 필요 X
- 스프링 컨테이너가 대신 생성해 주고 필요한 곳에 주입해 줌
- 이것을 의존성 주입(DI: Dependency Injection)이라고 함

### 3. 왜 싱글톤으로 관리하는가?
#### 매번 new 해서 객채를 만드는 방법은?
- 메모리 낭비
- 네트워크/DB 커넥션처럼 공유해야 할 자원도 새로 생성
- 각 객체마다 상태가 다르면 일관성 유지 어려움
#### 따라서, 스프링은 Bean을 기본적으로 싱글톤으로 관리
- 한 번만 만들어서 계속 재사용
- 메모리 효율도 좋고, 자원 관리도 깔끔함
#### 구조
```
[MemberService 클래스] ← 스프링이 → [MemberService 객체 1개 생성]
-> 모든 클래스가 이 1개의 Bean을 주입받아서 사용
```

**상속? 기존 클래스를 '재사용'하여 '확장'**

### 상속이 '왜' 필요할까?
- if '사람'이라는 클래스를 만들었음
- 근데, '학생', '직장인'도 사람임
- 공통 기능을 **부모 클래스**
- 다른 기능을 **자식 클래스**에서 **추가/변경**
- 다중 상속 X
```
#부모 클래스
class Person{
	String name;
    void inteoduce(){
    	System.out.println("안녕하세요," + name + "입니다.")
    }
}

#자식 클래스
class Student extends Person{
	String school;
}
```
- `Student`는 `Person`을 상속 받음
=> **필드/메서드**를 물려받는다는 의미
- `extends`

> 물려받는다는 것은 복사일까?

**자식 클래스에 복사 X, 상속 구조 안에서 "포함되어 있는 것처럼 동작"**
- 자식이 객체로 만들어질 때 부모 클래스 부분까지 하나로 이어진 설계도로 객체가 생성
- 실제로 **한 객체**, 부모+자식 기능이 모두 있는 객체
```
Student s = new Student();
s.introduce();  // Person의 메서드 실행
s.study();      // Student의 메서드 실행

```

### 부모 생성자 호출
- 자식 객체를 생성하면 부모 객체 생성 후에 자식 객체 생성
- **부모 생성자에 기본 생성자**가 있다면, 자식 생성자 맨 첫줄 컴파일 과정에서 자동으로 **super()** 추가
- **부모 클래스에 기본 생성자가 없고** 매개변수를 갖는 생성자만 있다면 개발자가 직접 **super(먀개값, ...)**를 추가해 줘야 함

### 메서드 재정의

#### 메서드 오버라이딩
- 상속된 메서드를 자식 클래스에서 재정의
- 부모 메서드의 선언부(리턴 타입, 메서드명, 매개변수)와 동일해야 함
- 접근 제한을 더 강하게 오버라이딩할 수 없음(public -> private 불가)
- `@Override` 어노테이션을 붙임녀 컴파일 단계에서 정확히 오버라이딩되었는지 체크, 문제가 있다면 컴파일 에러 출력 가능

### 부모 메서드 호출
- `super.~`로 부모 클래스 호출 가능

### final 클래스와 final 메서드
- final 클래스: 최종적인 클래스로 상속 X => 부모 클래스가 될 수 없음
- final 메서드: 최종적인 메서드로 오버라이딩 X

### protected 접근제한자
- 같은 패키지에서는 default처럼 접근 가능, 다른 패키지에서는 자식 클래스만 접근을 허용

### 타입 변환
- 클래스의 타입 변환은 **상속 관계**에 있는 클래스 사이에서 발생함

#### 자동 타입 변환
- 자식은 부모와 동일하게 취급될 수 있음
- 부모 타입으로 자동 타입 변환된 후에는 부모 클래스에 선언된 필드 메서드만 접근 가능
- 자식 클래스에서 오버라이딩된 메서드가 있다면 부모 메서드 대신 오버라이딩된 메서드가 호출됨

#### 강제 타입 변환
- 부모 타입은 자식 타입으로 자동 변환되지 않기 때문에 강제 타입 변환이 필요
- `자식 -> 부모` 타입 변환 후, **다시 `부모 -> 자식` 으로 변환할 때**만 사용 가능

### 오버라이딩 VS 오버로딩

#### 오버라이딩: 부모의 메서드를 **자식이 재정의**해서 자기 방식으로 바꾸는 것
```
class Student extends Person {
    @Override
    void introduce() {
        System.out.println("저는 학생입니다.");
    }
}
```
- 같은 이름의 메서드지만 **동작 다르게 정의**
- 부모가 만든 틀을 자식이 **커스터마이징**해서 씀
**왜 오버라이딩해서 쓰는가?**
- 부모의 기본 동작이 내 상황에 안 맞을 수 있음
- 전체 틀을 유지하고 일부만 바꾸기 위해

#### 오버로딩: 메서드 이름은 동일, **매개변수 다르게 해서** 여러개 정의
```
void introduce() { ... }
void introduce(String name) { ... }
void introduce(int age, String job) { ... }

```
- 이름은 같고, 파라미터 타입, 개수, 순서 다른 것 모두 허용
- 다형성 X

### 다형성(Polymorphism)
- 하나의 타입(부모)으로 다양한 형태(자식)을 가리킬 수 있음
```
Person p1 = new Student();
Person p2 = new Teacher();

p1.introduce();
p2.introduce();
```
> 부모 클래스 타입으로 선언하고, 객체 자체는 자식 클래스로 만든다는 개념 자체가 와닿지 않음

#### 왜 이렇게 쓰는가?
- Person[] people = {new Student(), new Teacher()};
- 이렇게 하면 **하나의 배열, 하나의 리스트**로 다양한 타입 묶어서 처리 가능
- student 타입, teacher 타입으로 객체를 생성했다면, 타입이 다르기 때문에 person이란 공통 성질이 있어도 활용할 수 없음
- 코드의 유연성, 확장성, 재사용성 증가

#### 다형성 흐름도
```
class Person
  └── class Student extends Person
  └── class Teacher extends Person

Person[] people = { new Student(), new Teacher() };

for (Person p : people) {
    p.introduce(); // 각각 Student, Teacher의 introduce() 실행됨
}

```

## CH08 인터페이스
> - 상속 VS 인터페이스
> - 인터페이스 VS 추상 클래스

> 📘 개구리책 4장 - 객체 지향 설계 원칙 참고

### 1. 클래스 -> 상속 -> 다형성
```
class Animal {
    void sound() {
        System.out.println("동물이 소리를 냅니다.");
    }
}

class Dog extends Animal {
    void sound() {
        System.out.println("멍멍!");
    }
}
```
- Dog이 Animal을 상속 받음
- sound() 오버라이딩
- 다형성을 통해 Animal a = new Dog() 가능

### 2. 그런데, 모든 클래스를 상속할 수 없을까?
- 문제: 어떤 클래스는 **공통 동작만 정의하고, 구체적으로는 직접 구현하고 싶지 않음**
- ex) 동물마다 울음소리는 다른데, 공통적으로 '울다'라는 메서드는 있어야 함

### 3. 추상 클래스(abstract class)?
- 구현하지 않은 **추상 메서드를 가질 수 있는 클래스**
- 상속 받은 자식 클래스가 **구체적으로 구현**
```
abstract class Animal {
    abstract void sound();  // 추상 메서드
    void breathe() {
        System.out.println("숨을 쉰다");
    }
}

class Cat extends Animal {
    @Override
    void sound() {
        System.out.println("야옹");
    }
}
```
- 부모 클래스에서 sound()를 틀만 만들고 구현 X
- 자식 클래스에서 **구현(Override)**

### 4. 인터페이스(Interface)?
- 아예 **구현 자체가 X, 순수한 추상 메서드의 집합**
- 자바에서 클래스 상속은 1개만 가능하지만,
- **인터페이스는 다중 구현 가능**
```
interface Flyable {
    void fly();
}

interface Swimmable {
    void swim();
}

class Duck implements Flyable, Swimmable {
    public void fly() {
        System.out.println("날아요");
    }

    public void swim() {
        System.out.println("헤엄쳐요");
    }
}
```
- `interface`는 `implements` 키워드로 사용
- 모든 메서드는 자동으로 public abstract
- 다중 구현 가능 -> 유연한 설계 가능

#### 인터페이스 사용 구조

**1. 인터페이스 정의(틀 만들기)**
```
public interface Flyable {
    void fly();  // 날 수 있는 애들은 반드시 이 메서드를 구현해야 함
}
```
- "날 수 있으면 fly()를 구현해!"라는 약속
- `interface`는 **메서드의 이름과 구조(틀)만 정의**하고 실제 구현 X

**2. 클래스에서 구현(implements로 기능 구현)**
```
public class Duck implements Flyable {
    @Override
    public void fly() {
        System.out.println("오리가 날개로 납니다!");
    }
}

public class Airplane implements Flyable {
    @Override
    public void fly() {
        System.out.println("비행기가 엔진으로 납니다!");
    }
}
```
- `Duck`, `Airplane`은 `Flyable`이라는 약속을 **구현**하는 클래스
- 따라서, 구현하는 클래스 내부에 **반드시 fly() 메서드를 정의**해야만 함 (안 하면 컴파일 에러)

**3. 다형성으로 활용**
```
public class FlightTest {
    public static void main(String[] args) {
        Flyable f1 = new Duck();
        Flyable f2 = new Airplane();

        f1.fly(); // 오리가 날개로 납니다!
        f2.fly(); // 비행기가 엔진으로 납니다!
    }
}
```
- `Flyable` 타입으로 두 객체를 **같은 리스트에 담을 수도 있고, 동일한 방식으로 호출 가능**
- 실제 어떤 객체냐에 따라 동작은 아예 다르게 나옴 -> 다형성

> 나의 의문
-> 인터페이스에선 메서드를 구현하도록 강제함
-> 그렇다면 각 구현 클래스에서 fly()메서드를 강제적으로 구현하는 것(따지면 오버라이딩)인데, 차라리 flayable()이라는 부모 클래스를 만들어서 Duck과 Airplane이 상속 받게 하고 다른 동작을 오버라이딩하는 것과 어떻게 다른 것일까?

#### 상속+오버라이딩 VS 인터페이스

- **상속 + 오버라이딩**: 기본 구현을 기반으로, **일부만 바꾸고 싶을 때**
- 계층적 구조를 만든다
- ex) Person의 introduce()를 70%은 공통으로 두고, 일부 내용만 학생/선생님이 바꾸고 싶을 때
- **인터페이스**: **구현 자체가 다름**
- ex) introduce()라는 이름은 같지만 **아예 성격이 다르게 동작**해야 할 때
- 계층보단 역할 분리

> 상속: "사람"처럼 **공통된 속성과 동작 공유** 구조
> ex) name, age, introduce() 같은 공통된 필드와 메서드를 가짐
> 인터페이스: "날 수 있다"처럼 **공통된 역할이나 기능만 명세(정의)하는 구조**
> ex) fly()라는 기능은 같지만
> **오리는 날개로 날고, 비행기는 엔진으로 난다**
> **결과는 같고, 과정은 다르다**

### 추상 클래스 VS 인터페이스

> 추상 클래스, 인터페이스 둘 다 **틀만 정의**하고, 실제 동작은 구현 클래스에서 완성함
> 그렇다면 **왜 둘을 구분해야 하는가?**

** 두 개념은 설계 철학과 사용 목적이 다름!**

- 'Animal -> Cat', 'Flyable -> Duck/Airplane' 구조처럼
- 1. **공통된 속성과 동작을 물려주기 위한 상속(추상 클래스)**가 적절한 경우
- 2. **공통된 역할만 강제하는 유연한 설계(인터페이스)가 적절한 경우
- 두 경우가 갈리기 때문이다

#### 비교표
| 비교 항목 | 추상 클래스 (abstract class) | 인터페이스 (interface) |
|-----------|------------------------------|-------------------------|
| 설계 목적 | 상속을 통한 코드 재사용       | 역할(기능)의 명세 제공   |
| 상속 구조 | 단일 상속만 가능              | 다중 구현 가능           |
| 구성 요소 | 필드 + 생성자 + 일반 메서드 + 추상 메서드 | 상수 + 추상 메서드 (Java 8 이후 default/static 허용) |
| 사용 예시 | Animal → Cat/Dog             | Flyable → Duck/Airplane |
| 확장성   | 기본 구현이 있으므로 편리한 확장 가능 | 구현 강제만 하므로 유연한 설계에 적합 |
| 용도 요약 | “이건 **A이다**” → IS-A 관계(계층적 관계) | “이건 **A 할 수 있다**” → CAN-DO 관계(역할 중심 관계) |

## CH09 중첩 선언과 익명 객체

> 📘 개구리책 5장 - 의존성 주입(DI) 참고

- 클래스가 여러 클래스와 관계를 맺는 경우 -> 독립적으로 선언하는 것이 유리
- 클래스가 특정 클래스만 관계를 맺는 경우 -> 중첩 클래스로 선언하는 것이 유지보수에 유리

## 중첩 클래스?
- ** 클래스 내부에 클래스를 선언하는 것 **
- **외부 클래스의 멤버처럼 정의되는 클래스**
- 주로 외부 클래스와 밀접한 관계가 있는 클래스일 경우 이렇게 선언함
```
class Outer {
    class Inner {
        void print() {
            System.out.println("Inner 클래스입니다.");
        }
    }
}
```
- Outer.Inner inner = new Outer().new Inner(); <- 이런 식으로 사용

### 왜 중첩 클래스를 쓰는가?
- 외부 클래스와 논리적으로 밀접한 관계일 때
- 외부 클래스 없이 독립적으로 사용할 일이 없을 때
- **캡슐화**: 외부 클래스와 내부 클래스가 논리적으로 밀접한 관계일 때 => 내부 구현을 외부에 노출하지 않기 위해 중첩 클래스로 감싸는 것
- 내부 클래스를 `private`으로 선언하여 외부 접근을 막고,
- 외부 클래스에서만 생성/제어하는 방식으로 **정보 은닉** 실현

### 중첩 클래스의 4 가지 유형
| 유형                     | 설명                    | 예시                                                   |
| ---------------------- | --------------------- | ---------------------------------------------------- |
| **인스턴스 멤버 클래스**        | 외부 클래스의 인스턴스 필요       | `Outer outer = new Outer(); outer.new Inner();`      |
| **정적 멤버 클래스 (static)** | 외부 클래스의 인스턴스 없이 사용 가능 | `Outer.StaticInner inner = new Outer.StaticInner();` |
| **로컬 클래스**             | 메서드 내에서 정의            | 메서드 블록 안에서만 사용                                       |
| **익명 클래스**             | 이름 없는 일회성 클래스         | 인터페이스나 추상 클래스 즉시 구현                                  |

### 인스턴스 멤버 클래스
- 외부 클래스의 인스턴스가 있어야 생성 가능
```
class Outer {
    class Inner {
        void method() {}
    }
}
Outer.Inner inner = new Outer().new Inner();
#Outer() 인스턴스가 생성된 후 Ineer() 동작

```
### 정적 멤버 클래스(static)
- 외부 클래스의 인스턴스 없이 사용 가능
- static이라 독립적
```
class Outer {
    static class StaticInner {
        void method() {}
    }
}
Outer.StaticInner inner = new Outer.StaticInner(); 
#Outer() 인스턴스 생성과 무관하게 StaticInner() 동작
```

### 로컬 클래스
- 메서드 안에서 선언한 클래스
- 외부에서 접근 불가
```
void method() {
    class LocalInner {
        void run() {}
    }
    new LocalInner().run();
}

```
### 바깥 멤버 접근
- 내부 클래스가 외부 클래스의 멤버(필드, 메서드)에 접근할 수 있는 구조
- 접근 방식: 내부 클래스 내부에서 외부 클래스의 이름 없이도 필드, 메서드 사용 가능
- 이름 충돌 or 명시적 구분 필요 => `OuterClassName.this.멤버` 형태로도 사용
```
public class Outer {
    String name = "Outer name";

    class Inner {
        String name = "Inner name";

        void printName() {
            System.out.println(name);                // Inner 클래스의 name
            System.out.println(Outer.this.name);     // Outer 클래스의 name
        }
    }
}
```
- `name` 필드가 내부 클래스, 외부 클래스에 모두 존재
- 이럴 때 `Outer.this.name`을 사용해서 **외부 클래스의 필드를 명시적으로 호출**
- 내부 클래스에서는 외부 클래스의 private 필드/메서드도 접근 가능
=> 내부 클래스도 **외부 클래스의 멤버처럼 취급**하기 때문

#### 외부 클래스의 멤버 접근 제한
- 인스턴스 멤버 클래스: 외부 클래스의 모든 필드와 메서드
- 정적 멤버 클래스: 외부 클래스의 필드와 정적 메서드

### 중첩 인터페이스
- 클래스 안에 인터페이스 선언(클래스 안에 클래스를 선언하는 것처럼)
```
class Button {
    interface OnClickListener {
        void onClick();
    }
}
```
- 스프링에서도 이런 구조 자주 씀(`인터페이스를 정의하고, 외부에서 구현하여 주입`)
- 스프링 DI가 중첩 인터페이스 구조라는 것이 아니라, 중첩 인터페이스 구조와 스프링 DI 구조가 개념적으로 유사하다는 의미 

>스프링에서 얘기하는 게 잘 와닿지 않음

### 중첩 인터페이스 구조 VS 스프링 의존성 주입(DI) 구조
#### 중첩 인터페이스 구조
```
class Button {
    interface ClickListener {
        void onClick();
    }

    private ClickListener listener;

    public void setListener(ClickListener listener) {
        this.listener = listener;
    }

    public void click() {
        listener.onClick();
    }
}
```
- `ClickListener`는 기능/역할만 정의(interface)
- 실제 로직 구현은 **외부**에서 -> `setListener()`로 주입
- 버튼은 `onClick()`을 어떻게 구현했는지 모름 => 그냥 `listener.onClick()` 호출

👉 **기능을 미리 약속하고(역할 정의), 외부에서 주입받아 동작**
-> 이것을 **느슨한 결합**, 인터페이스 기반 설계

#### 스프링 DI 구조
```
interface AlarmSender {
    void send(String msg);
}

@Service
class EmailSender implements AlarmSender {
    public void send(String msg) {
        System.out.println("이메일 발송: " + msg);
    }
}

@Component
class Notifier {
    private final AlarmSender sender;

    @Autowired
    public Notifier(AlarmSender sender) {
        this.sender = sender;
    }

    public void notify(String msg) {
        sender.send(msg);
    }
}
```
- `AlarmSender`도 역할만 정의(interface)
- `EmailSender`에서  실제 구현
- `Notifier`는 `AlarmSender`가 어떻게 동작하는지 모름 => 그냥 `sender.send` 호출

👉 마찬가지로, **기능을 인터페이스로 약속하고 외부에서 구현체를 주입받아 동작**

#### 정리
| 구분          | 중첩 인터페이스 구조                      | 스프링 DI 구조                      |
| ----------- | -------------------------------- | ------------------------------ |
| 인터페이스 정의 위치 | 클래스 내부 (`Button.ClickListener`)  | 별도 정의 (`AlarmSender`)          |
| 주입 방식       | 수동 주입 (`setListener(new 구현체())`) | 자동 주입 (`@Autowired`, IoC 컨테이너) |
| 공통 설계 철학    | 인터페이스 기반 느슨한 결합                  | 인터페이스 기반 느슨한 결합                |
| 역할 분리       | "버튼"과 "리스너 역할" 분리                | "사용자"와 "알람 전송 역할" 분리           |


### 익명 객체(익명 클래스)
- 익명(anonymous) -> 이름이 없는 객체
- 파이썬 `lambda` 함수랑 의도와 사용 목적이 비슷함

**의도/사용 목적**
- 이름 없는 일회용 코드 블럭
- 딱 한 번 쓰고 버릴 목적
- 짧고 간결하게 정리

> 그냥 메서드를 만들어서 재사용하는 게 좋을 것 같은데, 왜 굳이 일회용인 익명 클래스를 쓰는 거지?

#### 익명 클래스를 쓰는 상황
| 상황 | 설명                                     | 예시                       |
| -- | -------------------------------------- | ------------------------ |
| 1  | **이벤트 핸들러, 콜백 함수처럼** 딱 한 번 쓰는 인터페이스 구현 | 버튼 클릭 시 동작 정의            |
| 2  | **오직 한 메서드만 잠깐 구현해서 넘겨줄 때**            | `Runnable`, `Comparator` |
| 3  | **상속보다는 역할만 잠깐 필요할 때**                 | 외부 API에 일시적 객체 넘기기       |

**이벤트 기반 코드 예시**
```
button.setOnClickListener(new OnClickListener() {
    @Override
    public void onClick() {
        System.out.println("버튼이 눌렸어요!");
    }
});
```
- 이 코드는 버튼이 눌렸을 때만 실행되고 다시 쓰이지 않기 때문에 익명 클래스로 작성
- 사용 목적 명확

#### 익명 클래스 문법 구조
```
인터페이스 또는 추상클래스 변수 = new 인터페이스이름() {
    // 메서드 구현
};
```
-`인터페이스이름()`은 **클래스 이름 X, 타입(자료형)**으로 쓴 것
- {} **안에 실제 클래스가 정의되고 한 번만 생성됨**

## CH10 라이브러리와 모듈
>클래스부터 중첩 클래스까지는 흐름이 자연스러웠는데, 왜 라이브러리와 모듈은 중첩 클래스와 예외 처리 사이에 챕터로 들어온 걸까?

👉 CH 09: 클래스 내부 구조 설계(캡슐화, 중첩 클래스, 익명 객체 등)
👉 CH 10: 외부 구조 설계(라이브러리 -> 모듈화)
=> 이 클래스들을 어떻게 **외부에 노출하고, 어떻게 묶어서 배포할까?** <- 이게 **라이브러리/모듈**의 역할

### 라이브러리(Library)
- 프로그램을 개발할 때, 활용할 수 있는 클래스와 인터페이스를 모아 놓은 코드 묶음
- 일반적으로 JAR(JavaARchive) 압출 파일(.jar) 형태로 존재
- JAR 파일에는 클래스/인터페이스의 바이트코드 파일(.class)들이 압축되어 있음
- 다른 프로젝트에서 재사용 가능
- 자바는 `java.util`,`java.io` 같은 기본 라이브러리를 제공함 
👉 특정 클래스, 인터페이스가 여러 응용 프로그램을 개발할 때 공통으로 자주 사용된다면 JAR 파일로 압축해서 라이브러리로 관리하는 것이 좋다

> 라이브러리가 작업을 편하게 해 주는 게 목적이라면, 프레임워크랑 목적이 겹치는 거 아닌가?

#### 라이브러리 VS 프레임워크

| 항목             | **라이브러리 (Library)**                          | **프레임워크 (Framework)**                             |
| -------------- | -------------------------------------------- | ------------------------------------------------- |
| **주도권(제어 흐름)** | **개발자가 주도**<br>필요할 때 개발자가 직접 호출              | **프레임워크가 주도**<br>프레임워크가 개발자의 코드를 호출 (제어의 역전, IoC) |
| **구조**         | 단순 기능 모음                                     | 애플리케이션의 골격(구조)을 제공                                |
| **목적**         | 기능 단위 재사용                                    | 전체 애플리케이션 구성 주도                                   |
| **사용 예**       | `java.util.List`, `Apache Commons`, `Lombok` | `Spring Framework`, `Django`, `Angular`           |
| **설명 방식**      | "개발자가 필요할 때 꺼내 씀"                            | "프레임워크가 정해준 틀에 따라 개발"                             |
👉 라이브러리: 공구상자 <- 필요할 때 내가 호출
👉 프레임워크: 집의 구조 <- 틀을 프레임워크가 만들어 주고, 내가 여기에 맞춰서 구현

### 모듈(Module)
- Java 9부터 지원
- 패키지 관리 기능이 포함된 라이브러리
- 일반 라이브러리는 내부에 포함된 모든 패키지에 외부 프로그램에서 접근 가능
- 모듈은 일부 패키지를 은닉하게 접근할 수 없게 할 수 있음 **(공개할 것과 숨길 것을 구분할 수 있음)**
- 자신이 실행할 때 필요로 하는 의존 모듈을 모듈 기술자(module-info.java)에 기술할 수 있어 모듈 간의 의존 관계 쉽게 파악 가능
- 라이브러리의 일종이므로 JAR 파일 형태로 배포 가능
- 응용 프로그램을 개발할 때 원하는 기능의 모듈(JAR) 파일을 다운로드해서 이용
- 대규모 응용 프로그램은 기능별로 모듈화(modulization)해서 개발 가능

### 응용 프로그램의 모듈화
- 하나의 프로그램을 여러 모듈로 쪼개고 의존성 구조를 설계
- `exports` 키워드 사용
- 모듈이 가지고 있는 패키지를 외부에서 사용할 수 있도록 노출시키는 역할
- `requires` 키워드: 모듈을 컴파일하거나 실행할 때 필요한 의존 모듈 지정
- ex) `com.app.core`(핵심 로직), `com.app.web`(웹 UI 모듈), `com,app.db`(DB 처리 모듈)

### 모듈 배포용 JAR 파일
- 모듈 개발을 완료했다면 배포용 JAR 파일(.jar) 생성 가능
- 자바 9 이상에선 모듈 JAR -> `module-info.class` 포함

### 패키지 은닉
- `exports` 키워드로 외부 공개할 때만 패키지 지정
- `exports`되지 않은 패키지는 자동적으로 은닉
```
exports com.app.service;    // 이 패키지만 공개
// 나머지는 외부에서 접근 못 함
```
- 실무에서 중요: 외부에서 내부 구현 세부사항 노출 방지(정보 은닉)

> **중첩 클래스의 캡슐화**랑 **모듈 시스템의 패키지 은닉**은 비슷한 기능을 하는 것 같은데 어떻게 다를까? 

| 개념                            | 캡슐화 대상          | 은닉 수준               | 사용 목적                             |
| ----------------------------- | --------------- | ------------------- | --------------------------------- |
| **중첩 클래스**                    | 클래스 내부의 **클래스** | **클래스 내부(private)** | 외부에서 내부 구현을 감춤 (설계 단위 내 은닉)       |
| **모듈 시스템 (module-info.java)** | **패키지 전체**      | **모듈 외부(public)**   | 외부 모듈에서 접근 못 하게 막음 (애플리케이션 단위 은닉) |

#### 중첩 클래스로 은닉
```
public class Button {
    private class EventHandler {
        void handle() { ... }
    }
}
```
-`EventHandler`는 `Button` 외부에서 **보이지 않음**
- **같은 파일 안에서만** 사용하는 보조 클래스일 때 유용
👉 클래스 내부에서만 쓰이는 유틸 클래스 or 도우미 객체를 외부에 노출하지 않기 위해 사용
👉 **캡슐화 = 클래스 단위 설계 관점**

#### 모듈 시스템에서의 은닉
```
module my.module {
    exports com.my.publicapi; // 공개할 패키지
    // com.my.internal 은 외부 모듈에서 접근 불가
}
```
- `com.my.import` 패키지는 **다른 모듈에서 import** 불가
- 모듈이 직접 `exports`로 공개하지 않는 한 **은닉됨**
👉 의도적으로 내부 구현 패키지를 외부에서 못 보게 하여 라이브러리 사용자들이 의존하지 않도록 하는 설계
👉 **은닉 = 프로젝트/모듈 단위 배포 관점**

#### 그래서 모듈 시스템은?
| 목적         | 방법                                     | 설명                     |
| ---------- | -------------------------------------- | ---------------------- |
| 패키지 노출 제한  | `exports` 생략                           | 외부에서 접근 불가, 은닉됨        |
| 내부 구조 정리   | `com.my.internal`, `impl`, `support` 등 | 내부용임을 명시하는 패키지 이름으로 관리 |
| 안정적 API 제공 | `exports com.my.api;`                  | 외부에 보여줄 범위만 정확히 지정     |

### 전이 의존(requires transitive)
- 어떤 모듈 A가 모듈 B를 `requires`
- 모듈 B가 모듈 C를 다시 `requires`했을 때
- **A에서 C의 내용을 직접 사용할 수 있도록 허용하는 것**

#### 기본 의존 관계
```
A 모듈
 └── requires B;
       └── requires C;

A는 B의 API는 사용 가능하지만
C의 API는 직접 사용할 수 없음!
```
- A에서 C를 사용하려면 **직접 C requires 해야 함**

#### 전이 의존 관계
```
A 모듈
 └── requires B;
B 모듈
 └── requires transitive C;

A는 C의 API도 사용 가능!
```
- B가 C에 대해 `requires transitive`를 선언하면
- B를 의존하는 **A도 C를 자동으로 사용 가능**

#### 요약
```
[전이 의존이 없는 경우]
A ──▶ B ──▶ C  
(A는 C를 사용할 수 없음)

[전이 의존이 있는 경우]
A ──▶ B ──transitive──▶ C  
(A도 C를 사용할 수 있음)
```

### 집합 모듈(Aggregated Modules)
- 여러 모듈을 묶어서 하나로 묶은 것
- ex) `java.se`모듈 = `java.base`,`java.sql`,`java.xml`...

### 리플렉션 허용
- 은닉된 패키지는 기본적으로 다른 모듈에 의해 리플렉션 허용 X
- 리플렉션(reflection): 실행 도중에 타입(클래스, 인터페이스 등)을 검사하고 구성 멤버를 조사하는 것
- 경우에 따라 은닉된 패키지도 리플렉션을 허용해야 할 때가 있음
- 모듈은 모듈 기술자를 통해 모듈 전체 or 지정된 패키지에 리플렉션 허용 가능
- 특정 외부 모듈에서만 리플렉션 허용 가능
- `open` 키워드로, 리플렉션 API(ex) 스프링의 의존성 주입)가 특정 패키지를 열람할 수 있게 허용
```
#모듈 전체 리플렉션 허용
open module 모듈명{
    
}

#지정된 패키지에 대해 리플렉션 허용
module 모듈명{
    opens 패키지1;
    opens 패키지2;
}

#지정된 패키지에 대해 특정 외부 모듈에서만 리플렉션 허용
module 모듈명{
    opens 패키지1 to 외부모듈명, 외부모듈명, ...;
    opens 패지키2 to 외부모듈명;
}
```
### 자바 표준 모듈
- 다바는 이제 JDK 자체도 모듈로 나뉨
- ex) `java.base`,`java.sql`,`java.xml`,`jdk.httpserver`...

## CH11 예외처리

### 예외(Exception)
- **프로그램 실행 중에 발생하는 오류**
- 단순 버그가 아닌 **예상 가능한 문제 상황들**
- ex) 파일 없음, 배열 인덱스 초과, 0으로 나누기, null 접근 등

#### 오류(Error) VS 예외(Exception)
| 구분            | 설명             | 예시                  |
| ------------- | -------------- | ------------------- |
| **Error**     | 복구 불가능한 심각한 오류<br/>(컴퓨터 하드웨어 고장으로 응용 프로그램 실행  오류 발생) | 메모리 부족, JVM 내부 오류 등 |
| **Exception** | 복구 가능한 문제 상황<br/>(잘못된 사용 or 코딩으로 인한 오류)   | 파일 없음, 잘못된 입력 등     |
- Error는 catch로 복구 불가능, Exception은 catch로 복구 가능

#### 예외의 두 가지 종류
- 일반 예외(Exception): 컴파일러가 예외 처리 코드 여부를 검사하는 예외 -> 실행 예외를 제외한 모든 예외
- 실행 예외(Rutiome Exception): 컴파일러가 예외 처리 코드를 검사하지 않는 예외

- 자바는 예외가 발생하면 예외 클래스로부터 예외 처리 시 사용될 객체를 생성

#### 예외 클래스 계층 구조
```
Object
  └─ Throwable
       ├─ Error        (치명적 오류: JVM 내부 문제)
       └─ Exception    (예외 상황: 코드로 처리 가능)
             ├─ CheckedException (강제 처리 필요)
             └─ UncheckedException (런타임 예외, 선택적 처리)
```

### 예외 처리 코드 구성
- 기본 구조: `try-catch-finally`
```
try {
    // 예외 발생 가능 코드
} catch (예외타입 변수명) {
    // 예외 처리 코드
} finally {
    // 무조건 실행 (생략 가능)
}
```
-`finally`는 **예외 발생 여부와 무관하게 실행**

### 예외 종류에 따른 처리
#### 다중 catch
```
try {
    // 코드
} catch (ArrayIndexOutOfBoundsException e) {
    // 예외1 처리
} catch (NumberFormatException e) {
    // 예외2 처리
}
```
- 예외가 발생하면 **해당하는 catch 하나만 실행**
#### catch 블럭 순서 주의
- 예외 클래스들이 **상속 관계**일 경우, **상위 타입은 아래에 위치해야 함**
>무슨 말인지 모르겠음

**예외 클래스 구조(상속 계층)**
```
Object
 └── Throwable
      ├── Error
      └── Exception
           ├── IOException
           └── RuntimeException
                └── NullPointerException
```
**잘못된 순서**
```
try {
    // 예외 발생
} catch (Exception e) {
    // 상위 타입 먼저 -> 여기서 다 잡힘
} catch (NullPointerException e) {
    // 이 코드는 도달 불가! (Unreachable code 오류)
}
```
**옳은 순서**
```
try {
    // 예외 발생
} catch (NullPointerException e) {
    // 구체적인 예외 먼저
} catch (Exception e) {
    // 그 외 일반적인 예외
}
```

#### 여러 예외를 하나의 블럭으로 처리
```
catch (NullPointerException | NumberFormatException e) {
    // 예외 공통 처리
}

```

### 리소스 자동 닫기
- 리소스: 데이터를 제공하는 객체
- 리소스는 사용하기 위해 `open`, 사용한 후에는 `close`해 주어야 함
- 리소스를 사용하다가 예외가 발생할 때도 반드시 닫아 주어야 함
- 이런 경우 리소스를 닫기 우해 예외 발생 여부과 상관없이 자동으로 리소스를 닫아 줌

#### try-catch-finally 블럭
- 리소스를 자동으로 닫는 기본적인 방법은 이 블럭에서 `finally` 부분에 리소스 닫는 코드를 작성하는 것
```
try{
    fis = new FileInputStream("file.txt"); //파일열기
} catch(IOException e){
    ...
} finally{
    fis.close(); //파일닫기
}

```
#### try-with-resources 블럭 (java 7+)
- 위와 다르게 `finally`문에 작성할 필요 X
- try 괄호에 리소스 여는 코드를 작성하면 try 블럭이 정상적으로 실행을 완료했거나 or 예외가 발생하면 자동으로 리소스의 close() 메소스가 호출됨
- 하지만 `try-with-resources 블럭`을 사용하려면,
- `java.lang.AutoCloseable` 인터페이스를 구현하고
- 해당 인터페이스의 `close()` 메서드 오버라이딩 필요
```
public class MyResource implements AutoCloseable{
	//...
	@Override
	public void close() throws Exception {
		//리소스를 닫는 코드 작성
	}
}

public class Main {
	public static void main(String[] args) {
		try {
			MyResource fis1 = new MyResource("file1.txt");
			MyResource fis2 = new MyResource("file2.txt");
		}catch(IOException e) {
			//예외 처리 코드 작성
		}
        //finally문을 작성하지 않아도 자동으로 리소스가 닫힌다.
	}
}
```

### 예외 떠넘기기(throws)
- 대부분 메서드 내에서 예외가 발생하면 `try-catch` 블럭으로 예외 처리
- 하지만 어떤 경우에는 `throws` 키워드를 통해 메서드를 호출한 곳으로 예외를 떠넘길 수 있음
```
void method() throws IOException {
    // 예외 발생 가능
}
```
- 메서드 내에서 예외를 처리하지 않고 **호출한 곳으로 떠넘김**
- 예외를 받은 쪽에서 처리(`try-catch`)하거나 계속 떠넘김(`throws`)
- `throws Exception`, `throws Throwable`로 **모든 예외 포괄 가능

> 근데 이러면 결국 누군가는 떠넘기는 게 아니라 처리해야 하는데 굳이 왜 떠넘기는 거임?

| 질문                    | 답변                                                  |
| --------------------- | --------------------------------------------------- |
| 왜 예외를 떠넘기나?           | 로직과 예외 처리를 **역할 분리**하기 위해                           |
| 계속 떠넘기면 누가 처리하나?      | 결국 `main()`이나 호출한 쪽에서 처리 / **안 하면 JVM이 에러 출력 후 종료** |
| 그냥 메서드 내에서 처리하면 안 되나? | 물론 가능! 근데 **예외 대응을 유연하게 하려면 떠넘기는 게 더 유리할 때도 많음**    |



### 사용자 정의 예외

- 자바에 기본적으로 저장된 예외 이외에 예외를 발생시킬 상황이 존재
- ex) 은행 뱅킹 프로그램에서 잔고보다 더 많은 출금 요청이 들어왔을 때 -> 잔고 부족 예외 발생시켜야 함
- but, 자바의 표준 라이브러리에는 이 예외가 존재하지 않음
- 따라서, 사용자가 직접 예외 클래스를 정의하는데 이것을 **사용자 정의 예외 클래스**라고 함

#### 예외 발생시키기
- `throw` 키워드와 함께 예외 객체를 제공
- `throw`된 예외는 직접 `try-catch`블럭으로 예외 처리 가능
- 대부분은 메서드를 호출한 곳에서 예외를 처리하도록 `throws` 키워드로 예외를 떠넘김

#### throw VS throws

| 구분      | `throw`                    | `throws`                        |
| ------- | -------------------------- | -------------------------------- |
| 역할      | **예외를 "발생"시킴**             | **예외를 "떠넘기겠다고 선언"함** |            
| 위치      | 메서드 **내부**                 | 메서드 **선언부(헤더)** |                 
| 뒤에 오는 것 | 예외 객체 (new로 생성)            | 예외 클래스 이름 (예외 타입)|                
| 예시      | `throw new IOException();` | `void read() throws IOException` |

**throw가 직접 예외를 만드는 건 이해되는데, 왜 예외를 만들 일이 생길까?**

    // 실패하면 상위 메서드가 책임지도록 위임

#4. 일관된 에러 처리 로직을 만들 수 있음

#### StringTokenizer 클래스: 구분자로 연결된 문자열을 분리할 때 사용
- 문자열이 구분자로 연결되어 있을 때, 구분자를 기준으로 문자열을 분리하려면
- `String`의 `split()` 메서드를 이용하거나 `StringTokenizer` 클래스 활용

| 리턴 타입     | 메서드               | 설명                     |
| --------- | ----------------- | ---------------------- |
| `int`     | `countTokens()`   | 분리할 수 있는 토큰(문자열)의 총 개수 |
| `boolean` | `hasMoreTokens()` | 남아 있는 토큰이 있는지 확인       |
| `String`  | `nextToken()`     | 다음 토큰을 하나씩 반환          |

#### split() VS StringTokenizer
| 항목        | `split()`                        | `StringTokenizer`                   |
| --------- | -------------------------------- | ----------------------------------- |
| 반환값       | `String[]` (배열)                  | `StringTokenizer` 객체                |
| 사용법       | `"문자열".split("구분자")`             | `new StringTokenizer("문자열", "구분자")` |
| 정규표현식 지원  | ✅ 가능                             | ❌ 불가능                               |
| 사용 편의성    | 직관적이고 현대적인 방식                    | Java 1.0부터 존재, 구식 방식으로 간주됨          |
| 공백 문자열 처리 | 빈 문자열도 배열에 포함됨                   | 빈 문자열은 토큰으로 처리 안 됨                  |
| 성능        | 큰 차이 없음 (하지만 `split`이 일반적으로 추천됨) |                                     |

- 패키지와 타입 이름 정보는 아래 메서드로 얻을 수 있음

| 메소드                      | 용도                        |
| ------------------------ | ------------------------- |
| `Package getPackage()`   | 클래스의 패키지 정보 읽기            |
| `String getSimpleName()` | 패키지를 제외한 타입(클래스/인터페이스) 이름 |
| `String getName()`       | 패키지를 포함한 전체 타입 이름         |

#### 멤버 정보 얻기

| 메소드                                       | 용도             |
| ----------------------------------------- | -------------- |
| `Constructor[] getDeclaredConstructors()` | 클래스의 생성자 정보 읽기 |
| `Field[] getDeclaredFields()`             | 클래스의 필드 정보 읽기  |
| `Method[] getDeclaredMethods()`           | 클래스의 메소드 정보 읽기 |


### 어노테이션: 코드에서 @로 작성되는 요소
- 클래스 or 인터페이스를 컴파일하거나 실행할 때 어떻게 처리해야 할 것인지 알려주는 설정 정보

#### 어노테이션 용도
- 컴파일 시 사용하는 정보 전달
- 빌드 툴이 코드를 자동으로 생성할 때 사용하는 정보 전달
- 실행 시 특정 기능을 처리할 때 사용하는 정보 전달

#### 어노테이션 타입의 정의와 적용
- 어노테이션도 하나의 타입이므로 어노테이션을 사용하기 위해선 먼저 정의해야 함
- 정의 방식은 인터페이스 정의 방식과 유사

#### 어노테이션 적용 대상
- 어떤 대상에 어노테이션을 적용할 것인지 명시해야 함
- 적용 대상을 지정할 땐 `@Target` 어노테이션 사용

#### 어노테이션 유지 정책
- 어노테이션을 정의할 떄 `@AnnotationName`을 언제까지 유지할 것인지 지정해 줘야 함
- 유지 정책 지정할 때 `@Retention` 어노테이션 사용

> 어노테이션을 스프링에서 되게 잘 사용하지 않나?

## 스프링을 위한 어노테이션 정리

### 자바 어노테이션 기본 문법
#### 어노테이션
- 메타 데이터: 코드에 대한 부가 정보 제공
- 실행 로직 X, **개발자/컴파일러/프레임워크가 처리*

#### 선언 방법
```
public @interface MyAnnotation {
    String value(); // 속성
    int number() default 0; // 기본값
}
```
#### 사용 예시
```
@MyAnnotation(value = "test", number = 10)
public class TestClass {}
```
### 스프링에서 자주 사용하는 어노테이션

#### 컴포넌트 계열: `@Component`의 확장 개념으로 역할에 따라 구분

| 어노테이션             | 역할   | 설명                                    |
| ----------------- | ---- | ------------------------------------- |
| `@Component`      | 빈 등록 | 일반적인 컴포넌트 클래스 등록 시 사용                 |
| `@Service`        | 빈 등록 | 비즈니스 로직 클래스 등록 시 사용 (의미 부여용)          |
| `@Repository`     | 빈 등록 | DAO 클래스 등록 시 사용, 예외 변환 지원             |
| `@Controller`     | 빈 등록 | MVC 패턴에서 컨트롤러 등록 시 사용                 |
| `@RestController` | 빈 등록 | REST API 컨트롤러 등록 (`@ResponseBody` 포함) |

#### 의존성 주입(DI)

| 어노테이션                | 역할    | 설명                           |
| -------------------- | ----- | ---------------------------- |
| `@Autowired`         | 주입    | 스프링이 자동으로 의존성 주입 (생성자/필드/세터) |
| `@Qualifier("name")` | 선택 주입 | 같은 타입이 여러 개 있을 때 어떤 빈을 쓸지 지정 |
| `@Value("${설정값}")`   | 값 주입  | application.properties 값을 주입 |

#### 매핑 관련 어노테이션(Spring MVC)

| 어노테이션                       | 설명                       |
| --------------------------- | ------------------------ |
| `@RequestMapping("/hello")` | 경로 매핑 (GET/POST 등 모두 가능) |
| `@GetMapping("/hello")`     | GET 방식 요청 매핑             |
| `@PostMapping("/submit")`   | POST 방식 요청 매핑            |
| `@PathVariable`             | URL 경로의 변수값 추출           |
| `@RequestParam`             | 쿼리 파라미터 추출               |
| `@RequestBody`              | JSON → 객체 바인딩            |

### 스프링 DI 흐름과 어노테이션
#### 스프링에서의 의존성 주입 흐름
1. 클래스에 `@Component`, `@Service` 등으로 **빈 등록**
2. 필요한 의존성을 `@Autowired`를 통해 **주입**
3. 스프링 컨테이너가 객체를 관리하고 필요한 곳에 자동 주입

### 요약
- 어노테이션은 단순한 "정보 제공자"
- 스프링이 이 문법을 잘 활용하는 것
- 컴포넌트 등록(`@Component`, `@Service`)과 주입(`@Autowired`)가 핵심 흐름
- 스프링 기본 구조: **인터페이스 -> 구현 -> DI 주입**

### 그러면 내가 이해한 게 맞는지 정리를 해 보자

✅ "어노테이션을 이용해서 스프링이 작동한다는 건지?"
-> 스프링은 어노테이션을 통해 **개발자의 의도를 프레임워크에 알려주는 방식**
- `@Service`가 붙은 클래스: 나는 비즈니스 로직을 가진 플래스야
- `@Autowired`가 붙은 클래스: 여기에 의존성을 넣어 줘

✅ "객체 지향 프로그래밍에서 객체들을 사용하기 쉽게 빈으로 등록하고, 스프링이 사용할 때는 이 빈을 가져와서 사용하는 건지?"
- 빈: **스프링 컨테이너가 관리하는 객체**
- 직접 new 해서 쓰지 않고 스프링이 만들고 관리해 주는 객체
- 자바 객체 == 빈(스프링 관리 대상)이 되는 구조

✅ "스프링이 필요한 부분에 필요한 코드를 넣을 땐 @Autowired로 주입하는 건지?"
-`@Autowired`가 필요한 객체들을 자동으로 넣어 주는 역할(=의존성 주입, DI)를 하는 것
- 생성자, 필드, 새터에 붙여줄 수 있음

✅ "각각 객체들이 빈이 되는 거고 이 객체들을 연결시키는 게 의존성 주입이라는 소리인가?"
- 단순히 객체를 만들어서 연결 X
- **스프링이 관리하는 빈들 사이에서 필요한 연결을 자동으로 주입**하는 게 핵심
- 객체들을 연결 = **DI(의존성 주입)**

> 스프링은 어노테이션을 기반으로 객체(빈)을 등록하고, 그 객체 간의 의존성을 자동으로 주입하여, 개발자가 직접 객체 생성, 연결을 하지 않아도 되도록 하는 프레임워크

#### 흐름 정리
```
[개발자가 만든 클래스 (EmailSender)]
        ↓ @Component
[Bean으로 등록됨 (스프링 컨테이너가 관리)]
        ↓ @Autowired
[다른 클래스에서 필요한 Bean 주입 (e.g. Notifier에서 EmailSender 사용)]

```

## CH13 제네릭

### 제네릭(Generic)?
- 제네릭: 쉽게 말해서 **타입을 변수처럼 일반화시킨 문법**
- 제네릭 클래스: 타입이 정해지지 않은 클래스

- Box 클래스를 만든다면,
```
class StringBox {
    String value;
    void set(String value) { this.value = value; }
    String get() { return value; }
}
```
- 이렇게 만들 경우 `IntegerBox`,`DoubleBox` 등을 따로 만들어야 함

- **제네릭**을 사용한다면,
```
class Box<T> {
    T value;
    void set(T value) { this.value = value; }
    T get() { return value; }
}

```
- `T`: 타입 파라미터로, 이 클래스는 어떤 타입도 받을 수 있음
- 사용하는 쪽에서 타입을 지정해 주는 방식
```
Box<String> stringBox = new Box<>();
stringBox.set("Hello");

Box<Integer> intBox = new Box<>();
intBox.set(123);

```

#### 비유
- 기존 방식:  "문자 전용 우체통', "숫자 전용 우체통", "날짜 전용 우체통"을 각각 만들어야 함
- 제네릭 방식: "우체통" 하나가 문자, 숫자, 날짜를 다 감당

### 제네릭 타입
- 결정되지 않은 타입을 파라미터로 가지는 클래스와 인터페이스
- 제네릭 타입 예시
```
class Box<T> {
    private T value;

    public void set(T value) { this.value = value; }
    public T get() { return value; }
}
```
```
Box<String> strBox = new Box<>();
strBox.set("Hello");

Box<Integer> intBox = new Box<>();
intBox.set(100);
```
- Box<T>에서 T는 타입 파라미터(Type Parameter)
- Box<String>처럼 사용하면 타입이 정해짐(T -> String)
- 덕분에 하나의 Box 클래스로 다양한 타입 포용 가능
- Box<T>: 이거 자체가 제네릭 타입인 거임

### 제네릭 메서드
- **메서드 자체에 타입 파라미터를 선언**하는 방식
-> **클래스 전체가 제네릭이 아니어도** 메서드만 제네릭으로 쓸 수 있음
- 타입 파라미터가 메서드 선언부에서 정의된다는 점에서 제네릭 타입과 차이가 있음
```
public <T> T methodName(T param) {
    // T 타입의 로직
    return param;
}
```
- 여기에서 <T>는 **리턴 타입 앞에 위치한 타입 선언부**
- 이걸 붙여야 메서드 안에서 T를 타입처럼 쓸 수 있음
  
#### 장점
- 클래스가 제네릭이 아니더라도, **특정 기능만 타입 유연하게 사용 가능**
- `static` 메서드에서도 사용 가능(클래스 제네릭은 static이랑 같이 못 씀)

### 제한된 타입 파라미터
- 기본 제네릭은 `T`에 어떤 타입이든 올 수 있지만
- **특정 타입이나 그 자식 타입만 허용하고 싶을 때** 사용
  
```
class Box<T extends Number> { // Number 또는 그 하위 타입만 가능
    private T value;
    public void set(T value) { this.value = value; }
    public T get() { return value; }
}
```
  
#### 핵심 요약
| 구분                | 의미                                 |
| ----------------- | ---------------------------------- |
| `T extends 클래스`   | 클래스 또는 그 하위 타입만 가능                 |
| `T extends 인터페이스` | 인터페이스 구현체만 가능                      |
| `T extends A & B` | 다중 상한 제한도 가능 (클래스 1개 + 인터페이스 여러 개) |

### 와일드카드 타입 파라미터
- 제네릭 타입을 매개값이나 리턴 타입으로 사용할 때 타입 파라미터로 `?(와일드카드)` 사용 가능
- `?`는 범위에 있는 모든 타입으로 대체할 수 있다는 표시
  
#### 기본 문법
  | 구문              | 의미                            |
| --------------- | ----------------------------- |
| `<?>`           | 모든 타입 허용 (Unbounded wildcard) |
| `<? extends T>` | T 또는 T의 하위 타입 허용 (상한 제한)      |
| `<? super T>`   | T 또는 T의 상위 타입 허용 (하한 제한)      |

#### 예시 코드
```
List<?> list = new ArrayList<String>();
// 어떤 타입이든 올 수 있음

List<? extends Number> numbers = new ArrayList<Integer>();
// Number와 그 하위 타입만 가능 → Integer, Double 등

List<? super Integer> nums = new ArrayList<Number>();
// Integer와 그 상위 타입만 가능 → Number, Object 등

```
