## 5.1 Amazon S3 : 사용하기 쉬우며 기능이 강력한 스토리지 서비스
- Amazon S3 : 객체 스토리지 서비스 -> 설정에 따라서 정적 웹 서버로 공개하거나 쿼리를 사용할 수 있는 등 편리한 기능을 다양하게 갖춘 스토리지 서비스

### 5.1.1 Amazon S3 
- Amazon S3(Amazon Simple Storage Service) : 스마트한 객체 스토리지 서비스
- 객체 스토리지 : 데이터를 객체 단위로 관리하는 형식
- 인터넷상에 데이터 저장 장소 제공
- 용량 제한이 없으므로 최소한의 용량으로 시작해도 OK
#### <특징>
- 기능이 많음!
1. 쉽게 웹 서버를 만들 수 있음
2. 쿼리 기능으로 집계 가능
3. 확장 및 축소 간편

### 5.1.2 견고하고 스마트한 스토리지 서비스
#### <S3 특징>
1. 확장성 : 스토리지 클래스 & 수명 주기 정책
2. 가용성/내구성
3. 신뢰성 : 접근 관리 도구와 각종 규정 준수
4. 다양한 관리 기능 : 스토리지 클래스 분석과 리전 간 복제
5. 스마트한 기능 : S3 Select, 다른 서비스와 연동

### 5.1.3 요금 체계
- '보유하고 있는 용량' & '전송량' 기준으로 종량 과금됨
- S3 요금 = 저장 용량 X 전송량 
- 저장 용량 : 데이터를 지정한 양에 따라 과금
- 데이터를 주고받은 전송량에 따라 과금

### 5.1.4 전송량의 대한 개념
- 전송량 고려할 때 중요한 것 : 요청, 업로드, 다운로드
1. 수신 요청과 다운로드
- 수신 요청(GET) : 이 파일이 필요해
- 다운로드 : 파일 전송
2. 송신 요청과 다운로드
- 송신 요청(PUT) : 이 파일을 저장해
- 업로드 : 파일 전송

## 5.2 스토리지 클래스 : 다양한 종류의 스토리지

### 5.2.1 스토리지 클래스

- 스토리지 클래스 : 스토리지의 종류 <- S3에서 사용할 수 있는 스토리지 종류는 다양함
- Standard, 액세스 패턴에 따라 계층을 이동할 수 있는 클래스, 액세스 빈도가 낮은 데이터를 위한 클래스 등이 있어 사용자 목적에 맞춰 선택 가능
- 버킷(객체를 저장하는 컨테이너) 단위 X -> 객체(파일) 단위로 클래스 선택 가능
- 상황에 따라 변경할 수 있다는 점이 장점

### 5.2.2 스토리지 클래스의 종류

1. Standard : 가장 일반적인 클래스
- 3곳 이상의 AZ(가용 영역)에 데이터 저장 -> 99.9%의 가용성(시스템이 계속해서 가동하는 것) 보장
- 데이터를 검색할 때 요금 + 최소 용량의 요금이 없고 일할 계산 -> 쉽게 사용하기 좋음
2. Intelligent-Tiering
- 빈번한 액세스와 간헐적 액세스에 최적화된 두 가지 계층에 객체(파일)을 저장
- 어느 쪽에 저장할지는 객체별로 모니터하여 그 결과에 따라 자동 이동
- 기본적으로 Standard와 비슷하나 최소 저장 기간에 대한 요금이 설정되어 있어 주의 필요
3. Infrequent Access
- Standard 클래스에 비해 저장 요금이 낮게 설정되어 있는 대신 액세스 요금이 조금 높게 설정
- 액세스 빈도가 낮고 용량이 큰 데이터에 적합
4. Reduced Redundancy Storage
- 엄밀히 보면 스토리지 클래스가 아닌 옵션으로 분류되지만, 한 종류밖에 없기 때문에 실질적으로 스토리지 클래스의 하나라고 생각하는 것이 좋음
- Standard에 비해 이중화 수준을 맞춰 낮은 가격으로 제공
- 저장되는 AZ가 한 군데이므로 문제가 발생할 경우 데이터 유실 가능성 있음
5. S3 Glacier/S3 Deep Archive
- Glacier는 데이터 아카이브와 장기간 백업을 고려하여 만든 스토리지 클래스
- 다른 클래스와 마찬가지로 99.9999% 내구성을 가지며 가격이 낮아 대용량 데이터를 저렴한 가격으로 보관할 수 있음
- 데이터는 '볼트'라는 컨테이너에 저장
- 따라서 저장된 데이터를 읽는 경우 다른 S3 버킷으로 옮겨야 하는 작업 필요
- 범위로 검색해 일부 데이터만 검색 가능 But 기본적으로는 통으로 검색함
- 검색할 경우 Glacier 상의 데이터와 검색 대상의 데이터 양쪽에 요금이 부과되므로 주의할 것

## 5.3 S3의 사용 절차 : 스토리지 서비스를 사용하기까지
- S3는 파일을 버킷에 저장함
- 버킷에 저장한 파일 = 객체

### 5.3.1 S3 조작
- 기본적인 S3 조작(버킷의 생성 및 각종 설정 같은) -> 관리 콘솔의 S3 대시보드에서 수행
- 가장 기본적으로 객체(파일)의 업로드를 수행
- S3의 경우 API와 SDK를 사용하여 업로드하기 떄문에, 파일 업로드가 편함
- AWS Transder for SFTP가 제공되어 SFTP로 액세스 가능

### 5.3.2 S3 서비스의 기능
#### <S3 서비스 용어>
- 객체 : S3의 엔터티 단위, 텍스트나 이미지 등의 파일을 칭함
- 버킷 : 객체 저장 컨테이너, 모든 객체는 버킷에 저장
- 버킷명 : S3 버킷의 명칭은 다른 AWS 사용자를 포함하여 유일한 이름이어야 함, 웹 서버로 사용할 경우 도메인명 = 버킷명
- 객체 키 : 객체 식별자 모든 객체는 반드시 한 개의 키를 가짐, 버킷/객체 키/버전을 조합하여 객체를 고유하게 식별 = 이름이다
- 객체 메타 데이터 : 이름과 값의 세트, 객체를 업로드할 때 설정
=> 객체 키는 S3가 파일을 식별하기 위한 데이터, 메타데이터는 사람이 파일을 쉽게 관리하기 위한 데이터
- 리전 : 버킷의 물리적인 보관 장소가 있는 지역
- Amazon S3의 데이터 일관성 모델 : 쓰기 지연에 의한 데이터 불일치가 발생하면 안 되기 때문에 데이터의 무결성 보전
- 버전 관리 : 여러 버전 보관, 다른 버전은 별도의 객체로 취급
- 로그 : 버킷 단위나 객체 단위의 로그 기록 가능
- 암호화 : S3에 저장되는 데이터를 자동으로 암호화 가능
- 액세스 제어 : S3 버킷에 대해 권한 설정 가능
- 웹 서비스 : S3 버킷을 웹 사이트로 사용하는 기능

### 5.3.3 S3의 사용 절차
1. AWS에 로그인
- 리전을 선택하고 관리 콘솔을 열기
- S3 대시보드를 열기
2. 버킷을 만든다
- 버킷명 설정
3. 버킷을 설정
- 웹 서버로 사용할 경우 Static website hosting을 설정
- 접근할 수 있는 사용자 설정
4. 파일 업로드
- 관리 콘솔이나 전용 도구에서 파일 업로드

### 5.3.4 S3 버킷 생선 전 검토해야 할 것
- S3 버킷을 생성한 후에는 이름과 리전 변경 불가능
=> S3 버킷을 생성하기 전 어떻게 만들 것인지 고민 검토 과정 중요
#### <S3 버킷 생성 전 검토해야 할 것>
1. 웹 사이트로 사용할지 여부
1.1 (YES) 소메인을 사용할지 여부
-> 둘 다 익명 접속을 허가함
1.1.1 (YES) 버킷명을 도메인명과 똑같이 해야 함
1.1.2 (NO) 하고 싶은 이름을 써도 되지만 도메인명의 일부는 호스트명이 되므로 주의
1.2 (NO) 파일 서버인지, 로그 저장소인지
-> 접속 가능한 사용자를 관리하자
1.2.1 파일 서버 : 사용법에 맞게 도구나 SFTP 준비
1.2.2 로그 저장소 : 접속 대상과 인증 방법 고려

## 5.4 객체와 버킷 : 파일과 파일을 저장하는 장소
- 버킷명은 S3 내에서 유일한 이름이어야 함

### 5.4.1 객체와 버킷
- 버킷 : 윈도우 드라이브와 같은 것
- 객체 : 파일과 같은 것
- 버킷은 폴더가 아니므로 버킷 안에 버킷 만드는 행위 불가
- AWS 계정 한 개당 버킷 100개까지 생성 가능
- 객체도 단순한 파일이 아니라 관리를 위한 메타데이터 포함
- 버킷 한 개에 저장할 수 있는 객체 수는 제한이 없고 총 용량에도 제한 없음

### 5.4.2 버킷 생성과 명명 규칙
- 버킷 명은 처음과 마지막에 알파벳 or 숫자를 사용해야 함
- 3글자 이상 63글자 이하
- IP 주소 형식은 버킷명으로 쓸 수 없음
- 대문자 or 언더스코어는 버킷명으로 사용 불가
- DNS 명명 규칙에 따름
