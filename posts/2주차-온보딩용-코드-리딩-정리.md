# 도메인 분석 및 기능 목록

## Account 도메인: 회원가입, 로그인, JWT 인증

### 1. 기능 단위 구조 정리

#### 1.1 사용자 관리 기능
**기능 설명**
- 사용자는 `User` 엔티티로 관리
- 사용자 계정은 이메일을 기준으로 유니크하게 식별
- 사용자 상태는 `AccountStatus`를 통해 관리
- 특정 사용자 조회 및 로그인 사용자 본인 정보 조회 기능 제공

**관련 API**
- `GET /account/users/{username}` : 특정 사용자 조회
- `GET /account/@me` : 로그인한 사용자 정보 조회
- `PATCH /account/@me` : 로그인 사용자 정보 수정
- `DELETE /account/unregister` : 회원 탈퇴

**관련 코드**
- `apps/account/models.py` -> `User`
- `apps/account/enums.py` -> `AccountStatus`
- `apps/account/endpoints.py` -> `user_detail`, `me`, `update_user`, `unregister`

**특징**
- 사용자 조회 시 `User` 엔티티를 직접 반환하는 구조
- 정보 수정 시 엔티티 로딩 없이 Bulk Update 방식 사용
- 회원 탈퇴 시 상태 변경(Soft Delete) 구조가 있음에도 실제로는 Hard Delete 사용
- 상태 판단 로직(`is_active`, `is_deleted`)이 엔티티 내부에 캡슐화되어 있음

#### 1.2 회원가입 기능
**기능 설명**
- 신규 사용자 계정을 생성
- username과 email 중복을 검증

**관련 API**
`POST /account/signup`: 회원가입

**처리 흐름**
1. username 중복 여부 사전 조회
2. User 엔티티 생성
3. DB 저장 시 email Unique Constraint 위반 여부 확인

**관련 코드**
- `SignupPayload`
- `apps/account/models.py` -> `User`
- `DuplicatedUsernameError`, `DuplicatedEmailError`

**특징**
- username은 애플리케이션 레벨에서 중복 체크
- email은 DB 제약 조건에 의존하는 이중 검증 구조

#### 1.3 로그인 및 JWT 인증 기능
**기능 설명**
- 사용자 인증 후 JWT Access Token을 발급
- 발급된 토큰은 HTTP-only Cookie에 저장

**관련 API**
- `POST /account/login`
- `DELETE /account/logout`

**처리 흐름**
1. username 기준 사용자 조회
2.비밀번호 검증
3. JWT Access Token 생성
4. 응답 Body + Cookie 설정

**토큰 구성 정보**
- username
- display_name
- is_host

**관련 코드**
- `verify_password`
-`create_access_token`
- `AUTH_TOKEN_COOKIE_NAME`

**특징**
- 인증 로직이 Endpoint에 직접 위치
- Access Token만 사용하며 Refresh Token은 없음
- 로그아웃 시 서버 상태 변경 없이 Cookie 삭제만 수행

#### 1.4 OAuth 기반 로그인 기능
**기능 설명**
- 사용자는 `OAuth` 계정을 통한 로그인 가능
- 하나의 사용자 계정에 여러 `OAuth` 계정 연결 가능
- `OAuth` 계정은 `(provider, provider_account_id)` 조합으로 유니크하게 관리

**관련 코드**
- `apps/account/models.py` -> `OAuthAccount`

**특징**
- `OAuth` 계정은 단독으로 존재하지 않고, `User`에 종속되는 구조
- `OAuthAccount`는 인증 식별자 역할 집중

#### 1.5 사용자 역할 및 예약 관계
**기능 설명**
- 사용자는 예약 시스템에서 Host/Guest 역할을 가질 수 있음
- Host 사용자는 1개의 `Calendar`를 소유
- Guest 사용자는 N개의 `Booking` 소유 가능

**관련 코드**
- `apps/account/models.py` -> `User.calendar`, `User.booking`
- `apps/calendar/models.py`

**특징** 
- 역할을 별로 Role 테이블로 분리하지 않고 관계로 표현
- 한 사용자가 Host이면서 동시에 Guest가 될 수 있는 구조
- 역할이 "권한"이 아니라 "도메인 관계"로 모델링

### 2. 기술적 설계 포인트

### 3. Java 마이그레이션

**전환 방향**

#### 3.2 사용자 상태 관리 개선

	- ex) ACTIVE -> DELETE 허용, DELETE -> ACTIVE 제한
    
#### 3.3 OAuth 인증 구조 재설계
**문제점**
- `OAuthAccount`는 단순 매핑 엔티티 역할만 함
**전환 방향** (따로 Service를 만들어서 분리한다는 건가?)

- `OAuthAccount`는 인증 식별자 역할만 담당하도록 함

#### 3.4 관계 설계 유지 및 명확화
**유지사항**
- `User` <-> `Calendar` (1:1)
- `User` <-> `Booking` (1:N)

## Calendar/Booking 도메인: 일정 관리 및 예약 시스템
### 1. 기능 단위 구조 정리
#### 1.1 Calendar 관리 기능 (Host 전용)
**기능 설명**
- Host 사용자는 자신의 Calendar를 생성/조회/수정 가능
- Calendar는 공개 정보와 상세 정보로 구분 조회됨

**관련 API**
- `POST /calendar` : 캘린더 생성
- `PATCH /calendar` : 캘린더 수정
- `GET /calendar/{host_username}` : 캘린더 조회
	- 본인 -> 상세 정보
	- 타인 -> 공개 정보

**관련 Model**
`Calendar`
- `topics`: 예약 주제 목록
- `description`: 게스트에게 노출되는 설명
- `google_calendar_id`: 외부 캘린더 연동 식별자
- `host_id`: User와 1:1 관계

**특징**
- Host 1명당 Calendar 1개 (`host_id unique`)
- 권한 검증이 Endpoint 레벨에서 직접 수행됨

#### 1.2 TimeSlot 관리 기능 (예약 가능 시간 정의)
**기능 설명**
- Host는 자신의 Calendar에 예약 가능한 시간대를 등록
- 요일 + 시간 범위 기반으로 예약 가능성 정의

**관련 API**
- `POST /time-slots` : 타임슬롯 생성
- `GET /time-slots/{host_username}` : 타임슬롯 조회

**관련 Model**
`TimeSlot`
- `start_time`, `end_time`
- `weekdays`: 예약 가능한 요일 목록(JSON)
- `calendar_id`: Calendar 소속

**특징**
- TimeSlot 중복 검증 로직 존재
- DB 종류에 따라 로직 분기
- SQLite: Python 로직
- PostgreSQL: JSONB + SQL 함수

#### 1.3 Booking 생성 기능 (Guest 전용)
**기능 설명**
- Guest는 Host의 Calendar에 예약 생성 가능
- 예약은 특정 날짜 + TimeSlot 조합으로 생성

**관련 API**
- `POST /bookings/{host_username}`

**주요 검증 로직**
- Host 존재 여부
- 자기 자신 예약 방지
- 과거 날짜 예약 방지
- TimeSlot 요일 유효성 검증
- 동일 예약 중복 방지

**관련 Model**
`Booking`
-`when`: 예약 날짜
-`topic`, `description`
-`attendance_status`
-`time_slot_id`, `guest_id`
-`google_event_id`

**특징**
- 예약 생성 후 Google Calendar 이벤트 생성
- 외부 연동은 Background Task로 비동기 처리

#### 1.4 Booking 조회 기능
**Host 기준**
- `GET /calendar/{host_username}/bookings`
- `GET /calendar/{host_username}/bookings/stream`
- 월 단위 예약 조회
- Google Calendar 이벤트 병합 조회

**Guest 기준**
- `GET /guest-calendar/bookings`
- 페이지네이션 기반 조회

#### 1.5 Booking 수정 및 상태 관리
**Host 기능**
- 예약 일정 변경
- 예약 상태 변경 (`attendance_status`)
-`PATCH /bookings/{booking_id}`
-`PATCH /bookings/{booking_id}/status`

**Guest 기능**
- 예약 내용 수정
- 예약 취소
- `PATCH /guest-bookings/{booking_id}`
- `DELETE /guest-bookings/{booking_id}`

**특징**
- 과거 예약에 대한 수정/취소 제한
- 상태 변경 시 Google Calendar 이벤트 동기화

#### 1.6 예약 파일 업로드 기능
**기능 설명**
- Guest는 예약에 파일 업로드 가능

**관련 API**
- `POST /bookings/{booking_id}/upload`

**관련 Model**
- `BookingFile`
	- FileSystemStorage 기반 파일 저장
	- Booking에 종속
    
### 2. 기술적 설계 포인트
#### 2.1 비즈니스 로직의 위치
- 대부분의 검증/도메인 규칙이 Endpoint에 직접 위치
- Service 계층 부재

#### 2.2 트랜잭션 경계
- DB 커밋 후 외부 API 호출
```python
session.add(booking)
await session.commit()   # ✅ 여기서 DB는 확정됨
...
background_tasks.add_task(_apply_event_id)  # 👉 그 다음 Google API
```
1. DB에 예약 저장됨 (되돌릴 수 없음)
2. 그 다음에 Google Calendar에 일정 생성 요청
3. 만약 Google API 실패하면?
- 보상 트랜잭션 없음 <= 외부 API를 실패했을 때 방금 만든 예약을 취소하는 로직이 없음

#### 2.3 동시성 이슈 가능성 
- TimeSlot 중복 검증은 애플리케이션 레벨
- 동시 요청 시 레이스 컨디션 가능 
- UNIQUE 붙여서 동시에 예약할 수 없게 막아야 할 것 같음 (해당 로직을 찾지 못함)

- 인증/인가: Account 도메인 의존

- Calendar/Booking은 Account 없이 동작 불가

## 외부 연동: Google Calendar API
### 1. 연동 대상 및 책임
**연동 대상**
- Google Calendar Event: 예약(Booking) 단위로 Google Calendar Event 1개 생성

**책임 분리**
- 내부 시스템: 예약 데이터 정합성 보장
- 외부 시스템: 일정 시각화 및 알림 제공

### 2. 기능 단위 연동 흐름 
#### 2.1 예약 생성 시 연동
**연동 시점**
- Booking 생성 후 DB 커밋 완료 이후
**처리 흐름**
1. Booking 생성 및 DB 저장
2. Background Task 등록
3. Google Calendar API 호출
4. 생성된 Event ID를 Booking에 저장

**관련 코드**
-`POST /bookings/{host_username}`
-`GoogleCalendarService.create_event`
-`booking.google_event_id`

**특징**
- 외부 API 호출 실패 시 예약 자체는 유지됨
- 외부 연동은 시스템 핵심 트랜잭션에 포함되지 않음

#### 2.2 예약 수정 시 연동
**연동 시점**
- 예약 날짜 또는 시간 변경 시

**처리 흐름**
1. Booking 수정
2. DB 커밋
3. Google Calendar Event 업데이트 (비동기)

**특징**
- Google Event ID가 존재할 경우에만 업데이트 수행
- 내부 상태 변경과 외부 상태 변경이 분리됨

#### 2.3 예약 취소 시 연동
**연동 시점**
- 예약 취소 처리 이후

**처리 흐름**
1. Booking 상태를 CANCELLED로 변경
2. DB 반영
3. Google Calendar Event 삭제 (비동기)

### 3. 기술적 설계 포인트 
#### 3.1 비동기 처리 방식
- FastAPI BackgroundTasks 사용
- DB 트랜잭션 이후 외부 API 호출 수행

**의도**
- 외부 API 지연으로 인한 사용자 응답 지연 방지
- 내부 시스템 안정성 우선

#### 3.2 트랜잭션 경계
```
[DB Transaction] ── commit ──▶ [Google Calendar API]
```
- 내부 DB 상태가 항상 우선
- 외부 연동 실패 시 보상 트랜잭션 없음

#### 3.3 장애 및 불일치 가능성
- Google API 호출 실패 시:
	- 예약은 존재
	- 외부 일정은 누락될 수 있음
	- 재시도 또는 동기화 보정 로직 없음

### 4. 설계상 한계 및 개선 포인트
**문제점**
- 외부 연동 실패 감지 및 재처리 불가
- DB 상태와 외부 상태 간 불일치 가능
- Google Calendar 연동 로직이 Endpoint에 직접 노출됨
