> **[Point]** 객체 지향 패러다임의 핵심은 **자율적인 객체들의 협력**

객체지향의 목표는 실세계를 모방하는 것이 아닌 새로운 세계를 창조하는 것
실세계의 모방이라는 개념은 비현실적이지만 실세계에 대한 비유가 객체지향의 다양한 측면을 이해하고 학습할 때 효과적이라 놓지 못하는 것
그래서 소프트웨어 객체란 실세계 사물의 모방이라는 전통적인 관점에서 객체지향의 다양한 개념을 학습해야 함

# 협력하는 사람들
- 커피 주문이라는 상황을 가정해 보자
- 커피 주문이라는 협력에 참여하는 모든 사람들은 커피가 정확하게 주문되고, 주문된 커피가 손님에게 정확하게 전달될 수 있도록 맡은 바 역할과 책임을 다하고 있는 것
- 제조된 커피를 받아 들고 일자리로 돌아가는 것까지 손님의 책임 완수
- 객체지향에서 가장 중요한 개념 세 가지는 **역할, 책임, 협력**

## 협력 = 요청 + 응답
- 사람은 스스로 해결하지 못하는 문제에 직면했을 때, 도움을 받을 수 있는 사람에게 도움을 요청(request)한다
- 일반적으로 하나의 문제를 해결하기 위해 다수의 사람/역할이 필요하기 때문에 요청은 연쇄적으로 발생한다
- 요청을 받은 사람은 주어진 책임을 다하면서 필요한 지식/서비스를 제공한다 => 다른 사람의 요청에 응답(response)한다
- 따라서 응답 역시 요청의 반대 방향으로 연쇄적으로 발생
- 요청과 응답을 통해 다른 사람과 협력할 수 있는 능력은 인간으로 하여금 거대하고 복잡한 문제를 해결할 수 있는 공동체를 형성할 수 있게 함
- 협력의 성공은 특정한 역할을 맡은 각 개인이 얼마나 요청을 성실히 이행하는가에 달림

## 역할과 책임
- 역할(role): 어떤 협력에 참여한느 특정한 사람이 협력 안에서 차지하는 책임이나 의무를 의미
- 책임(responsibility) => 역할이라는 단어는 의미적으로 책임이라는 개념 내포
- 특정한 역할은 특정한 책임 암시 => 협력에 참여하며 특정할 역할을 수행하는 사람들은 역할에 적합한 책임을 수행

"사람들이 협력을 위해 특정한 역할을 맡고 역할에 적합한 책임을 수행한다?"
1. 여러 사람이 동일한 역할 수행 가능
2. 역할은 대체 가능성
3. 책임을 수행하는 방법은 자율적으로 선택 가능 
	- 다형성(polymorphism): 동일한 요청에 대해 서로 다른 방식으로 응답할 수 있는 능력
4. 한 사람이 동시에 여러 역할 수행 가능

# 역할, 책임, 협력
> 사람 => "객체"
에이전트의 요청 => "메시지"
에이전트의 요청 처리 방법 => "메서드"

- 기능을 구현하기 위해 협력하는 객체들
- 역할과 책임을 수행하며 협력하는 객체들

- 애플리케이션의 기능은 더 작은 책임으로 분할 
- 책임은 적절한 역할을 수행할 수 있는 객체에 의해 수행됨
- 시스템은 역할과 책임을 수행하는 객체로 분할
- 시스템의 기능은 객체 간의 연쇄적인 요청과 응답의 흐름으로 구성된 협력으로 구현

- 객체지향 프로그래밍에서 역할은 중요하지만 간과하는 경우가 많음
- 역할은 유연하고 재사용 가능한 협력 관계를 구축할 때 중요한 설계 요소
- 대체 가능한 역할과 책임은 객체지향 패러다임의 중요한 기반을 제공하는 다형성과도 깊이 연관

# 협력 속에 사는 객체
- 객체지향 애플리케이션에서 실제로 협력에 참여하는 주체는 "객체"
- 객체가 없다면 객체지향 세계도 아무 의미 X
- 객체는 애플리케이션 기능을 구현하기 위해 존재 
	- 아주 작은 기능도 혼자 감당하기에 버거워 일반적으로 다른 객체와의 협력을 통해 기능을 구현
    - 협력 => 객체 지향의 아름다움 결정
    - 객체 => 협력이 얼마나 조화를 이루는지

- 공동체의 일원으로 객체가 갖춰야 할 두 가지 덕목
	- 객체는 충분히 "협력적"이어야 함 => 다른 객체의 요청에 충실히 귀를 기울이고 다른 객체에게 적극적으로 도움을 요청할 수 있는 오픈마인드여야 함
    - 객체는 충분히 "자율적"이어야 함 => 객체 공동체에 속한 객체들은 공동의 목표를 달성하기 위해 협력에 참여하지만, 스스로의 결정과 판단에 따라 행동하는 자율적인 존재여야 함
    
상태와 행동을 함께 지닌 자율적인 객체
- 객체 = 상태(state)와 행동(behavior)을 함께 지닌 실체라고 정의
	- 객체가 협력에 참여하기 위해 어떤 행동을 해야 한다면 그 행동을 하는 데 필요한 상태도 함께 지니고 있어야 함(어떤 행동을 하기 위해 필요한 상태를 모르는 게 말이 안 됨)
    
객체의 자율성 => 객체의 내부와 외부를 명확하게 구분하는 것으로부터 나옴
	- 사적인 부분: 객체 스스로 관리하고 외부에서 간섭할 수 없게 X
    - 외부에서는 접근이 허락된 수단을 통해서만 객체와 의사소통해야 함
    - 객체가 '무엇(what)'을 수행하는지는 알 수 있지만 '어떻게(how)' 수행하는지에 대해 알 수 없어야 함
    
> 내 의문
1. 객체의 자율성?
- 자율성 = 객체가 자기 행동과 상태를 스스로 관리(철학/원리)
2. 인터페이스와의 차이
- 외부가 객체의 "무엇을 할 수 있는지"만 알게 하는 계약 도구(언어적 장치)
3. 캡슐화의 차이
- 내부를 감추어 자율성 보장(실천 방법)

과거 전통적 개발 방법 = 데이터와 프로세스의 엄격한 구분
객체지향 = 데이터와 프로세스를 하나로 묶어서 객체의 자율성을 보장
- 자율적인 객체로 구성된 공동체는 유지보수가 쉽고 재사용이 용이한 시스템을 구축할 수 있는 가능성 제시

## 협력과 메시지
- 객체는 협력을 위해 다른 객체에게 메시지를 전송하고, 다른 객체로부터 메시지를 수신함
- 협력은 메시지를 전송하는 객체와 메시지를 수신하는 객체 사이의 관계로 구성
- 메시지 전송 객체 = 송신자
- 메시지 수신 객체 = 수신자
    
## 메서드와 자율성
- 메서드(method) = 객체가 수신된 메시지를 처리하는 방법
- 객체지향 프로그래밍 언어에서는 클래스 안에 포함된 함수 or 프로시저를 통해 구현
- 메시지를 수신한 객체가 실행 시간에 메서드를 선택할 수 있ㄴ다는 점은 다른 프로그래밍 언어와 구분되는 특징
- 절차적인 언어 => 프로시저 호출에 대한 실행 코드를 컴파일 시간에 결정함

- 외부의 요청이 무엇인지 표현하는 메시지와 요청을 처리하기 위한 구체적인 방법인 메서드를 부닐하는 건 객체의 자율성을 높이는 핵심 메커니즘 => 자율화

# 객체 지향의 본질
- 객체지향: 시스템을 상호작용하는 자율적인 객체들의 공동테로  바라보고 객체를 이용해 시스템을 분할하는 방법
- 자율적인 객체: 상태와 행위를 함꼐 지니며 스스로 자기 자신을 책임지는 객체
- 객체는 시스템 행위 구현을 위해 다른 객체와 협력 => 각 객체는 협력 내에서 정해진 역할을 수행하며 역할은 관련된 책임의 집합
- 객체는 다른 객체와 협력하기 위해 메시지를 전송하고, 매시지를 수신한 객체는 메시지를 처리하는 데 적합한 메서드 자율적으로 선택

- 클래스는 객체지향에 중요한 구성 요소지만 객체지향의 핵심을 이루는 중심 개념은 X
- JS 같은 프로토타입 기반 객체지향 언어에서는 클래스 존재 X, 오직 객체만 존재함

- 코드를 담는 클래스의 관점에서 객체의 관점으로 사고의 중심을 전환하는 것 
- 핵심은 적절한 책임을 수행하는 역할 간의 유연하고 견고한 협력 관계를 구축하는 것
