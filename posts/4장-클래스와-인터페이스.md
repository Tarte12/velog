# ITEM 15 클래스와 멤버의 접근 권한을 최소화하라
> 잘 설계된 컴포넌트는 정보 은닉(캡슐화)가 잘 되어 있음

### 정보 은닉의 장점
- 시스템을 구성하는 컴포넌트를 서로 독립시켜 개발, 테스트, 최적화, 적용, 분석, 수정을 개별적으로 해 줄 수 있음
1. 시스템 개발 속도를 높임 => 컴포넌트의 병렬 개발이 가능해짐
2. 시스템 관리 비용 낮춤 => 각 컴포넌트의 빠른 파악 디버깅, 다른 컴포넌트로 교체하는 부담 적어짐
3. 정보 은닉 자체가 성능 최적화에 도움을 줌 => 최적화할 컴포넌트만 골라서 최적화할 수 있음 (다른 컴포넌트에 영향 X)
4. 소프트웨어의 재사용성 => 외부에 거의 의존하지 않고 독자적으로 동작할 수 있다면 낯선 환경에도 유용하게 쓰일 가능성이 큼
5. 큰 시스템을 제작하는 난이도를 낮춤 => 시스템이 완성되지 않았어도 개별로 검증 가능

**자바는 정보 은닉을 위한 다양한 장치를 제공함**
> 핵심은 자바가 제공하는 **접근 제한자**를 제대로 활용하는 것
=> **모든 클래스와 멤버의 접근성을 최대한 좁히자**

- 접근 제어 메커니즘은 클래스, 인터페이스, 멤버의 접근성(접근 허용 범위)를 명시
- 그리고 각 요소의 접근성은 그 요소가 선언된 위치와 접근 제한자(private, protected, public)으로 정해짐

### 톱레벨 클래스와 인터페이스에 부여하는 접근 수준
- **package-private**: 해당 패키지 안에서만 이용 가능 => 패키지 외부에서 쓸 이유가 없다면 public으로 선언할 이유 X
	-> 클라이언트에 아무런 피해 없이 다음 릴리스에서 수정, 교체, 제거 가능
    -> public이 된다면 API가 되어 하위 호환을 위해 영원히 관리 필요
- **public**: 공개 API가 됨
- **private static**: 한 클래스에서만 사용하는 package-private 톱레벨 클래스나 인퍼에이스는 이것을 사용하는 클래스 안에 **private static**로 중첩시키자 (아이템 24) => 중첩시키면 바깥 클래스 하나에서만 접근 가능

### 멤버(필드, 메서드, 중첩 클래스, 중첩 인터페이스)에 부여하는 접근 수준
- **private**: 멤버를 선언한 톱레벨 클래스에서만 접근 가능
- **package-private**: 멤버가 소속된 패키지 안의 모든 클래스에서 접근 가능
- **protected**: package-privte 접근 범위 + 이 멤버를 선언한 클래스의 하위 클래스에서도 접근 가능
- **public**: 모든 곳에서 접근 가능

### 접근 수준 어떻게 정해야 할까
- 공개 API를 잘 설계하고, 나머지는 **private**로 돌리자
- 오직 같은 패키지의 다른 클래스가 접근해야 하는 멤버만 **package-private**로 바꿔 주자
- 권한을 많이 풀어야 되면 컴포넌트를 더 쪼갤 생각을 하자
- 보통 private와 package-privete 멤버는 공개 API에 영향을 주지 않지만, **Serializable을 구현한 클래스**는 그 필드도 의도치 않게 공개 API가 될 수 있다 (아이템 86, 87)
- 상위 클래스의 메서드를 재정의할 때는 그 접근 수준을 상위 클래스에서보다 좁게 설정할 수 없다 => 접근성을 좁히지 못하게 방해하는 제약이 됨
-> 상위 클래스의 인스턴스는 하위 클래스의 인스턴스로 대체해 사용할 수 있어야 한다는 리스코프 치환 원칙에 때문에 필요
- 테스트를 위해 어느 정도 접근 범위 늘려도 되지만 공개 API는 안 됨
- **public 클래스**는 상수용 public static final 필드 외에는 **어떠한 public 필드도 가져서는 안 됨**
- public static final 필드가 참조하는 객체가 불변인지 확인하자

### 어떻게 package-private를 쓸까?

```java
// com.example.todo.domain 패키지
package com.example.todo.domain;

// ✅ User는 public (외부에서 사용해야 하니까)
public class User {
    private String name;
    private UserNameValidator validator = new UserNameValidator();
    
    public void changeName(String newName) {
        validator.validate(newName);  // 내부적으로만 사용
        this.name = newName;
    }
}

// ✅ Validator는 package-private (User 내부 로직에만 필요)

    void validate(String name) {
        if (name == null || name.length() > 50) {
            throw new IllegalArgumentException("이름 규칙 위반");
        }
    }
}

// ✅ 이것도 package-private (도메인 내부 헬퍼)
class UserNameFormatter {
    String format(String name) {
        return name.trim().toLowerCase();
    }
}
```

# ITEM 16 public 클래스에서는 public 필드가 아닌 접근자 메서드를 사용하라
#### 퇴보한 클래스
> 인스턴스 필드를 모아놓는 일 이외에 목적 없는 클래스

```java
class Point {
	public double x;
    public double y;
}
```
**문제점**
- 캡슐화 이점 X
- API 수정하지 않고 내부 표현 바꿀 수 X
- 불변식 보장 X
- 외부에서 필드에 접근할 때 부수 작업 수행 X

**대안**
- 필드를 private로 바꾸고 public 접근자(getter)를 추가

#### 접근자와 변경자(mutator) 메서드를 활용해 데이터 캡슐화
```java
class Point {
	private double x;
    private double y;
    
    public Point(double x, double y) {
    this.x = x;
    this.y = y;
	}
    
    public double getX() {return x;}
    public double getY() {return y;}

    public double setX() {this.x = x;}
    public double setY() {this.y = y;}
}
```
**문제점**
- public 클래스는 이 방식이 맞음
- **패키지 바깥에서 접근할 수 있는 클래스라면 접근자를 제공**함으로써 내부 표현 방식을 언제든 바꿀 수 있는 유연성 얻을 수 있음
- 하지만, **package-private 클래스 혹은 private 중첩 클래스라면 데이터 필드를 노출해도 문제가 없음**
- 해당 클래스가 표현하려믄 추상 개념만 올바르게 표현하면 됨
- 이 방식이 접근자 방식보다 깔끔함

> **결론**: 그러니까 **package-private 클래스 혹은 private 중첩 클래스**는 종종 (불변이든 가변이든) 필드를 노출하는 게 나을 수 있음

### 4가지 비교
```java
// ❌ public 클래스 - 반드시 getter 필요
public class Point {
    public double x;  // 나쁨!
    public double y;
}

// ✅ public 클래스 - getter 사용
public class Point {
    private double x;
    private double y;
    
    public double getX() { return x; }
    public double getY() { return y; }
}

// ✅ package-private 클래스 - 필드 노출 OK
class Point {
    public double x;  // 같은 패키지 내에서만 쓰니까 괜찮음
    public double y;
}

// ✅ private 중첩 클래스 - 필드 노출 OK
public class Line {
    private static class Point {  // Line 내부에서만 사용
        public double x;  // 외부에 노출 안 되니까 괜찮음
        public double y;
    }
    
    private Point start = new Point();
}
```
- **이중 캡슐화**를 피하자는 논리

# ITEM 17 변경 가능성을 최소화하라
- 불변 클래스: 그 인스턴스의 내부 값을 수정할 수 없는 클래스
- ex) String, 기본 타입의 박싱된 클래스들, BigInteger, BigDecimal 
- 불변 클래스는 가변 클래스보다 설계, 구현, 사용 쉽고 오류 적고 안전함

### 클래스를 불변으로 만드는 규칙
**1. 객체의 상태를 변경하는 메서드(변경자)를 제공하지 않는다**
**2. 클래스를 확장할 수 없게 한다**
- 하위 클래스에서 객체의 상태를 변하게 만드는 사태를 막음

**3. 모든 필드를 final로 선언한다**
- 시스템이 강제하는 수단을 이용해 설계자의 의도를 드러내는 방법
- 새로 생성된 인스턴스를 동기화 없이 다른 스레드로 건네도 문제없이 동작하게끔 보장할 때 필요

**4. 모든 필드를 private로 선언한다**
- 필드가 참조하는 가변 객체를 클라이언트에서 직접 접근해 수정하는 일을 막음

**5. 자신 외에 내부 가변 컴포넌트에 접근할 수 없게 한다**
- 클래스에 가변 객체를 참조하는 필드가 하나라도 있다면 클라이언트에서 그 객체의 참조를 얻을 수 없게 해야 함

### 불변 객체의 특징
- **단순함** => 생성 시점의 상태를 파괴될 때까지 그대로 간직하기 때문
- **불변 객체는 근본적으로 스레드 안전하여 따로 동기화할 필요없음** => 여러 스레드가 동시에 사용해도 훼손 X
- 다른 스레드에 영향 못 주니까 **안심하고 공유 가능**
- **불변 객체는 자유롭게 공유할 수 있고, 불변 객체끼리 내부 데이터 공유 가능**
- **객체를 만들 때 다른 불변 객체들을 구성요소로 사용하면 이점이 많음**
-> ex) 맵의 키, 집합(Set)의 원소로 사용 => Map, Set은 **안에 담긴 값이 바뀌면 불변식이 망가짐**
- **불변 객체 자체로 실패 원자성 제공** => 상태가 변하지 않아서 불일치 상태 빠질 가능성 X
- **단점: 값이 다르면 반드시 독립된 객체로 만들어야 함**

### 정리
- getter가 있다고 setter를 무조건 만들지 말자
- **클래스는 꼭 필요한 경우가 아니면 불변으로**
- **불변으로 만들 수 없는 클래스도 변경할 수 있는 부분을 최소한으로**
- **합당한 이유가 없다면 모든 필드는 private final로**
- **생성자는 불변식 설정이 모두 완료된 초기화가 완벽히 끝난 상태의 객체를 생성해야 함**

### 불변 객체를 어떤 식으로 쓸까?
- **Entity는 가변이어도 되지만 DTO는 불변으로**
```java
// ❌ Entity를 불변으로 만들면 안 됨 (JPA가 동작 안 함)
@Entity
public class Todo {
    @Id @GeneratedValue
    private Long id;
    private String title;
    private boolean completed;
    
    // 상태 변경 메서드 (가변)
    public void complete() {
        this.completed = true;
    }
    
    public void updateTitle(String newTitle) {
        this.title = newTitle;
    }
}
```
```java
// ✅ 불변 DTO - API 응답
public class TodoResponse {
    private final Long id;
    private final String title;
    private final boolean completed;
    private final LocalDateTime createdAt;
    
    public TodoResponse(Long id, String title, boolean completed, LocalDateTime createdAt) {
        this.id = id;
        this.title = title;
        this.completed = completed;
        this.createdAt = createdAt;
    }
    
    // getter만 있음
    public Long getId() { return id; }
    public String getTitle() { return title; }
    public boolean isCompleted() { return completed; }
    public LocalDateTime getCreatedAt() { return createdAt; }
    
    // setter 없음!
}

// ✅ 불변 VO (Value Object)
public class TodoTitle {
    private final String value;
    
    public TodoTitle(String value) {
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException("제목은 필수입니다");
        }
        if (value.length() > 100) {
            throw new IllegalArgumentException("제목은 100자 이하여야 합니다");
        }
        this.value = value;
    }
    
    public String getValue() { return value; }
    
    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        TodoTitle todoTitle = (TodoTitle) o;
        return Objects.equals(value, todoTitle.value);
    }
}
```
```java
// ✅ Service에서 사용
@Service
public class TodoService {
    private final TodoRepository todoRepository;
    
    // 불변 DTO 반환
    public TodoResponse getTodo(Long id) {
        Todo todo = todoRepository.findById(id)
            .orElseThrow(() -> new NoSuchElementException("할 일을 찾을 수 없습니다"));
        
        // Entity → 불변 DTO 변환
        return new TodoResponse(
            todo.getId(),
            todo.getTitle(),
            todo.isCompleted(),
            todo.getCreatedAt()
        );
    }
    
    // Entity는 내부에서 변경
    public void completeTodo(Long id) {
        Todo todo = todoRepository.findById(id)
            .orElseThrow(() -> new NoSuchElementException("할 일을 찾을 수 없습니다"));
        
        todo.complete();  // Entity는 가변 - 상태 변경
        // 변경 감지로 자동 저장 (dirty checking)
    }
}
```
#### IF) TO-DO 프로젝트에서 불변 객체 어디에?
1. API 응답 DTO (`TodoResponse`, `TodoListResponse`)
2.Value Object (`TodoTitle`, `UserId`, `Email`)
3. 설정 객체 (`PaginationConfig`, `AppProperties`)
4. 이벤트 객체 (`TodoCompletedEvent`)

> 그러니까 값을 **표현하는 객체**, **동작하는 객체**를 불변 객체로 쓸 수 있음

# ITEM 18 상속보다는 컴포지션을 사용하라
- 상속은 코드 재사용 수단이지만 항상 최선은 아님
- 여기에서 '상속'은 **클래스가 다른 클래스를 확장하는 구현 상속** 의미 (인터페이스 상속 X)

- **상속은 캡슐화를 깨뜨림** => 상위 클래스가 어떻게 구현되느냐에 따라 하위 클래스의 동작에 이상이 생길 수 있음

그러면 상속 써서 문제 생길 여지를 준다는 거니까, 이것의 대안책은 무엇일까?
> **기존 클래스를 확장하지 않고, 새로운 클래스를 만들고 private 필드로 기존 클래스의 인스턴스를 참조하게 하자**

- **컴포지션**(Composition)
	- 기존 클래스가 새로운 클래스의 구성요소로 쓰인다는 뜻
    - 전달(forwarding): 새 클래스의 인스턴스 메서드들이 기존 클래스의 대응하는 메서드를 호출해 결과 반환
    - 전달 메서드(forwarding method): 새 클래스의 메서드들
    => 이것을 통해 새로운 클래스는 기존 클래스의 내부 구현 방식의 영향에서 벗어나고, 기존 클래스에 새로운 메서드가 추가되어도 영향 받지 않음


### 예시: 알림 기능이 있는 할 일 관리
#### 상속
- `ArrayList.addAll()`이 내부적으로 `add()`를 호출하는지 몰랐음
- 상위 클래스(`ArrayList`)의 구현 세부사항에 의존하게 됨
- 상위 클래스가 바뀌면 하위 클래스가 깨짐
```java
// ❌ 상속 방식 - 문제 발생
public class ArrayList<E> {
    private Object[] elements;
    private int size = 0;
    
    public boolean add(E e) {
        elements[size++] = e;
        return true;
    }
    
    public boolean addAll(Collection<? extends E> c) {
        for (E e : c) {
            add(e);  // 내부적으로 add() 호출
        }
        return true;
    }
}

// 알림 기능 추가 - 상속 사용
public class NotifyingTodoList extends ArrayList<Todo> {
    private final NotificationService notificationService;
    
    public NotifyingTodoList(NotificationService notificationService) {
        this.notificationService = notificationService;
    }
    
    @Override
    public boolean add(Todo todo) {
        boolean result = super.add(todo);
        notificationService.notify("할 일 추가: " + todo.getTitle());  // 알림 1번
        return result;
    }
    
    @Override
    public boolean addAll(Collection<? extends Todo> todos) {
        boolean result = super.addAll(todos);  // 내부적으로 add()를 호출함!
        notificationService.notify("여러 할 일 추가: " + todos.size() + "개");  // 알림 1번
        return result;
    }
}

// 사용 시 문제 발생
NotifyingTodoList todoList = new NotifyingTodoList(notificationService);
todoList.addAll(Arrays.asList(todo1, todo2, todo3));

// 결과: 알림이 5번 울림!
// "할 일 추가: todo1"  ← add()에서
// "할 일 추가: todo2"  ← add()에서
// "할 일 추가: todo3"  ← add()에서
// "여러 할 일 추가: 3개"  ← addAll()에서
// 의도한 건 addAll 알림 1번인데, add 알림이 3번 더 울림!
```
#### 컴포지션
**상속 방식의 문제**:
- `super.addAll()`이 내부적으로 `add()`를 호출 → 알림 중복
- `ArrayList` 구현이 바뀌면 `NotifyingTodoList`도 깨짐
- `ArrayList`의 모든 메서드(100개 이상)가 노출됨

**컴포지션 방식의 장점**:
- `todos.addAll()`은 우리가 만든 `add()`와 무관 → 알림 정확히 1번
- `ArrayList` 구현이 바뀌어도 영향 없음
- 필요한 메서드만 선택적으로 노출 가능
- 나중에 `ArrayList` 대신 `LinkedList`로 바꾸기 쉬움

5. 추상 클래스와 상속 지양의 관계
```java
// ✅ 컴포지션 방식 - 안전함
public class NotifyingTodoList {
    private final List<Todo> todos;  // 상속이 아닌 포함
    private final NotificationService notificationService;
    
    public NotifyingTodoList(NotificationService notificationService) {
        this.todos = new ArrayList<>();  // 구현체는 언제든 바꿀 수 있음
        this.notificationService = notificationService;
    }
    
    public boolean add(Todo todo) {
        boolean result = todos.add(todo);  // 위임
        notificationService.notify("할 일 추가: " + todo.getTitle());
        return result;
    }
    
    public boolean addAll(Collection<? extends Todo> newTodos) {
        boolean result = todos.addAll(newTodos);  // 위임
        notificationService.notify("여러 할 일 추가: " + newTodos.size() + "개");
        // ArrayList가 내부적으로 add()를 호출하든 말든 상관없음!
        return result;
    }
    
    // 필요한 메서드만 노출
    public Todo get(int index) {
        return todos.get(index);
    }
    
    public int size() {
        return todos.size();
    }
}

// 사용 시 정상 동작
NotifyingTodoList todoList = new NotifyingTodoList(notificationService);
todoList.addAll(Arrays.asList(todo1, todo2, todo3));

// 결과: 알림 1번만 울림
// "여러 할 일 추가: 3개"  ← 의도대로!
```
    
# ITEM 19 상속을 고려해 설계하고 문서화하라, 그러지 않았다며 상속을 금지하라상속을 고려해 설계하고 문서화하라, 그러지 않았다며 상속을 금지하라

### 상속을 고려한 설계와 문서화?

1. 먼저 메서드를 재정의하면 무슨 일이 일어나는지 정확히 정리하여 문서화해야 함
- **상속용 클래스는 재정의할 수 있는 메서드들을 내부적으로 어떻게 이용하는지(자기사용) 문서로 남겨야 함**
2. 일단 문서화한 것은 그 클래스가 쓰이는 한 반드시 지켜야 함
- 지키지 않으면 그 내부 구현 방식을 믿고 활용하던 하위 클래스가 오동작할 수 있음
3. 다른 사람이 효율 좋은 하위 클래스를 만들 수 있게 일부 메서드들을 protected로 제공해야 할 수 있음

**결론**
- 개귀찮으니까 무조건 상속을 써야만 하는 이유가 없다면 상속을 쓰지 말자

# ITEM 20 추상 클래스보다는 인터페이스를 우선하라
> **요약**
- 자바의 다중 구현 수단: **추상 클래스** VS **인터페이스**
- 인터페이스가 더 유연하고, 기존 클래스에 쉽게 적용 가능
- **믹스인(mixin), 디폴트 메서드, 골격 구현(skeletal implementation)** 이해 필요

| 비교 항목      | 추상 클래스          | 인터페이스              |
| ---------- | --------------- | ------------------ |
| 상속         | 한 번만 가능         | 여러 개 동시에 가능        |
| 기존 클래스에 적용 | 거의 불가능          | implements 한 줄이면 됨 |
| 필드         | 인스턴스 변수 가질 수 있음 | 상수만 가능             |
| 목적         | 공통된 “기능 구현 공유”  | 공통된 “규칙 정의”        |

### 핵심 개념
#### 믹스인(Mixin)
- 클래스에 선택적 기능을 "섞는" 인터페이스
- ex) `Comparable`, `Serializable`, `Cloneable`
#### 골격 구현(Skeletal Implementation)
- 인터페이스의 기본 구현을 제공하는 추상 클래스
- ex) `AbstractList`, `AbstractMap`, `AbstractSet`
#### 템플릿 메서드 패턴과 유사
- 템플릿 메서드처럼 공통 로직을 상위 추상 클래스가 제공

# ITEM 23 태그 달린 클래스보다는 클래스 계층 구조를 활용하라
### 태그 달린 클래스?
- 하나의 클래스가 여러 역할을 동시에 하는 형태
```java
class Shape {
    enum Type { CIRCLE, RECTANGLE }
    Type type;
    double radius;
    double width, height;

    double area() {
        if (type == Type.CIRCLE) return Math.PI * radius * radius;
        else return width * height;
    }
}
```
- `Shape` 안에 원과 사각형을 둘 다 넣음 => 필요 없는 변수 생기고, 코드 복잡해지고, 실수하기 좋아짐

### 좋은 설계: 역할을 분리해서 계층 구조로
-> 새로운 도형을 추가할 때도 기존 코드를 건드리지 않아도 됨
```java
abstract class Shape {
    abstract double area();
}

class Circle extends Shape {
    double radius;
    double area() { return Math.PI * radius * radius; }
}

class Rectangle extends Shape {
    double width, height;
    double area() { return width * height; }
}
```

### 결론
- "태그(enum) + switch"로 구분하는 구조는 유지보수 지옥
- **다형성**으로 바꾸면 구조가 훨씬 깔끔해지고 오류가 줄어든다

# ITEM 24 멤버 클래스는 되도록 static으로 만들라
### 중첩 클래스 
```java
class Outer {
    class Inner { }         // 비정적 멤버 클래스
    static class StaticInner { } // 정적 멤버 클래스
}
```
| 구분        | 비정적 멤버 클래스    | 정적 멤버 클래스   |
| --------- | ------------- | ----------- |
| 외부 클래스 참조 | 있음            | 없음          |
| 메모리       | 더 많이 사용       | 효율적         |
| 사용 목적     | 외부 객체와 연결된 동작 | 독립적인 도우미 역할 |


### 문제점
- 비정적 멤버 클래스는 외부 객체를 자동으로 참조 => 실수로 `static`을 빼면 **메모리 누수** 생길 수 있음

### 권장
- **외부 인스턴스가 꼭 필요할 때만 비정적**
- **나머지는 다 static**
