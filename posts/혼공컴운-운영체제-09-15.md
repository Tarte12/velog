# CH09 운영 체제 시작하기

## 운영체제
1. 운영체제: 응용 프로그램에 필요한 지원 할당, 응용 프로그램이 올바르게 실행되도록 관리
2. 커널 영역: 운영체제가 적재되는 공간
3. 사용자 영역: 커널 영역을 제외한 응용 프로그램이 적재되는 공간

## 커널
1. 커널: 운영체제의 핵심 서비스를 담당하는 부분
2. 운영체제가 제공하는 서비스 중 커널에 포함되지 않는 서비스 존재
- UI(사용자 인터페이스) : GUI(그래픽), CLI(커맨드라인)
- UI는 운영체제가 제공하지만 컴퓨터와 상호작용 위한 통로로만 작용

## 이중 모드
- 운영체제는 사용자가 실행하는 응용 프로그램이 하드웨어 자원에 직접 접근하는 것을 막아 자원을 보호함
- 응용 프로그램이 자원에 접근하려고 할 때 오직 자신을 통해서만 접근 가능하도록 함

**이중모드**: 응용 프로그램이 자원에 접근하기 위해 운영체제에 도움을 요청, 운영체제가 대신 자원에 접근해 요청 작업을 수행 => 운영체제의 역할이 이중 모드로 구현됨
- CPU가 명령어를 실행한 모드를 사용자 모드와 커널 모드로 구분하는 방식

**사용자 모드** 
- 운영체제 서비스 제공받을 수 없는 실행 모드
- 커널 영역 코드 실행 X
- 일반 응용 프로그램

**커널 모드**
- 운영체제 서비스 제공받을 수 있는 실행 모드
- 커널 영역 코드 실행 가능
- CPU가 커널 모드로 명령어를 실행 => 자원에 접근하는 명령어를 비롯한 모든 명령어 실행 가능

**시스템 호출(system call)**
- 운영체제 서비스를 제공받기 위한 요청
- CPU가 시스템 호출을 처리하는 순서는 인터럽트 처리 순서와 비슷함가 시스템 호출을 처리하는 순서는 인터럽트 처리 순서와 비슷함
- 시스템 호출 발생 명령어 실행
- CPU는 지금까지의 작업을 백업
- 커널 영역 내 시스템 호출 수행 코드 실행
- 다시 기존에 실행하던 응용 프로그램으로 복귀

> system call은 프로그램에 굉장히 많이 사용되어 => 구조를 개선하는 것만으로도 컴퓨터 동작 속도가 많이 올라감

## 운영체제 핵심 서비스
### 1. 프로세스 관리
- 프로세스: 실행 중인 프로그램
- 하나의 CPU는 한 번에 하나의 프로세스만 실행 => CPU는 프로세스들을 조금씩 번갈아 실행
### 2. 자원 접근 및 할당
- 운영체제가 프로세스들이 사용할 자원에 접근하고 조작하여 프로세스에 자원을 할당함

#### CPU
- CPU 스케줄링: 프로세스들에 공정하게 CPU를 할당하기 위해 어떤 프로세스로부터 CPU를 이용하게 할 것인지, 얼마나 오래 CPU를 이용하게 할 것인지 결정하는 것
#### 메모리
- 새로운 프로세스가 적재될 때마다 어느 주소에 적재할 건지 결정
#### 입출력 장치
- 인터럽트 서비스 루틴을 제공해 입출력 작업 수행

### 3. 파일 시스템 관리
- 운영체제가 보조기억장치 속 데이터를 어떻게 파일과 디렉터리로 관리하는지

# CH10 프로세스 & 스레드

## 프로세스
- 실행 전 프로그램은 그저 보조기억장치에 있는 데이터 덩어리
- 보조기억장치에 저장된 프로그램을 메모리에 적재하고 실행하면 프로세스

### 프로세스 종류
- 포그라운드 프로세스: 사용자가 볼 수 있는 공간에서 실행되는 프로세스
=> 카카오톡, 메모장 등
- 백그라운드 프로세스: 사용자가 보지 못하는 뒷편에서 실행되는 프로세스
=> 백신 프로그램, 그래픽 드라이버 등
- 데몬(유닉스): 백그라운드에서 실행되는 프로그램으로, 사용자가 직접 제어하지 않고 백그라운드를 돌면서 여러 작업을 하는 프로그램
- 서비스(윈도우): 백그라운드에서 실행되는 응용 프로그램으로, 데몬과 비슷함
> 데몬 VS 서비스
- 데몬은 주로 서버에서 사용 => 시스템에서 독립적으로 실행
- 서비스는 주로 다른 프로그램이나 서비스를 지원하기 위해 사용 => 모니터링, 제어 등의 역할 지원에 초점
- but 혼용되어 사용되는 편

### 프로세스 제어 블록(PCB)
- 프로세스는 한정된 시간만큼 CPU를 이용하고, 시간이 끝나면 다시 차례를 기다리는 것을 반복
- 따라서 운영체제가 프로세스 실행 순서를 관리하고, 프로세스에 CPU를 비롯한 자원을 배분
- PCB는 **프로세스와 관련된 정보를 저장**하는 자료 구조
- 해당 프로세스를 식별하기 위한 정보 저장
- 커널 영역에 생성- 커널 영역에 생성
> 왜 커널 영역에 생성되는지? => 운영체제의 내부 자료구조라서 운영체제가 직접 접근하고 수정할 수 있어야 함

#### PCB에 담기는 정보
**프로세스 ID**: 특정 프로세스 식별 위한 고유 번호
**레지스터 값**: 해당 프로세스가 실행하며 사용했던 프로그램 카운터를 비롯한 레지스터 값 저장
**프로세스 상태**: 현재 프로세스 상태
**CPU 스케줄링 정보**: CPU 할당 받을 순서
**메모리 관리 정보**: 어느 주소에 저장되어 있는지
**사용한 파일과 입출력 장치 목록**: 어떤 입출력장치가 할당되어 있는지, 어떤 파일을 열었는지

### 문맥교환
- 문맥: 하나의 프로세스 수행 재개 위해 기억해야 할 정보
- 문맥 교환: 기존 프로세스 문맥을 PCB에 백업하고, 새로운 프로세스를 실행하기 위해 PCB로부터 새로운 프로세스를 실행하는 것

### 프로세스 메모리 영역
- 프로세스 생성 => 커널 영역에 PCB 생성
- 프로세스는 사용자 영역에 어떻게 배치되는가?

**코드 영역**
- 실행할 수 있는 코드(기계어) 저장
- 정적 할당 영역: 쓰기가 금지된 읽기 전용 공간, 크기가 변하지 않음
**데이터 영역**
- 프로그램이 실행되는 동안 유지할 데이터가 저장되는 공간
- 대표적인 예시: 전역 변수
- 정적 할당 영역: 크기가 변하지 않음
> 메모리 자체가 RAM에 존재하므로 휘발성인데, 왜 데이터 영역만 구분해서 프로그램이 실행되는 동안 유지할 데이터가 저장되는 공간이라고 했을까?
> **데이터 영역**: 여기 저장된 데이터는 **실행 중 전체 기간 유지**
> **스택, 힙**: **실행 중에도 생명 주기가 더 짧고 동적으로 변함**

**힙 영역**
- 프로그래머가 직접 할당할 수 있는 저장 공간
- 동적 할당 영역: 크기가 실시간으로 변함
- 프로그래밍 과정 중 힙 영역에 메모리 공간을 할당했다면, 언젠가는 해당 공간을 반환해야 함
- 메모리 누수: 메모리 공간을 반환하지 않는다면 할당한 공간은 메모리 내에 계속 남아 낭비를 초래함
> CG가 이 역할을 하는 거 아닌가? => 맞음 (힙 영역 메모리 반환과 관련된 핵심 기술)
> JAVA는 자동이고 C/C++은 수동이긴 한데 어쨌든 해재를 해 주긴 해야 하니까 개념적으로는 설명하는 느낌인 듯?

**스택 영역**
- 데이터를 일시적으로 저장하는 공간으로 잠깐 쓰다가 버릴 값들이 저장되는 공간
- 매개 변수, 지역 변수 같은 거
- 동적 할당 영역

일반적으로 힙 영역을 메모리에서 낮은 주소에서 높은 주소로 할당, 스택 영역은 높은 주소에서 낮은 주소로 할당
> 왜? => 메모리 공간을 최대한 유연하게 활용하기 위한 전략
> 서로 충돌하지 않도록 메모리를 효율적으로 사용하기 위해
> 만약 같은 방향으로 자라면
> - 사이에 고정된 경계 있어야 함
> - 하지만 어느쪽이 더 많이 필요할지 모름: 메모리 낭비 or 오버플로우 위험 증가

** 메모리 구조 기본 **
```
주소 ↓ (낮음)

[ 코드 영역 ]           ← 프로그램의 기계어
[ 데이터 영역 ]         ← 전역/정적 변수
[ 힙 영역 ]            ↑ ↑ ↑ 동적으로 할당되는 영역 (malloc, new 등)
...
[ 스택 영역 ]          ↓ ↓ ↓ 함수 호출/지역 변수 (call stack)

주소 ↑ (높음)

```
> 힙: 낮은 주소 -> 높은 주소
> malloc(), new 같은 호출로 **필요한 만큼 할당**
> 어떤 데이터가 얼마나 오래 필요할지 알 수 없음
> 밑에서 위로 쌓아올리는 방식이 관리에 유리
> 동적으로 늘어나는 용도

> 스택: 높은 주소 -> 낮은 주소
> 스택은 함수 호출 시 생성되고 리턴 시 제거됨 (LIFO)
> 자동으로 push/pop되며 크기가 빨리 변함
> 위에서 아래로 내려가는 방식이 하드웨어와 OS 입장에서 효율적

## 프로세스 상태 & 계층 구조

### 프로세스 상태
- 컴퓨터를 사용할 때 여러 프로세스들이 빠르게 번갈아 실행되기 때문에, 하나의 프로세스는 여러 상태를 거치며 실행함
![](https://velog.velcdn.com/images/emprimula/post/70444061-f685-4a98-98aa-fec1d5a75241/image.png)

**생성 상태**
- 프로세스 생성 중인 상태
- 이제 막 메모리에 적재되어 PCB를 할당받은 상태
**준비 상태**
- 당장 CPU를 할당받아 실행할 수 있지만, 차례를 기다리는 상태
- 디스패치: 실행 상태로 전환
**실행 상태**
- CPU를 할당받아 실행 중인 상태
- 할당된 일정 시간 동안만 CPU 사용 가능
- 할당된 시간 모두 사용 => 준비 상태
- 실행도중 입출력 장치 사용 => 작업 끝날 때까지 대기 상태
**대기 상태**
- 입출력장치의 작업 기다리는 상태
**종료 상태**
- 프로세스가 종료된 상태
- 프로세스가 종료되면 운영체제는 PCB와 프로세스가 사용한 메모리를 정리

### 프로세스 계층 구조
- 프로세스는 실행 도중 시스템 호출을 통해 다른 프로세스를 생성 가능
- 부모 프로세스: 새 프로세스를 생성한 프로세스
- 자식 프로세스: 부모 프로세스에 의해 생성된 프로세스
- 다른 프로세스라서 PID는 다름
- 많은 운영체제가 프로세스가 프로세스를 낳은 계층적인 구조로 프로세스를 관리함
- 프로세스 계층 구조: 위의 과정을 도표로 그리면 트리 구조가 됨

### 프로세스 생성 기법
- 부모 프로세스를 통해 생성된 자식 프로세스들은 **복제와 옷 갈아입기** 통해 실행
- **fork**: 부모 프로세스가 fork를 통해 자신의 복사본을 자식 프로세스로 생성하고, (자신 프로세스의 복사본을 만드는 시스템 호출)
- **exec**: 만들어진 복사본(자식 프로세스)은 exec를 통해 자신의 메모리 공간을 다른 프로그램으로 교체 (자신의 메모리 공간을 새로운 프로그램으로 덮어쓰는 시스템 호출)
- fork/exec는 시스템 호출
- 자식 프로세스는 부모 프로세스의 복사본이기 때문에 부모 프로세스의 자원들이 자식 프로세스에 상속됨
- 자식 프로세스는 exec 시스템을 호출하여 새로운 프로그램으로 전환
- 코드 영역과 데이터 영역의 내용이 실행할 프로그램의 내용으로 바뀌고 나머지 영역은 초기화됨

>이 부분 정리하면서 헷갈린 부분 다시 정리

| 질문 | 답변 요약 |
|------|-----------|
| system call은 커널에서 실행돼? | ✅ 맞아요. 사용자 프로그램이 요청 → 커널이 실행 |
| fork/exec는 커널이 처리해? | ✅ 맞아요. 커널이 복사하거나 메모리를 교체함 |
| 결과는 메모리에 저장돼? | ✅ 맞아요. 커널이 처리 후 사용자 프로세스 메모리(사용자 영역)에 적재됨 |
| 프로세스는 어떻게 메모리에 있나? | ✅ 하나의 프로세스는 자기만의 메모리 공간을 갖고 있고, 그 안에 코드/데이터/힙/스택 등으로 나뉘어 있음. 각각 따로 있는 게 아니라 프로세스 하나에 포함된 구성 요소임 |


## 스레드
- 프로세스를 구성하는 실행 흐름의 단위

### 프로세스와 스레드
- 전통적인 관점에서 하나의 프로세스는 한번에 하나의 일만 처리
- 단일 스레드 프로세스: 실행의 흐름 단위가 하나
- 스레드는 프로세스 내에서 각기 다른 스레드 ID, 프로그램 카운터 값을 비롯한 레지스터 값, 스택으로 구성되어 있음
- 각자 값을 가지고 있기 때문에 스레드마다 각기 다른 코드 실행 가능
- 스레드들은 실행에 필요한 최소한 정보만 유지한 채 프로세스 자원을 공유하여 실행
- 프로세스 자원을 공유하는 것이 스레드의 핵심
- 스레드의 개념이 도입되면서 하나의 프로세스가 한 번에 여러 일을 동시에 처리할 수 있게 되었음
- 따라서 스레드는 **프로세스를 구성하는 실행 단위**
- 최근 많은 운영체제는 CPU에 처리할 작업을 전달할 때 프로세스가 아닌 스레드 단위로 전달

#### 🏠 하숙집과 하숙생 비유로 이해하는 프로세스와 스레드

| 개념 | 비유 | 설명 |
|------|------|------|
| **프로세스** | 하숙집 | 각 하숙집은 독립된 공간과 자원(방, 부엌, 화장실)을 갖고 있고, 다른 하숙집과는 독립되어 있음. |
| **스레드** | 하숙집에 사는 하숙생 | 같은 하숙집에 사는 사람들은 방도 공유하고, 부엌이나 화장실 같은 자원도 함께 사용함. |

---

#### 💡 하숙집 비유의 장점

- 하숙생들은 **같은 집안 자원(부엌, 화장실 등)을 함께 쓰면서 협력**  
- 하지만 하숙집은 **다른 하숙집과는 독립적**이라 서로 간섭하지 않음  
- 만약 하숙생 중 한 명이 문제를 일으키면 같은 집 안 사람들은 영향을 받지만, 다른 하숙집 사람들은 영향 받지 않음

---

#### ✅ 요약

> 프로세스 = 하숙집 (독립된 공간, 자원)  
> 스레드 = 하숙생 (같은 집 안에서 자원 공유하며 함께 사는 단위)


> 질문: 프로세스가 하나의 프로그램을 뜻한다면, 스레드는 어떤 역할을 하는 걸까?

> 프로세스가 한글, 카카오톡 같은 하나의 프로그램을 뜻하는 거잖아?  
> 그렇다면 프로세스 하나를 실행한다는 건 카카오톡 하나를 실행하는 걸로 느껴지는데,  
> 스레드로 여러 작업이 된다는 말은 잘 감이 안 잡혀.  
> 내가 메시지 전송을 할 때 타인이 동시에 메시지를 나한테 보내는 작업이 가능한 그런 느낌인 걸까?

---

#### 💡 답변: 정확해요! 그게 바로 스레드의 존재 이유입니다

하나의 프로그램을 실행하면 **프로세스**가 만들어집니다.  
예를 들어, 카카오톡을 실행하면 하나의 **카카오톡 프로세스**가 만들어지는 것이죠.

하지만 카카오톡은 단순히 메시지만 주고받는 프로그램이 아니죠?

- 내가 메시지를 입력하고 보내고
- 상대방의 메시지를 실시간으로 받고
- 알림 소리를 울리고
- 이모티콘이 움직이고
- UI 화면이 계속 갱신되고...

이 모든 것을 **동시에 처리**하려면 어떻게 해야 할까요?

바로 그럴 때 **스레드**가 등장합니다.  
**스레드는 프로세스 내에서 동시에 여러 작업을 실행하기 위한 최소 단위**입니다.

---

#### 📱 카카오톡을 예로 든 스레드 구조

| 기능 | 설명 | 해당 스레드의 역할 |
|------|------|--------------------|
| 메시지 입력 및 전송 | 사용자의 입력을 받고 서버로 전송 | **전송 스레드** |
| 메시지 수신 | 서버로부터 도착한 메시지를 수신하고 출력 | **수신 스레드** |
| 알림 처리 | 메시지 도착 시 소리/진동 알림 | **알림 스레드** |
| 애니메이션 처리 | 이모티콘 움직임, UI 전환 등 시각적 효과 | **UI 스레드** |

---

#### 🧠 만약 스레드가 없다면?

- 메시지를 입력하고 **보낸 다음에야** 메시지를 받을 수 있음  
- 알림이 울리려면 메시지 수신이 끝날 때까지 기다려야 함  
- 이모티콘 애니메이션은 멈춰 있거나 끊김

즉, **모든 작업이 순차적**으로 실행되어  
사용자 경험이 **엄청 불편**해지게 됩니다.

---

#### ✅ 요약

> - 하나의 프로그램 = 하나의 **프로세스**
> - 동시에 여러 작업을 수행하기 위해 필요한 실행 단위 = **스레드**
> - 메시지 전송과 수신을 동시에 처리할 수 있는 이유가 바로 스레드 덕분!

### 멀티프로세스와 멀티스레드
- 멀티프로세스: 여러 프로세스 동시 실행
- 멀티스레드: 여러 스레드로 프로세스 동시 실행

- 프로세스 단위로는 서로 자원 공유 X
- 스레드 단위로는 같은 프로세스 자원 공유 O

- 프로세스 두 개를 동시 실행 => 프로세스의 모든 자원이 복제되어 메모리에 적재되는데 메모리 낭비임
- 스레드는 같은 프로세스 내의 같은 자원을 공유하기 때문에, 여러 프로세스를 병행 실행하는 것보다 메모리를 효율적으로 사용 가능
- but 하나의 스레드에 문제 생기면 프로세스 전체에 문제 생길 수 있음

# CH11 CPU 스케줄링
## CPU 스케줄링
- CPU 스케줄링: 운영체제가 프로세스들에게 공정하고 합리적으로 CPU 자원을 배분하는 것자원을 배분하는 것
### 프로세스 우선순위
- 우선순위 높은 프로세스: 빨리 처리해야 하는 프로세스 (EX. 입출력 작업이 많은 프로세스)
- 대부분의 프로세스들은 CPU와 입출력장치를 모두 사용하여 실행
- 프로세스는 실행 상태와 대기 상태를 반복하며 실행됨
- 프로세스 종류마다 입출력장치를 이용하는 시간과 CPU를 이용하는 시ㅣ간의 양에 차이 존재

- 입출력 집중 프로세스: 입출력 작업이 많은 프로세스
=> 실행 상태보다 대기 상태에 더 많이 머무름
- CPU 집중 프로세스: CPU 작업이 많은 프로세스
=> 대기 상태보다 실행 상태에 더 많이 머무름

**이런 차이 때문에 프로세스의 중요도에 맞게 운영체제가 우선순위 부여**

### 스케줄링 큐: 대기줄
- 운영체제는 다음 프로세스를 빠르게 찾기 위해 프로세스들이 줄을 서서 기다리길 요구
- 스케줄링 큐로 이 줄을 구현하고 관리
- 운영체제가 관리하는 대부분의 자원을 큐로 관리
- 대표적으로 준비 큐, 대기 큐

**준비 큐**
- CPU를 이용하고 싶은 프로세스들이 서는 줄
**대기 큐**
- 입출력장치를 이용하기 위해 대기 상태에 접어든 프로세스들이 서는 줄

- 운영체제는 PCB들이 큐에 삽입된 순서대로 프로세스들을 꺼내서 실행하지만, 만약 우선순위가 높은 프로세스가 있다면 먼저 실행

### 선점형과 비선점형 스케줄링

- 선점형 스케줄링: 프로세스가 CPU를 비롯한 자원을 사용하고 있더라도, 운영체제가 프로세스로부터 자원을 강제로 빼앗아 프로세스에 할당할 수 있는 스케줄링 방식
- 비선점형 스케줄링: 하나의 프로세스가 자원을 사용하고 있다면, 그 프로세스가 종료되거나 스스로 대기 상태에 접어들기 전까진 다른 프로세스가 끼어들 수 없는 스케줄링 방식태에 접어들기 전까진 다른 프로세스가 끼어들 수 없는 스케줄링 방식

## CPU 스케줄링 알고리즘

### 비선점형
#### 선입 선처리 스케줄링(FCFS)
- 준비된 큐에 삽입된 순서대로 프로세스를 처리하는 방식
- CPU를 먼저 요청한 프로세스부터 할당
- 호위 효과: CPU를 오래 사용하는 프로세스가 먼저 도착했을 때 다른 프로세스들이 무작정 기다리는 현상
#### 최단 작업 우선 스케줄링(SJF)
- 준비 큐에 삽입된 프로세스들 중 CPU 이용 시간의 길이가 가장 짧은 프로세스부터 실행하는 방식
### 선점형
#### 라운드 로빈 스케줄링(RR)
- FCFS에 각 프로세스가 CPU를 사용할 수 있는 정해진 시간을 의미하는 타임 슬라이스라는 개념이 더해진 스케줄링 방식
- 정해진 타임 슬라이스만큼의 시간 동안 돌아가며 CPU를 이용하는 방식
- 타임 슬리이스 크기를 잘 정하는 것이 중요
#### 최소 잔여 시간 우선 스케줄링(SRT)
- SJF + RR
- 프로세스들은 정해진 타임 슬라이스만큼 CPU를 사용하되, CPU를 사용할 다음 프로세스로는 남아있는 작업 시간이 가장 적은 프로세스가 선택됨
#### 우선순위 스케줄링
- 프로세스들에 우선순위를 부여하고, 가장 높은 우선순위를 가진 프로세스부터 실행
- 기아 현상: 우선순위가 낮은 프로세스의 실행이 계속 지연되는 현상
- 에이징: 기아 현상을 막는 대표적 기법 => 오래 대기한 프로세스의 우선순위를 점차 높이는 방식
#### 다단계 큐 스케줄링
- 우선순위별로 준비큐를 여러 개 사용하는 방식
- 우선순위가 가장 높은 큐에 있는 프로세스 먼저 처리 => 우선순위가 가장 높은 큐가 비면 다음 우선순위 큐에 있는 프로세스를 처리
- 큐 단위로 타임 슬라이스를 여러 개 지정할 수 있고, 큐마다 다른 스케줄링 알고리즘 사용 가능
#### 다단계 피드백 큐 스케줄링
- 다단계 큐 스케줄링의 발전된 형태
- 다단계 큐 스케줄링에선 프로세스들이 큐 사이 이동 불가
- 다단계 피드백 큐 스케줄링은 너무 오래 기다리고 있는 프로세스를 점차 높은 우선순위 큐로 이동시킬 수 있음

# CH 12 프로세스 동기화
## 동기화
- 협력하여 실행되는 프로세스들은 실행 순서와 자원의 일관성을 보장해야 하기 때문에 동기화되어야 함
### 동기화의 의미
- 협력적으로 실행되는 프로세스들은 올바르게 실행되기 위해 동기화 필수
- 프로세스 동기화: 프로세스 수행 시기를 맞추는 것
- 프로세스들 사이의 수행 시기를 맞추는 것은 크게 두 가지
**실행 순서 제어**: 프로세스들을 올바른 순서대로 대기
**상호 배제**: 동시에 접근해서 안 되는 자원에 하나의 프로세스만 접근하게 하기

=> 동기화는 실행 순서 제어를 위한 동기화와 상호 배제를 위한 동기화가 있음

**실행 순서 제어를 위한 동기화**: 
- 동시에 실행되는 프로세스들을 올바른 순서대로 실행하는 것이 첫 번째 프로세스 동기화
**상호 배제를 위한 동기화**
- 상호 배제는 공유가 불가능한 자원의 동시 사용을 피하기 위해 사용하는 알고리즘

### 생산자와 소비자 문제
- 물건을 계속 생산하는 생산자와 생산된 물건을 소비하는 소비자로 이뤄짐
- 생산자와 소비자는 '총합'이라는 데이터를 공유
- 생산자는 버퍼에 물건을 넣은 후 총합을 1을 증가시킴
- 소비자는 버퍼에 물건을 빼낸 후 총합을 1을 감소시킴
- 이 프로세스를 각 1000,000번 동시에 실행시켰을 때
- 총합이 10이어야 하지만 다른 수가 나오거나 오류가 발생하기도 함
=> 이것은 생산자 프로세스와 소비자 프로세스가 동기화되지 않아 발생
- 각 프로세스가 작업이 끝나기 전에 총합을 수정하였기 때문
- 동시에 접근하면 안 되는 자원에 동시에 접근하였기 때문

### 공유 자원과 임계 구역
- 공유 자원: 생산자와 소비자 문제에서 총합 같은 여러 개의 프로세스가 공동으로 두고 사용하는 자원
- 전역 변수, 파일, 입출력장치, 보조기억장치 다 가능
- 임계 구역: 공유 자원 중 두 개 이상의 프로세스를 동시에 실행하면 문제가 발생하는 자원이 있는데 이에 접근하는 코드 영역
- 두 개 이상의 프로세스가 임계 구역에 진입하려고 하면 하나는 대기해야 함
- 레이스 컨디션: 잘못된 실행으로 인해 여러 프로세스가 동시다발적으로 임계 구역의 코드를 실행하여 문제가 발생하는 경우
- 데이터의 일관성이 깨지는 문제 발생

**운영체제가 임계 구역 문제를 세 가지 원칙으로 해결**
1. 상호 배제: 한 프로세스가 임계 구역에 진입했다면 다른 프로세스는 임계 구역에 들어올 수 없음
2. 진행: 임계 구역에 어떤 프로세스도 진입하지 않았다면, 임계 구역에 진입하고자 하는 프로세스는 들어갈 수 있어야 함
3. 유한 대기: 한 프로세스가 임계 구역에 진입하고 싶다면 그 프로세는 언젠가 임계 구역에 들어올 수 있어야 함

## 동기화 기법
### 뮤텍스 락
- 동시에 접근해서 안 되는 자원에 동시에 접근하지 않도록 만드는 도구
- 상호 배제를 위함
- 자물쇠 기능을 코드로 구현(탈의실 안에 사람이 있는지 없는지 자물쇠를 보고 판단)
- 하나의 전역 변수와 두 개의 함수로 구현 가능
1. 전역 변수 lock: 자물쇠 역할로 임계 구역이 감기면 true, 열렸으면 false
2. acquire 함수: 임계 구역을 잠그는 역할로 프로세스가 임계 구역에 직입하기 전에 호출하는 함수
- 만약 임계 구역이 잠겼다면 열릴 때까지 반복적으로 확인
- 열려 있다면 임계 구역을 닫는 역할
3. release 함수: 임계 구역의 잠금을 해제하는 역할로 작업이 끝나고 호출하는 함수
- 현재 잠긴 입계 구역을 열어 주는 함수
- acquire 함수는 임계 구역이 잠겨있을 때 반복적으로 프로세스는 lock을 확인하는데 이 대기 방식을 바쁜 대기라고 함

### 세마포
- 뮤텍스 락과 비슷하지만 더 일반화된 동기화 도구
- 공유 자원이 여러 개 있을 때도 적용 간으
- 탈의실 갯수가 여러 개로 늘어난 상태
- 프로세스는 임계 구역 앞에서 멈춤 신호를 받으면 기다리고, 가도 좋다는 신호를 받으면 임계 구역에 들어감
- 구현
1. 전역 변수 S: 임계 구역에 진입할 수 있는 프로세스 갯수
2. wait 함수: 임계 구역에 들어가도 되는지 기다려야 하는지 가르쳐 주는 함수
- 사용할 수 있는 자원이 없으면 프로세스 상태를 대기로 만들고
- 그 프로세스의 PCB를 세마포를 위한 대기 큐에 넣음
3. signal 함수: 임계 구역 앞에서 기다리는 프로세스에 '이제 가도 좋다고' 신호를 줌
- 대기 중인 프로세스를 대기 큐에서 제거
- 프로세스를 준비상태로 변경하고 준비 큐에 옮김

### 모니터
- 최근에 등장한 동기화 도구로 사용자가 사용하기 편함
- 모니터는 공유 자원과 공유 자원에 접근하기 위한 인터페이스를 묶어 관리
- 프로세스는 반드시 인터페이스를 통해서만 공유 자원에 접근하도록

=> 모니터는 공유 자원을 다루는 인터페이스에 접근하기 위한 큐를 만들고. 모니터 안에 항상 하나의 프로세스만 들어오게 하여 상호 배제를 위한 동기화를 ㅈ공

- 실행 순서 제어를 위한 동기화도 제공 => 조건 변수
1. 특정 프로세스가 아직 실행할 조건이 되지 않았을 때 wait로 실행 중단
2. 특정 프로세스가 실행될 조건이 충족했을 때 sigmal을 통해 실행 재개

# CH 13 교착 상태
## 교착 상태
- 두 개 이상의 프로세스가 각자 가지고 있는 자원을 무작정 기다린다면 그 어떤 프로세스도 더 이상 진행할 수 없는 교착 상태가 됨

### 식사하는 철학자 문제
![](https://velog.velcdn.com/images/emprimula/post/4150cc1b-fbcb-4d09-971b-fd8a61f16a94/image.png)
1. 계속 생각하다가 왼쪽 포크가 사용 가능하면 집어든다
2. 계속 생각하다가 오른쪽 포크가 사용 가능하면 집어든다
3. 왼쪽, 오른쪽 포크를 모두 집어들면 정해진 시간 동안 식사를 한다
4. 식사 시간이 끝나면 오른쪽 포크를 내려놓는다
5. 오른쪽 포크를 내려놓은 뒤 왼쪽 포크를 내려놓는다
6. 1번부터 반복

- 한두 명의 철학자가 식사할 땐 문제가 없지만 모든 철학자가 동시에 포크를 집어 식사를 하면 어떤 철학자도 식사를 할 수 없고 영원히 생각만 하는 상황이 발생할 수 있음

- 교착 상태: 일어나지 않을 사건을 기다리며 진행이 멈춰 버리는 현상

- 철학자는 프로세스/스레드, 포크는 자원, 생각하는 행위는 자원을 기다리는 것에 빗댈 수 있음
- 포크는 한번에 하나의 프로세스/스레드만 접근할 수 있으니 임계 구역

- 해결법 
1. 교착 상태가 발생했을 떄의 상황을 정확히 표현
2. 교착 상태가 일어나는 근본적인 원인 찾기

### 자원 할당 그래프
- 교착 상태는 자원 할당 그래프를 통해 단순하게 표현 가능
- 어떤 프로세스가 어떤 자원을 사용하고 어떤 프로세스가 어떤 자원을 기다리고 있는지 표현하는 간단한 그래프

**자원 할당 그래프 그리는 법**
1. 프로세스는 원, 자원의 종류는 사각형
2. 사용할 수 있는 자원의 갯수는 자원 사각형 내에 점으로 표현
3. 프로세스가 어떤 자원을 할당받아 사용 중이라면 자원에서 프로세스를 향해 화살표
4. 프로세스가 어떤 자원을 기다리고 있다면 프로세스에서 자원으로 화살표

### 교착 상태 발생 조건
- 상호 배제: 한 프로세스가 사용하는 자원을 다른 프로세스가 사용할 수 없을 때
- 점유와 대기: 자원을 할당받은 상태에서 다른 자원을 할당받기를 기다리는 상태
- 비선점: 어떤 프로세스도 다른 프로세스의 자원을 강제로 뺏을 수 없을 때
- 원형 대기: 자원 할당 그래프가 원의 형태로 그려질 때

## 교착 상태 해결 방법: 예방, 회피, 검출 후 회복
### 교착 상태 예방
- 교착 상태 필요 조건 네 가지 중 하나를 충족하게 못하게 하는 것
**상호 배제 제외**
- 모든 자원을 공유 가능하게 하겠다
- 현실적으로 어려움
**점유와 대기 제외**
- 점유와 대기를 없애면 특정 프로세스에 자원을 몰빵하거나 아예 안 주거나
- 자원의 활용률이 낮아질 수 있음
- 기야 현상 야기: 자원을 많이 사용하는 프로세스는 자원을 적게 사용하는 프로세스에 비해 동시에 자원을 사용할 타이밍 확보가 어려움
**비선점 조건 제외**
- 자원을 이용 중인 프로세스로부터 해당 자원 뺏을 수 있음
- 일부 자원엔 효과적이지만 범용성이 떨어짐
**원형 대기 조건 제외**
- 모든 자원에 번호를 붙이고 오름차순으로 자원을 할당
- 이 행위가 간단하지 않고 활용률 떨어질 수 있음
### 교착 상태 회피
- 교착 상태가 발생하지 않을 정도로만 조심조심 자원을 할당
- 교착 상태를 한정된 자원의 무분별한 할당으로 인해 발생하는 문제로 간주

- 프로세스들이 배분할 수 있는 자원의 양을 고려해 교착 상태가 발생하지 않을 정도로만 자원을 배분
**안전 상태**: 교착 상태가 발생하지 않고 모든 프로세스가 정상적으로 자원을 할당받고 종료될 수 있는 상태
**불안전 상태**: 교착 상태가 발생할 수 있는 상황

- 안전 순서열: 교착 상태 없이 안전하게 프로세스들에 자원을 할당할 수 있는 순서
- 안전 상태: 안전 순서열대로
- 불안전 상태: 안전 순서열이 없는 상황

### 교착 상태 검출 후 회복
- 교착 상태 발생을 인정하고 사후 조치
**선점을 통한 회복**
- 교착 상태가 해결될 때까지 한 프로세스씩 자원을 몰아주는 방식
- 교착 상태가 해결될 때까지 다른 프로세스로부터 자원을 강제로 빼앗고 한 프로세스에 할당하는 방식
**프로세스 강제 종료를 통한 회복**
- 교착 상태에 놓인 프로세스를 강제 종료하거나
- 교착 상태가 없어질 때까지 한 프로세스씩 강제 종료

# CH 14 가상메모리
## 연속 메모리 할당
- 프로세스들을 메모리에 연속적으로 할당할 때 무엇을 고려해야 하는지
### 스와핑
- 현재 실행되고 있지 않은 프로세스들을 임시로 보조기억장치 일부 영역으로 쫓아내고,
- 그렇게 해서 생긴 메모리 빈 공간에 다른 프로세스를 적재하여 실행하는 방식

**스왑 영역**: 프로세스들이 쫓겨나는 보조기억장칭의 일부 영역
**스왑 아웃**: 현재 실행되지 않은 프로세스가 메모리에서 스왑 영역으로 옮겨지는 것
**스왑 인**: 스왑 영역에 있던 프로세스가 다시 메모리로 옮겨오는 것

### 메모리 할당
**최초 적합**
- 운영체제가 메모리 내에 빈 공간을 순서대로 검색하다가 적재할 수 있는 공간을 발견하면 그 공간에 프로세스를 배치하는 방식
- 검색 최소화 + 빠른 할당
**최적 적합**
- 빈 공간을 모두 검색해 본 후, 프로세스가 적재될 수 있는 공간 중 가장 작은 공간에 프로세스를 배치하는 방식
**최악 적합**
- 빈 공간을 모두 검색해 본 후, 프로세스가 적재될 수 있는 공간 중 가장 큰 공간에 프로세스를 배치하는 방식

### 외부 단편화
- 연속 메모리 할당은 외부 단편화 문제를 가지고 있어 메모리를 효율적으로 사용하는 방법은 아님
- 프로세스를 할당하기 어려울 만큼 작은 메모리 공간들로 메모리가 낭비되는 현상

- 외부 단편화를 해결할 수 있는 대표적인 방안 => 메모리 압축
- 압축: 흩어진 빈 공간을 하나로 모으는 방식으로, 메모리 내에 저장된 프로세스를 적당히 재배치시켜 흩어져 있는 작은 빈 공간을 하나의 큰 빈 공간으로 만드는 방법
- 압축 방식은 빈 공간을 하나로 모으는 동안 시스템이 하던 일을 중지해야 하고, 메모리에 있는 내용을 옮기는 방법은 오버헤드를 야기하며, 어떤 프로세스를 어떻게 움직여야 오버헤드를 최소화하며 압축할 수 있는지가 명확하지 않음

=> 그래서 **페이징 기법** 등장

## 페이징을 통한 가상 메모리 관리
- 가상 메모리: 실행하고자 하는 프로그램을 일부만 메모리에 적재하여 실재 물리 메모리보다 더 큰 프로세스를 실행할 수 있게 하는 기술(케이크를 잘라서 조각 케이크만 냉장고에 넣어 놓는 느낌?)
- 가상 메모리 관리 기법 => 페이징, 세그먼테이션
### 페이징
- 연속 메모리 할당 방식에서 외부 단편화가 생긴 근본적인 이유는 각기 다른 크기의 프로세스가 메모리에 연속적으로 할당되었기 때문
- 만일 메모리/프로세스를 일정한 단위로 자르고, 이것을 메모리에 불연속적으로 할당할 수 있다면 외부 단편화 발생 X
- 이 개념이 **페이징**
- 프로세스의 논리 주소 공간을 **페이지** 단위로 일정하게 자르고, 메모리 물리 주소 공간을 **프레임**이라는 페이지와 동일한 크기의 일정한 단위로 자른 뒤, 페이지를 프레임에 할당하는 가상 메모리 관리 기법
- 스왑 아웃 = 페이지 아웃, 스왑 인 페이지 인
- 프로세스를 이루는 페이지 중 실행에 필요한 일부 페이지만 메모리에 적재, 당장 필요하지 않은 페이지들은 보조기억 장치에 
- 이 방식으로 물리 메모리보다 더 큰 프로세스 실행 가능

### 페이지 테이블
- 프로세스가 메모리에 불연속적 배치 => CPU는 순차적 실행 불가
- 페이징 시스템 => 프로세스가 물리 주소에 불연속적 배치되어도, 논리 주소에 연속적으로 배치되도록 **페이지 테이블** 이용

- 페이지 번호와 프레임 번호를 짝지어 주는 역할(CPU가 페이지 번호만 보고 어떤 프레임에 할당되었는지 알 수 있음)
- 프로세스마다 각자의 페이지 테이블을 가졌으며, 각 프로세스의 페이지 테이블은 메모리에 적재
- CPU 내의 **페이지 테이블 베이스 레지스터(PTBR)**는 각 프로세스의 페이지 테이블이 적재된 주소를 나타냄
- 페이지 테이블을 메모리에 두면 접근 시간이 두 배로 늘어난다는 단점
=> CPU 곁에 **TLB**라는 페이지 테이블의 캐시 메모리를 둠
- TLB는 페이지 테이블의 캐시이므로 페이지 테이블의 일부 내용을 저장
- 참조 지역성에 근거에 주로 최근에 사용한 페이지 위주로 가져와 저장
- TLB 히트: CPU가 발생한 논리 주소에 대한 페이지  번호가 TLB에 있을 경우
- TLB 미스: CPU가 발생한 논리 주소에 대한 페이지  번호가 TLB에 없어 메모리 내의 페이지 테이블에 접근하는 경우

### 페이징에서 주소 변환
- 하나의 페이지 혹은 프레임은 여러 주소를 포괄하고 있기 때문에, 특정 주소에 접근하려면 두 가지 정보 필요

1. 어떤 페이지 or 프레임에 접근하고 싶은지
2. 접근하려는 주소가 그 페이지 or 프레임으로부터 얼마나 멀리 떨어져 있는지

- 페이징 시스템에선 모든 논리 주소(페이지)가 기본적으로 **페이지 번호**와 **변위**로 이뤄짐
**페이지 번호**: 접근하고자 하는 페이지 번호
**변위*: 접근하려는 주소가 프레임의 시작 번지로부터 얼만큼 떨어져 있는지 알기 위한 정보

### 페이지 테이블 엔트리
- 페이지 테이블의 각각의 행
- 페이지 번호, 프레임 번호
- 유효 비트, 보호 비트, 참조 비트, 수정 비트
**유효 비트**
- 현재 해당 페이지에 접근 가능한지 여부
- 현재 페이지가 메모리에 저장되었는지 or 보조기억장치에 있느닞
- 메모리가 적재 => 유효 비트 1, 메모리에 적재 X => 유효 비트 0
- 유효 비트 0인 페이지로 접근하려고 하면 **페이지 폴트**라는 예외 발생
**보호 비트**
- 페이지 보호 기능을 위해 존재하는 비트
- 해당 페이지가 읽고 쓰기가 가능한 페이지인지 or 읽기만 가능한 페이지인지
- 읽기만 가능 => 0, 읽고 쓰기가 가능 => 1
- 더 복잡하게 구현한 경우 => r, w, x로 읽기, 쓰기, 실행하기 권한 조합 나타낼 수 있음
**참조 비트**
- CPU가 이 페이지에 접근한 적이 있는지 여부
- 적재 이후 CPU가 읽거나 쓴 페이지 => 1, 아예 없는 페이지 => 0
**수정 비트**
- 해당 페이지에 데이터를 쓴 적이 있는지 없는지 수정 여부
- 변경된 적 O => 1, 변경된 적 X => 0

> 이 개념을 사용을 할 수 있나? => 내가 프로젝트를 짤 때 메모리 최적화를 고려하는 부분에서 생각해 볼 수 있을 듯??
> 페이징은 OS의 영역이지만, 개발자가 메모리 접근 패턴을 지역성(Locality)에 맞게 짜지 않으면 Page fault 발생

**어떻게 고려할 수 있을까?**
1. 메모리 접근의 지역성 원칙 고려
- 페이징은 인접한 메모리 접근에 유리
- 코드나 데이터 접근을 연속적으로 처리하면 Page Fault 줄어든다
- 배열 순차 접근이 랜덤 접근보다 캐시 지역성이 좋고 Page Fault가 즐어든다

2. 데이터 구조 배치 최적화
- 연관 있는 데이터를 근접 저장
- 지나치게 많은 포인터, 분산을 피함 => 힙에 산재되어 캐시 미스 유발
>**왜?**

- CPU 캐시가 데이터를 한번에 읽어들이기 어려움
- 그로 인해 캐시 미스 발생

3. 데이터 불필요한 로딩 줄이기
- 자주 쓰지 않는 대용량 데이터를 메모리에 다 올리지 않기

## 페이지 교체와 프레임 할당
### 요구 페이징
- 프로세스를 메모리에 적재할 때 처음부터 모든 페이지를 적재하지 않고 필요한 페이지만 메모리에 적재하는 기법
- 요구되는 페이지만 적재하는 기법

**절차**
1. CPU가 특정 페이지에 접근하는 명령어 실행
2. 해당 페이지가 현재 페이지에 있을 경우 CPU는 페이지가 적재된 프레임에 접근
3. 해당 페이지가 현재 메모리에 없을 경우 Page Fault 발생
4. 페이지 폴트 처리 루틴은 해당 페이지를 메모리로 적재하고 유효 비트 1로 설정
5. 다시 1번 수행

- 요구 페이지 시스템이 안정적으로 작동하려면 필연적으로 필요한 페이지 적재 위해 메모리에 전재된 페이지를 보조기억장치로 보내야 함
- 메모리에 적재된 많은 페이지 중 어떤 페이지를 내보내는 것이 최선인지 결정하는 방법이 **페이지 교체 알고리즘**

### 페이지 교체 알고리즘
- 좋은 페이지 교체 알고리즘은 일반적으로 페이지 폴트를 가장 적게 일으키는 알고리즘
- 페이지 폴트 자주 발생 = 보조기억장치로 내쫓을 페이지 잘못 고름

#### 페이지 교체 알고리즘
**FIFO 페이지 교체 알고리즘**
- 가장 먼저 올라온 페이지부터 내쫓는 방식
- 프로그램 실행 초기에 프로그램 실행 내내 사용될 내용이 포함된 경우 비효율적
**최적 페이지 교체 알고리즘
- CPU에 의해 참조되는 횟수 고려 알고리즘
- 앞으로 사용 빈도가 가장 낮은 페이지를 교체하는 알고리즘
- 가장 낮은 페이지 폴트율을 보장하지만 구현이 어려움
**LRU 페이지 교체 알고리즘**
- 가장 오랫동안 사용되지 않은 페이지를 교체하는 알고리즘

### 스레딩과 프레임 할당
- 페이지 폴트가 자주 발생하는 더 근본적인 이유 => 프레임 수가 적기 떄문
- 반대로 프로세스가 사용할 수 있는 프레임 수가 많으면 일반적으로 페이지 폴트 빈도 감소
- 스레싱: 프레임이 부족할 때 CPU는 페이지 폴트가 자주 발생하고, 프로세스가 실제 실행되는 시간보다 페이징에 더 많은 시간을 소요하여 성능이 저해되는 문제
- 스레싱 발생 원인: 각 프로세스가 필요로 하는 최소한의 프레임 수가 보장되지 않았기 때문
- 운영체제는 각 프로세스들이 무리없이 실행하기 위한 최소한의 프레임 수를 파악하고 프로세스들에 적절한 수만큼 프레임을 할당해 줄 수 있어야 함

#### 정적 할당 방식
**균등 할당**
- 세 개의 프로세스에 총 300개의 프레임을 할당할 수 있다면, 각 프로세스에 100개씩 프레임을 할당
- 프로세스의 크기가 다 달라서 비합리적
**비례 할당**
- 프로세스의 크기가 크면 프레임을 많이 할당, 적으면 적게 할당

#### 동적 할당 방식
- 프로세스를 실행하는 과정에서 배분할 프레임을 결정하는 방식 
**작업 집합 모델**
- '프로세스가 일정 기간 동안 참조한 페이지 집합'을 기억하여 빈번한 페이지 교체 방지
- 작업 집합: 실행 중인 프로세스가 일정 시간 동안 참조한 페이지 집합
- CPU가 과거에 주로 참조한 페이지를 작업 집합에 포함하면, 운영체제가 작업 집합의 크기만큼 프레임을 할당
**페이지 폴트 빈도**
- 아래의 두 개의 가정에서 생긴 아이디어
1. 페이지 폴트율이 너무 높으면 그 프로세스들은 너무 적은 프레임을 가짐
2. 페이지 폴트율이 너무 낮으면 그 프로세스는 너무 많은 프레임을 가짐
- 페이지 폴트율의 상한성, 하한선을 골라 이 범위 안에서 프레임을 할당

# CH 15 파일 시스템
## 파일과 디렉토리
### 파일
- 보조기억장치에 저장된 관련 정보의 집합
- 모든 파일에는 이름, 파일 실행 위한 정보, 파일 관련 부가 정보 존재
- 부가 정보 = **속성, 메타데이터**
- 파일 속성: 파일 형식, 위치, 크기 등 파일과 관련된 정보

**속성 종류**
- 유형: 파일 종류 => 확장자 이용
- 크기: 현재 크기와 최대 크기
- 보호: 어떤 사용자가 읽고, 쓰고, 실행할 수 있는지
- 생성 날짜
- 마지막 접근 날짜
- 마지막 수정 날짜
- 생성자
- 소유자
- 위치

### 디렉토리
- 파일을 일목요연 관리 위해 이용
- 윈도우에선 디렉토리 = 폴더
- 옛날 운영체제에는 하나의 디렉토리만 존재
- 1단계 디렉토리: 모든 파일이 하나의 디렉토리 아래 있는 구조
- 트리 구조 디렉토리: 여러 계층 구조
- 그래서 경로가 생김
**절대 경로**: 루트 디렉토리부터 자기 자신까지
**상대 경로**: 현재 디렉토리부터
- 디렉토리도 그냥 '특별한 형태의' **파일**
- 디렉토리는 보조기억장치에 테이블 형태의 정보로 저장

## 파일 시스템
- 파일과 디렉토리를 보조기억장치에 일목요연하게 저장하고 접근할 수 있게 해 주는 운영체제 내부 프로그램

### 파티셔닝과 포맷팅
- 보조기억장치 사용 위해 파티션을 나누는 작업(파티셔닝)과 포맷 작업(포맷팅)을 거쳐야 함
- **파티셔닝**: 저장장치의 논리적인 영역을 구획하는 작업
- **파티션**: 파티셔닝 작업을 통해 나누어진 영역 하나하나
- **포맷팅**: 파일 시스템을 설정하여 어떤 방식으로 파일을 저장하고 관리할 것인지 결정하고, 새로운 데이터를 쓸 준비를 하는 작업

### 파일 할당 방법
- 운영체제는 파일과 디렉토리를 블록 단위로 읽고 슴
- 하나의 파일이 보조기억장치에 저장될 떄는 하나 이상의 블록에 걸쳐 저장
- 하드 디스크의 가장 작은 저장 단위는 섹터
- 운영체제는 하나 이상의 섹터를 블록이란 단위로 묶어 블록 단위로 파일과 디렉토리 관리
- 파일을 보조기억장치에 할당하는 방법은 크게 두 가지가 있음
#### 연속 할당
- 가장 단순한 방식으로 보조기억장치 내 연속적인 블록에 파일을 할당하는 방식
- 구현은 간단하지만 외부 단편화 문제
#### 불연속 할당
**연결 할당**
- 각 블록 일부에 다음 블록의 주소를 저장하여 각 블록이 다음 블록을 가르키는 형태로 할당
- 외부 단편화 문제는 해결하지만 단점 있음
1. 반드시 첫 번째 블록부터 읽어야 함
2. 하드웨어 고장이나 오류 발생 시 해당 블록 이후 블록 접근 불가
=> 이것을 변형해 사용한 파일 시스템이 FAT 파일 시스템
**색인 할당**
- 파일의 모든 블록 주소를 색인 블록이라는 하나의 블록에 모아 관리하는 방식
- 연결 할당과 달리 파일 내 임의의 위치에 접근이 쉬움
=> 이것을 기반으로 만든 파일 시스템이 유닉스 파일 시스템

### 파일 시스템

#### FAT 파일 시스템
- USB, SD 등 저용량 저장장치에서 사용
- 파일 할당 테이블(FAT): 각 블록에 포함된 블록의 주소를 한데 모아 테이블의 형태로 관리하면 연결 할당 단점을 해결할 수 있는데 이 테이블을 의미
- FAT 파일 시스템에서는 FAT 파이션 앞부분에 만들어지며, 뒤이어 루트 디렉토리가 저장되는 영역이 있고, 뒤에 서브 디렉토리와 파일들을 위한 영역 존재

#### 유닉스 파일 시스템
- 유닉스 계열 운영체제에서 사용
- 색인 블록을 i-node라고 부르며, i-node에는 열다섯 개의 블록 주소 저장 가능
- i-node들은 파티션 내 특정 영역에 모여있음
- i-node 영역에 i-node들이 있고, 데이터 영역에 디렉토리와 파일 존재
- i-node는 유한하기 때문에 하나만으로 파일의 데이터 블록을 모두 가르킬 수 없어 아래 방법으로 이 문제를 해결
1. 블록 주소 중 열두 개에는 직접 블록 주소 저장
2. 첫 번째 내용으로 충분하지 않으면 열세 번째 주소에 단일 간접 블록 주소 저장
3. 두 번째 내용으로 충분하지 않으면 열네 번째 주소에 이중 간접 블록 주소 저장
4. 세 번째 내용으로 충분하지 않으면 열세 번째 주소에 삼중 간접 블록 주소 저장
- 이 방법으로 i-node만 알면 파일 속성뿐만 아니라 파일 크기가 크더라도 파일 데이터를 모두 가르킬 수 있음
