#### 2회차 요약
# 1. 왜 스프링인가?
## 💡흐름
- 서블릿 -> 톰캣 + JSP -> 반복 작업 귀찮 -> 스프링 등장
- 목적: **비즈니스 로직 집중, 높은 응집도, 낮은 결합도, POJO 지향**

## 🔍 키워드 정리

| 개념                 | 설명                                 | 스프링 프로젝트 적용                         |
| ------------------ | ---------------------------------- | ----------------------------------- |
| **POJO**           | 특정 프레임워크에 종속되지 않은 순수 자바 객체         | `@Entity`, `@Service` 등도 POJO 원칙 따름 |
| **Servlet/Tomcat** | 클라이언트 요청을 처리하는 저수준 자바 기술           | 스프링이 이 위에서 동작함                      |
| **AOP (프록시 기반)**   | 공통 관심사(로깅, 트랜잭션 등)를 메서드 실행 전/후에 삽입 | `@Transactional`, `@Slf4j`, 예외 로깅   |
| **DI/전략 패턴**       | 의존성을 외부에서 주입 -> 결합도 낮춤             | `@Autowired`, 생성자 주입                |
| **싱글톤 패턴**         | Bean 한 번만 생성해서 공유                  | `@Service`, `@Repository` 등 싱글톤     |
| **템플릿 메서드 패턴**     | 전체 구조는 고정, 세부는 하위 클래스가 정의          | `JpaRepository` 메서드 구현 전략           |

# 2. 트랜잭션 & AOP (@Transactional)

## 🔍 키워드 정리

| 항목                 | 내용                                                     |
| ------------------ | ------------------------------------------------------ |
| **@Transactional** | 메서드 실행 전 → 트랜잭션 시작<br>실행 후 → 정상: commit / 예외: rollback |
| **프록시 기반 AOP**     | 내부적으로 `프록시 객체`가 진짜 객체 호출을 감쌈                           |
| **제약**             | private 메서드에는 적용 안 됨 (`public`만 지원)                    |

# 3. 조회 성능 개선 전략

## 🔍 키워드 정리

| 주제               | 설명                       | 적용 포인트                              |
| ---------------- | ------------------------ | ----------------------------------- |
| **N+1 문제**       | 연관된 엔티티를 지연로딩 시 쿼리 N개 발생 | `fetch join`, DTO로 필요한 데이터만 추출      |
| **카디널리티**        | 인덱스 효율성 척도 (값 다양성)       | 인덱스 설계 시 실험 필요                      |
| **정규화**          | 중복 제거 (테이블 분리)           | `product`, `product_image` 등 테이블 분리 |
| **반정규화**         | 조인 줄이기 위해 테이블 합치기        | 조회 성능이 중요한 곳에 적용                    |
| **DTO 최적화**      | 필요한 필드만 선택적으로 추출         | `List<ProductSummaryDto>` 등         |
| **비동기 처리**       | 빠른 응답을 위해 처리 분리          | `@Async`, but 트랜잭션 전파 안 됨 주의        |
| **트랜잭션 아웃박스 패턴** | 외부 시스템과의 트랜잭션 보장         | 카프카 등 메시지 큐 연동 시 고려                 |


# 4. ERD 설계 전략
- **정규화 단계에서** 연관 테이블 분리 (ex. product ↔ image, category, review)
- **반정규화 고려** : 성능 병목이 심한 조회 쿼리는 중복 허용하고 컬럼 직접 포함
- 설계할 때 주의: join이 3단계 이상이면 성능 저하 우려

# 5. 응답 최적화 흐름

## 📌 응답 시간 구성
```
요청 전송 ⟶ 서버 처리 (WAS + DB) ⟶ 응답 데이터 생성 ⟶ 응답 전송
```

## 📌 최적화 방법

| 항목        | 개선 방안                                   |
| --------- | --------------------------------------- |
| DTO 최적화   | 필요한 필드만 보내기                             |
| 쿼리 최적화    | `fetch join`, `select`로 필요한 필드만         |
| GC 부하 줄이기 | 불필요한 객체 생성 줄이기                          |
| 외부 API 연동 | try-catch-close로 자원 반환                  |
| ERD 구조    | 적절한 정규화와 반정규화                           |
| 인덱스 튜닝    | Full Scan vs Index Scan 비교 분석 (EXPLAIN) |

# 6. 스프링 프로젝트 적용 예시

- 🔧 예: 상품 조회 API
1. DTO 설계: ProductSummaryDto → 상품명, 가격, 썸네일만 포함
2. 쿼리 최적화: @Query + JOIN FETCH로 한방 쿼리
3. 페이징: Pageable + Slice<ProductSummaryDto>
4. 성능 이슈 발견 시: 로그 확인 (show_sql, hibernate_statistics)
5. ERD 설계 팁: 정규화하되 product_image는 1:N으로 분리
6. 트랜잭션 처리: 상품 등록 시 @Transactional, 실패 시 rollback
7. 외부 API 연동: 예를 들어 썸네일 자동 생성 외부 서비스 → RestTemplate + try-catch-finally + @Async 고려
