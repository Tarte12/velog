# ITEM 34 int 상수 대신 열거 타입을 사용하라

열거 타입: 일정 개수의 상수 값을 정의하고, 그 외의 값은 허용하지 않는 타입
	- ex) 사계절, 태양계의 행성, 카드게임의 카드 종류 등
    - 기존: 정수 열거 패턴(int enum pattern)
    1. 타입 안전 보장 X
    2. 표현력 X -> 경고를 보내야 할 때도 컴파일러가 경고 메시지 출력 X
    3. 정수 열거 패턴을 사용한 프로그램은 깨지기 쉬움
    4. 정수 상수를 문자열로 출력하기 까다로움 => 정수 대신 문자열 상수를 사용하는 변형 패턴도 존재
    => 근데 그냥 이 단점을 해결하고 장점 많은 열거 타입(enum type)을 쓰자고 제시함

열거 타입의 특성
**아이디어**
- 자바의 열거 타입은 완전한 형태의 클래스라서(단순한 정숫값일 뿐인) 다른 언어의 열거 타입보다 강력함
- 열거 타입 자체는 클래스이고, 상수 하나당 자신의 인스턴스를 하나식 만들어서 public static final 필드로 공개
- 열거 타입은 밖에서 접근할 수 있는 생성자를 제공하지 않아서 사실상 final임
- 따라서, 클라이언트가 인스턴스를 직접 생성하거나 확장 X => 열거 타입으로 선언한 인스턴스들은 하나씩만 존재 보장
=> 싱글턴 -> 원소가 하나뿐인 열거 타입
=> 열거 타입 -> 싱글톤을 일반화한 형태

장점
1. 컴파일타임 타입 안전성 제공
- 다른 타입의 값을 넘기려고 하면 컴파일 오류 (다른 값끼리 == 연산자로 비교하는 꼴)
2. 이름 공간이 존재해서 이름이 같은 상수도 공존
3. 열거 타입에 새로운 상수를 추가하거나 순서 바꿔도 컴파일 과정 필요 X
- 공개되는 게 오직 필드 이름뿐 => 정수 열거 패턴과 달리 상수 값이 클라이언트로 컴파일되어 각인 X
4. 열거 타입의 toString 메서드는 출력하기에 적합한 문자열을 내어줌
5. 임의의 메서드나 필드 추가 가능
6. 임의의 인터페스 구현 가능 

그렇다면 열거 타입에 메서드나 필드를 추가하는 경우는 언제일까?
ex) 태양계의 여덟 행성을 열거 타입으로 생각해 보자
-> 각 행성의 질량과 반지름이 있다면 => 표면 중력 계산 가능
-> 어떤 객체의 질량이 주어짐 => 그 객체가 행성 표면에 있을 떄 무게 계산 가능
-> 그러니까 열거한 내용을 가지고 특정 기능을 만들고 싶다면 추가 가능

열거 타입 상수 각각을 특정 데이터와 연결지으려면 생성자에서 데이터를 받아 인스턴스 필드에 저장하면 됨

- 열거 타입은 근본적으로 불변이라 모든 필드는 final이어야 함
- 필드를 public으로 선언해도 되지만, private로 두고 별도 public 접근자 메서드를 두는 게 나음

- Planet의 생성자에서 표면중력을 계산해 저장한 이유 => 최적화
- 그러니까 열거 타입은 단순한 것에 비해 Good

- 열거 타입은 자신 안에 정의된 상수들의 값을 배열에 담아 반환하는 정적 메서드인 values를 제공
- 값들은 선언된 순서로 저장
- 각 열거 타입의 값의 toString 메서드는 상수 이름을 문자열로 반환하여 println, printf로 출력하기 좋음

- if) 명왕성이 퇴출됐는데 열거 타입에서 상수를 하나 제거한다면?
=> 제거한 상수를 참조하지 않은 클라이언트는 아무 영향 X
=> 제거한 상수를 참조하는 클라이언트는? => 컴파일할 때 컴파일 오류 뜸 or 컴파일하지 않을 경우 런타임에 유용한 예외 발생
-> 정수 열거 패턴일 경우 이런 오류 메시지 안 줌

- 열거 타입을 선언한 클래스 or 그 패키지에서만 유용한 기능은 private나 package-private 메서드로 구현
- 구현된 열거 타입 상수는 자신을 선언한 클래스 or 패키지에서만 사용할 수 있는 기능을 담음
- 해당 기능을 클라이언트에 노출할 이유가 없다면 private, 필요하다면 package-private 사용

- 널리 쓰이는 열거 타입은 톱레벨 클래스로 생성 
- 특정 톱레벨 클래스에만 쓰인다면 -> 해당 클래스의 멤버 클래스로 만들라

- 만일 상수마다 동작이 달라져야 한다면?
ex) 사칙연산 계산기의 연산 종류를 열거 타입으로 선언 -> 실제 연산까지 열거 타입 상수가 직접 수행해야 하는 경우
- 열거 타입에 apply라는 추상 메서드를 선언 => 각 상수별 크랠스 몸체, 각 상수에서 자신에 맞게 재정의하면 됨
=> 이것을 상수별 메서드 구현이라고 함

- apply는 추상 메서드이므로 재정의 안 하면 컴파일 오류로 알려줌
- 상수별 메서드 구현을 상수별 데이터와 결합할 수 있음
- 열거 타입에는 상수 이름을 입력받아 그 이름에 해당하는 상수를 반환해 주는 valueOf(String) 메서드가 자동 생성됨

- 열거 타입의 toString 메서드를 재정의할 때 => toString이 반환하는 문자열을 해당 열거 타입 상수로 변환해 주는 fromString 메서드도 함께 제공하는 걸 고려해 보자

- 열거 타이브이 정적 필드 중 열거 타입의 생성자에서 접근할 수 있는 것은 상수 변수뿐
-열거 타입의 생성자에서 같은 열거 타입의 다른 상수에도 접근 불가
- fromString이 Optional<Operation>을 반환하는 점도 주의
=> 주어진 문자열이 가리키는 연산이 존재하지 않을 수 있음을 클라이언트에 알리고 그 상황을 클라이언트가 대처하도록 함
  
단점
- 상수별 메서드 구현에서는 열거 타입 상수끼리 코드 공규가 어려움
=> 기존 열거 타입에 상수별 동작을 혼합해 넣을 떄는 switch문잊 ㅗㅎ은 선택이 될 수 있음
  
- 열거 타입의 성능은 정수 상수와 별로 다르지 않음 => 열거 타입을 메모리에 올리는 공간과 초기화하는 시간이 들긴 하지만 체감적으로 미미함
  
그러면 열거 타입을 언제 쓰냐?
- 필요한 원소를 컴파일타입에 다 알 수 있는 상수 집합이라면 항상 열거 타입을 사용하자
- 열거 타입에 정의된 상수 개수가 영원히 고정 불변일 필요 없음 => 나중에 상수가 추가돼도 바이너리 수준에서 호환되도록 설계됨

# ITEM 35 ordinal 메서드 대신 인스턴스 필드를 사용하라
 
- 대부분의 열거 타입 상수는 자연스럽게 하나의 정숫값에 대응됨 
- ordinal 메서드 제공 => 열거 타입이 해당 상수가 그 열거 타입에서 몇 번째 위치인지 반환하는 메서드로 열거 타입이 제공함
- 열거 타입 상수와 연결된 정숫값이 필요하면 ordinal 메서드를 이용하고 싶을 것 => 하지 말라고 하겟지 (유지보수가 끔찍하다)
  
열거 타입 상수에 연결된 값은 ordinal 메서드로 얻지 말고 인스턴스 필드에 저장해라
  
- ordinal 메서드는? => EnumSet이나 EnumMap처럼 열거 탕ㅂ 기반 범용 자료구조에 쓸 목적으로 설계되었으므로 이 경우아니면 사용 X
  
# ITEM 36 비트 필드 대신 EnumSet을 사용하라
 
비트 필드
- 열거한 값들이 주로 (단독이 아닌) 집합으로 사용될 경우 => 예전에는 각 상수에 서로 다른 2의 거듭제곱 값을 할당한 정수 열거 패턴을 사용함
- 비트별 OR을 사용해 여러 상수를 하나씩 모아 집합으로 만든 것
- 비트 필드를 사용하면 비트별 연산을 사용해 집합 연산을 효율적으로 수행할 수 있으나 단점이 많음

단점
1. 정수 열거 상수 단점 그대로 가져감
2. 비드 필드 값이 그대로 출력되면 단순한 정수 열거 상수 출력 시보다 해석하기 훨씬 어려워짐
3. 비트 필드 하나에 녹아 있는 모든 원소를 순회하기 까다로움
4. 최대 몇 비트가 필요한지 api 작성 시 미리 예측하여 적절한 타입을 선택해야 함 => API를 수정하지 않고는 비트수를 더 늘릴 수 없기 때문
  
=> 그러니까 java.util 패키지의 EnumSet 클래스를 쓰자
- 열거 타입 상수의 값으로 구성된 집합을 효과적으로 표현해 줌
- Set 인터페이스를 완벽히 구현
- 타입 안전
- 다른 어떤 Set 구현체와도 함께 사용 가능
- EnumSet 내부는 비트 벡터로 구현
- 원소가 총 64개 이하라면 => 대부분의 경우 EnumSet 전체를 long 변수 하나로 표현하여 비트 필드에 비견되는 성능을 보임
- removeAll과 retainAll 같은 대량 작업 (비트 필드를 사용ㅎ랄 떄 쓰는 것과 같은) 비트를 효율적으로 처리할 수 있는 산술 연산을 써서 구현했다
- 그러면서도 비트를 직접 다룰 때 흔히 겪는 오류들에서 해방됨 => EnumSet이 다 처리해 줘서

# ITEM 37 ordinal 인덱싱 대신 EnumMap을 사용하라
배열이나 리스트에서 원소를 꺼낼 떄 ordinal 메서드로 인덱스를 얻는 코드가 있음
-> 문제?
1. 배열은 제네릭과 호환되지 않아 비검사 형 변환 필요 + 컴파일이 깔끔하지 않을 가능성
2. 배열은 각 인덱스의 의미를 모르니 출력 결과에 직접 레이블을 달아야 함
3. 정확한 정숫값을 사용한다는 것을 내가 직접 보증해야 함 => 타입이 안전하지 않으니까
  
=> 그냥 EnumMap를 써라
- 배열 인덱스의 경우 실질적으로 열거 타입 상수를 값으로 매핑하는 일을 하기 때문에 Map을 사요해도 됨
- 짧고 명료하고 안전하고 성능 Good
=> 왜?
- EnumMap 내부에서 배열을 사용하는데 내부 구현 방식을 안으로 숨겨서 Map 타입 안전성과 배열의 성능을 모두 얻어냄
  
- EnumMap 생성자가 받는 키 타입의 Claa 객체는 한정적 타입 토큰으로 런타임 제네릭 타입 정보를 제공
- 스트림을 사용해서 맵 관리하면 코드 더 줄일 수 있음 
- 근데 스트림 쓰면 약간 다르게 동작함
  => only EnumMap 언제나 식물의 생애주기당 하나씩의 중첩 맵만 만든다
  => 스트림 해당 생애주기에 속사는 식물이 있을 때만 만든다
  
# ITEM 38 확장할 수 있는 열거 타입이 필요하면 인터페이스를 사용하라

- 보통은 열거 타입이 타입 안전 열거 패턴보다 우수
- 예외 => 타입 안전 열거 패턴은 확장 가능, 열거 타입은 확장 불가
- 보통 열거 타입 확장하는 게 좋지 않은 생각이라 이렇게 설계했다고 봐야...
근데 예외가 있음 => 연산 코드임
- 가끔 API가 제공하는 기본 외에 사용자 확장 연산을 추가할 수 있도록 열어 줘야 할 때가 있음
=> 이때의 확장 아이디어가 열거 타입이 임의의 인터페이스를 구현할 수 있다는 것
- 인터페이스를 확장할 수 있으니까 인터페이스를 연산의 타입으로 사용할 수 있음
- 개별 인스턴스 수준을 너머 타입 수준에서도 기본 열거 타입 대신 확장된 열거 타입을 넘겨 확장된 열거 타입의 원소 모두를 사용하게 할 수 있음

- 인터페이스를 이용해 확장 가능한 열거 타입을 흉내 내는 방식에도 문제 존제 => 열거 타입끼리 구현을 상속할 수 없다는 점
- 아무 상태로 의존하지 않는 경우 => 디폴트 구현을 이용해 인터페이스에 추가할 수 있음
- 코드 중복이 많다면 (공유하는 기능이 많다면) => 그 부분을 별도 도우미 클래스나 정적 도우미 메서드로 분리하는 방식이 있음
  
# ITEM 39 명명 패턴보다 애너테이션을 사용하라
내 의문점 => Spring 쓰면 다 애너테이션 쓰지 않아...?

# ITEM 40 @Override 애너테이션을 일관되게 사용하라
  
@Override
- 메서드 선언에만 달 수 있음
- 이 애너테이션이 달린 것은 사윙 타입의 메서드를 재정의했음을 뜻함
- 일관되게 사용하면 여러 악명 높은 버그를 예방해 줌
  
=> 사우이 클래스의 메서드를 재정의하려는 모든 메서드에 @Override 애너테이션을 달자
- 예외: 구체 클래스에서 상위 클래스의 추상 메서드를 재정의할 땐 안 달아도 됨
- 구체 클래스인데 아직 구현하지 않은 추상 메서드가 남을 경우 => 컴파일러가 그 사실을 바로 알려주기 때문
