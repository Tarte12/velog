# ITEM 57 지역변수의 범위를 최소화하라

**문제점**
- 변수는 **살아 있는 범위가 길수록 버그를 만들 확률이 높음**
- 특히 복사-붙여넣기, 반복문에서 실수 많이 남

**규칙**
1. 지역변수는 **처음 사용할 때 선언**하기
2. 가능하면 **선언과 동시에 초기화**하기
3. **for문 적극 사용** -> 반복 변수 범위가 자동으로 좁아짐
4. 메서드가 길다면 -> **기능별로 쪼개라**

**for문 VS while문**
```java
// ✅ 좋은 예 - for-each 문
for (Element e : c) {
    // e로 작업
}

// ✅ 좋은 예 - 전통적인 for 문
for (Iterator<Element> i = c.iterator(); i.hasNext(); ) {
    Element e = i.next();
    // e와 i로 작업
}

// ❌ 나쁜 예 - while 문
Iterator<Element> i = c.iterator();
while (i.hasNext()) {
    doSomething(i.next());
}
// 여기서 i를 실수로 재사용할 수 있음!
```
**for문 장점**
1. **범위 제한**: 반복 변수가 반복문 안에서만 유효
2. **복사 오류 방지**: 컴파일 타임에 오류 감지 
3. **간결함**: 코드가 더 짧고 읽기 쉬움

# ITEM 58 전통적인 for문보다는 for-each문을 사용하라

**문제점**
- 인덱스(i), 반복자(iterator)는 **버그의 원천**
- 중첩 반복에서 실수하면 컴파일도 안 잡힘

**for-each문 장점**
```java
// ❌ 전통적인 for 문 - 지저분함
for (int i = 0; i < a.length; i++) {
    // a[i]로 작업
}

// ✅ for-each 문 - 깔끔함
for (Element e : elements) {
    // e로 작업
}
```

**for-each문을 쓰기 좋은 경우**
- 컬렉션/배열 **그냥 순회만 할 때**
```
for (Element e : elements) {
    // e만 신경 쓰면 됨
}
```

**for-each문을 못 쓰는 경우**
1. **파괴적인 필터링**: `remove()` 메서드 호출해야 할 때
2. **변형**: 원소의 값을 교체해야 할 때
3. **병렬 반복**: 여러 컬렉션을 동시에 순회할 때

# ITEM 60 정확한 답이 필요하다면 float와 double은 피하라

**문제점**
- float/double은 **근사치 계산용**
```java
// ❌ 부정확한 결과
System.out.println(1.03 - 0.42);  // 0.6100000000000001

double funds = 1.00;
for (double price = 0.10; funds >= price; price += 0.10) {
    funds -= price;
}
// 잘못된 결과!
```
**대안**
1. **BigDecimal 사용**
- 단점: 사용하기 불편하고 느림
```java
// ✅ 정확한 계산
final BigDecimal TEN_CENTS = new BigDecimal(".10");
BigDecimal funds = new BigDecimal("1.00");
// ... 정확한 금액 계산
```
1. **int 또는 long 사용** (권장)
```java
// ✅ 센트 단위로 계산
int funds = 100;  // 1달러 = 100센트
for (int price = 10; funds >= price; price += 10) {
    funds -= price;
}
```
# ITEM 61 박싱된 기본 타입보다 기본 타입을 사용하라

**차이**

| 기본 타입   | 박싱 타입        |
| ------- | ------------ |
| 값만 있음   | **객체 + 식별성** |
| null 없음 | **null 가능**  |
| 빠름      | 느림           |

1. null
- 기본 타입은 **존재 보장**
- 박싱 타입은 **null 상태 섞임**
=> 비스니스 로직에서 **"값이 0"과 "값이 없음"이 섞인다면** 버그 발생

**박싱 타입 써야 하는 경우**
1. 컬렉션의 원소, 키, 값 (예:`List<Integer>`)
- 자바 제네릭 설계의 한계
- 제네릭은 `Object` 기반으로 동작
- 기본 타입은 `Object`를 상속받지 않음
- 따라서 제네릭에는 반드시 참조 타입만 사용 가능
```java
// ❌ 불가능! 제네릭은 기본 타입을 받을 수 없음
List<int> numbers;        // 컴파일 에러!
Map<int, String> map;     // 컴파일 에러!

// ✅ 박싱 타입 사용
List<Integer> numbers = new ArrayList<>();
Map<Integer, String> map = new HashMap<>();
```
2. 매개변수화 타입의 타입 매개변수 (예: `Thread.ocal<Long>`)
- 1번과 같은 이유로 제네릭 제약
3. 리플렉션을 통한 메서드 호출
```java
// 리플렉션으로 메서드 호출 시
Method method = obj.getClass().getMethod("setValue", Integer.class);
method.invoke(obj, 42);  // Integer로 전달해야 함

// int.class는 있지만, 리플렉션 API는 Object 기반이라
// 실제로는 박싱된 타입을 다룸
```

# ITEM 64 객체는 인터페이스로 참조하라
**왜?**
- 구현 교체가 쉬워짐
- 코드 유연성 좋아짐

**주의**
- 원래 클래스가 **특별한 기능**을 제공하고 코드가 그것에 의존한다면 조심
- 예: `LinkdHashSet`의 순서 보장 기능

**인터페이스가 없다면 클래스 사용**
1. **값 클래스**: `String`, `BigInteger` 등
2. **클래스 기반 프레임워크**: `OutputStream` 등
3. **특별한 메서드 제공**: `PriortyQueue.comparator()` 등

# ITEM 65 리플렉션보다는 인터페이스를 사용하라
**리플렉션**
- 런타임에 클래스 정보를 가져오고, 생성자/메서드/필드를 조작할 수 있는 기능
```java
Class<?> c = Class.forName("com.example.MyClass");
Method m = c.getMethod("run");
m.invoke(obj);
```
**리플렉션 단점**
1. **컴파일타임 타입 검사 불가** -> 런타임 오류 발생
2. **코드가 지저분하고 장황함**
3. **성능 저하** 

**왜 쓸까?**
=> "사용자 코드"가 아니라 "도구 코드"를 만들 때
- 프레임워크
- 플러그인 구조
- DI 컨테이너
- 테스트 도구

**권장**
- 리플렉션으로 메서드 호출까지 X
- 객체 생성까지만 리플렉션
- 이후에는 인터페이스 사용

# ITEM 66 네이티브 메서드는 신중히 사용하라
**네이티브 메서드**
- C/C++ 같은 네이티브 언어로 작성한 메서드를 자바에서 호출하는 기능
```java
native void fastCalc();

// Java -> C/C++ 호출 (JNL)
```

**쓰는 이유**
- OS 기능 접근
- 기존 C 라이브러리 재사용
- 극단적 성능

**문제점**
1. 안전하지 않음 - 메모리 훼손 가능
2. 플랫폼 의존적 - 이식성 낮음
3. 디버깅 어려움
4. 가비지 컬렉터가 관리 못함
5. 경계를 넘나들 때마다 비용 발생
6. 접착 코드 작성 필요 - 귀찮고 가독성 나쁨

**결론**
- 성능 개선 목적으로는 거의 사용 X
- 꼭 필요한 경우: 저수준 자원이나 레거시 라이브러리
- 최소한으로만 사용하고 철저히 테스트


# ITEM 67 최적화는 신중히 하라
**최적화**
- 최적화는 좋은 결과보다 해로운 해로운 결과로 이어지기 쉬움
- 성능 때문에 견고한 구조를 희생하지 말자
- 빠른 프로그램보다 좋은 프로그램을 작성하자
- 좋은 프로그램이지만 원하는 성능이 나오지 않는다면, 그 아키텍처 자체가 최적화할 수 있는 길을 안내할 것
- 좋은 프로그램은 개별 구성 요소의 내부가 독립적으로 설계되어 있기 때문

**올바른 최적화 순서**

**1단계: 좋은 설계부터**
```java
// ✅ 깨끗하고 명확한 구조 우선
public class WellDesigned {
    private final List<Item> items; // 캡슐화
    
    public int getTotal() {
        return items.stream()
            .mapToInt(Item::getPrice)
            .sum();
    }
}
```
**2단계: 성능 측정**
```java
// ✅ 최적화 전후로 측정하라
long start = System.nanoTime();
// 테스트할 코드
long elapsed = System.nanoTime() - start;
```
**3단계: 프로파일링**
- 프로파일링 도구 사용(VisualVM, JProfiler 등)
- 시간을 가장 많이 쓰는 10%의 코드 찾기
- 알고리즘 개선 필요성 확인
```java
// ❌ 미세한 최적화보다는
for (int i = 0; i < n; i++) {
    result += i; // 이런 거 최적화하지 마라
}

// ✅ 알고리즘 개선이 중요
// O(n²) → O(n log n) 같은 개선
```
**4단계: JMH로 마이크로 벤치마킹**
```java
// JMH 사용 예시
@Benchmark
public void testMethod() {
    // 성능 측정할 코드
}
```
**최적화 시 주의사항**
```java
// ❌ 성능을 위해 캡슐화 깨지 마라
public class BadOptimization {
    public int[] data; // public 필드 - 나쁨!
}

// ✅ 필요하면 프로파일링 후 신중히 결정
public class GoodDesign {
    private final int[] data;
    
    public int get(int index) {
        return data[index];
    }
}

```
**성능과 관련된 설계 설정**
```
// API 설계 시 성능 고려사항

// ❌ 가변 타입 반환 - 방어적 복사 필요
public Dimension getSize() {
    return new Dimension(size); // 매번 복사!
}

// ✅ 불변 타입 또는 기본 타입
public int getWidth() { return width; }
public int getHeight() { return height; }

// ❌ 상속 - 상위 클래스 종속
public class Slow extends SuperSlow { }

// ✅ 컴포지션 - 유연함
public class Fast {
    private final Helper helper;
}

// ❌ 구현 타입 - 나중에 변경 어려움
public LinkedHashSet<String> getNames() { }

// ✅ 인터페이스 타입 - 구현체 교체 가능
public Set<String> getNames() { }
```
