## 1. 프론트엔드: "어디에 두느냐"가 "무엇을 만드느냐"를 결정한다 🏗️

초기 개발 단계에서는 매우 전형적인 **역할 기반 폴더 구조(hooks, components, api 등)**를 택했다. 하지만 기능이 확장될수록 비극이 시작되었다. 특정 도메인의 로직 하나를 고치기 위해 프로젝트 전체 폴더를 유람해야 하는 '인지적 부하'가 발생했고, 코드의 응집도는 바닥을 쳤다.

### 🧐 FSD와 Bulletproof React 사이의 고민

구조를 완전히 뒤엎기로 결심했을 때, 두 가지 선택지가 있었다. 계층 구조가 매우 엄격한 **FSD(Feature-Sliced Design)**와 비교적 직관적인 **Bulletproof React** 패턴이었다.

우리 팀의 규모와 생산성을 냉정하게 따져보았다. 너무 엄격한 규칙은 오히려 독이 될 수 있다고 판단했고, 결국 기능을 `features/` 단위로 격리하여 도메인 중심의 응집도를 높이는 **Bulletproof 구조**를 선택했다. 이 결정 이후, 코드는 제자리를 찾았고 협업 속도는 눈에 띄게 빨라졌다.

### 🔗 외부 상태와의 사투: useSyncExternalStore

단순히 코드 정리만으로 해결되지 않는 문제가 있었다. 바로 `localStorage`를 통한 인증 상태 관리다. 멀티 탭 환경에서 한쪽 탭이 로그아웃되어도 다른 탭은 여전히 로그인 상태로 남아있는 **데이터 불일치(Inconsistency)** 현상이 발생했다.

이를 해결하기 위해 React 18의 `useSyncExternalStore`를 도입했다. 브라우저의 `storage` 이벤트와 커스텀 이벤트를 구독(Subscribe)하여, 외부 저장소의 변화를 React가 즉각적으로 감지하고 스냅샷을 다시 찍도록 구현했다.

| 문제 현상 | 해결책 | 효과 |
| --- | --- | --- |
| 멀티 탭 상태 불일치 | `useSyncExternalStore` 도입 | 실시간 외부 상태 동기화 |
| Hydration Mismatch | `getServerSnapshot` 강제 null 처리 | SSR 정합성 에러 해결 |

**💡 Insight:** 아키텍처는 단순히 파일 정리함이 아니다. 외부 상태와 React 생명주기 사이의 정합성을 어떻게 설계적으로 '강제'할 것인가에 대한 결단이었다.

## 2. 인증/인가: Stateless라는 환상과 Redis라는 현실 🔒

우리는 확장이 용이한 **무상태(Stateless)** 아키텍처를 지향하며 JWT를 채택했다. 하지만 이론과 현실은 달랐다. JWT는 한번 발급되면 서버가 통제할 수 없다. 로그아웃을 해도 토큰이 만료될 때까지 유효하다는 점은 보안상 치명적인 결함이었다.

### ⚖️ Fail-closed: 보안과 가용성 사이의 줄타기

Spring Security OAuth2 표준 라이브러리는 기본적으로 세션 기반으로 동작했다. 우리의 Stateless 지향성과 정면으로 충돌하는 지점이었다. 여기서 깊은 고민에 빠졌다.

> "보안을 위해 가용성을 포기할 것인가(Fail-closed), 가용성을 위해 보안을 타협할 것인가(Fail-open)?"

우리의 선택은 **보안**이었다. 무상태의 순수성을 조금 잃더라도 Redis를 도입하여 하이브리드 설계를 구축하기로 했다.

### 🛠️ 하이브리드 보안 전략의 핵심

1. **RTR (Refresh Token Rotation):** 토큰 갱신 시 기존 RT를 폐기하고 신규 RT를 발급한다. 특히 이미 사용된 RT가 유입될 경우, 이를 탈취로 간주하여 유저의 모든 활성 세션을 즉시 무효화하는 **재사용 감지(Reuse Detection)** 로직을 구현했다.
2. **Redis Blacklist:** 로그아웃 시 Access Token의 잔여 TTL만큼 Redis에 SHA-256 해싱된 토큰을 저장하여 즉각적인 접근을 차단했다.
3. **커스텀 OAuth 2.0 구현:** 아키텍처 일관성을 위해 `RestClient`를 활용해 OAuth 2.0 flow를 직접 제어했다. 덕분에 완전한 Stateless 지향성을 유지하면서도 강력한 제어권을 얻었다.

**💡 Insight:** 실무에서 '완전한 무상태'는 이상에 가깝다. 성능을 위해 AT는 무상태로 두되, 보안 제어권을 위해 RT는 Redis라는 **'상태(State)'**를 통해 관리하는 하이브리드 전략이 최선임을 배웠다.

## 3. 시스템 가용성: 외부 API와의 위태로운 악수 🤝

Google Calendar API 연동 과정에서 큰 고비를 맞았다. 외부 서버의 응답 지연이 우리 메인 비즈니스 로직(예약 트랜잭션)을 점유하여 전체 시스템 병목을 유발할 위험이 발견된 것이다. 타임존 부재로 인한 시점 해석의 모호성 또한 데이터 정합성을 위협했다.

### 🛡️ 방어적 연동(Defensive Integration) 정책

외부 시스템은 언제든 실패할 수 있는 '신뢰할 수 없는 영역'이다. 이를 위해 시스템 가용성을 최우선으로 하는 설계를 채택했다.

* **Instant 도입:** 타임존 정보를 배제한 UTC 기준 절대 시간인 `Instant`를 도입하여 유일한 **진실의 원천(SSOT)**을 구축했다. 🌍
* **멱등성(Idempotency)과 Upsert:** 네트워크 불안정으로 인한 중복 요청에 대비해 외부 이벤트 ID를 추적하고 `upsert` 로직을 적용했다.
* **선제적 검증 (PR #241):** 설정 저장 전 `validateCalendarAccess`를 호출하여 런타임 에러를 사전에 차단(**Fail-fast**)했다.

**💡 Insight:** 외부 시스템과 연동할 때는 물리적, 논리적 결합도를 최대한 낮춰야 한다. 시스템의 가용성을 지키기 위해서는 항상 **'실패를 전제한 방어적 설계'**가 필수적이다.

## 🏁 마치며: 기술은 도구일 뿐, 본질은 정합성이다

이번 프로젝트를 통해 얻은 가장 큰 수확은 "어떤 기술을 썼는가"보다 **"데이터의 정합성을 어떻게 보장할 것인가"**에 대한 관점의 변화다.

* 브라우저 탭 사이의 상태 정합성
* 토큰의 보안 상태와 서버의 통제권 사이의 정합성
* 우리 서버와 외부 API 사이의 데이터 정합성

결국 모든 설계적 고민은 이 '정합성'이라는 단어로 귀결되었다. 화려한 기술 스택보다 중요한 것은, 내가 짠 코드 한 줄이 시스템 전체의 일관성을 해치지 않는지 끊임없이 의심하는 태도라는 것을 다시 한번 배운다. 👨‍💻
