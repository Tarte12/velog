### 1. Post.java
```java
package org.example.demo3.domain.post;

import jakarta.persistence.*;
import lombok.*;
import java.time.LocalDateTime;

@Entity
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Post {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;

    @Lob
    private String content;

    private LocalDateTime createdAt;

    @Builder
    public Post(String title, String content) {
        this.title = title;
        this.content = content;
        this.createdAt = LocalDateTime.now();
    }

    public void update(String title, String content) {
        this.title = title;
        this.content = content;
    }
}

```
### 2. PostController.java 
```java
package org.example.demo3.controller;


import lombok.RequiredArgsConstructor;
import org.example.demo3.domain.post.Post;
import org.example.demo3.service.PostService;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.util.List;

@RestController //REST API를 만드는 클래스라는 표시
@RequiredArgsConstructor
@RequestMapping("/api/posts") //자원(posts)에 접근하는 URL
public class PostController {

    private final PostService postService;

    @PostMapping //HTTP 메서드와 연결
    public ResponseEntity<Post> create(@RequestBody Post post) {
        return ResponseEntity.ok(postService.create(post));
    }

    @GetMapping //HTTP 메서드와 연결
    public ResponseEntity<List<Post>> findAll() {
        return ResponseEntity.ok(postService.findAll());
    }

    @GetMapping("/{id}") //HTTP 메서드와 연결
    public ResponseEntity<Post> findById(@PathVariable Long id) {
        return postService.findById(id)
                .map(ResponseEntity::ok)
                .orElse(ResponseEntity.notFound().build());
    }

    @PutMapping("/{id}") //HTTP 메서드와 연결
    public ResponseEntity<Void> update(@PathVariable Long id, @RequestBody Post post) {
        postService.update(id, post.getTitle(), post.getContent());
        return ResponseEntity.ok().build();
    }

    @DeleteMapping("/{id}") //HTTP 메서드와 연결
    public ResponseEntity<Void> delete(@PathVariable Long id) {
        postService.delete(id);
        return ResponseEntity.noContent().build();
    }
}
```

### 4. PostService
```java
package org.example.demo3.service;


import lombok.RequiredArgsConstructor;
import org.example.demo3.domain.post.Post;
import org.example.demo3.repository.PostRepository;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import java.util.List;
import java.util.Optional;

@Service
@RequiredArgsConstructor
public class PostService {

    private final PostRepository postRepository;

    public Post create(Post post) {
        return postRepository.save(post);
    }

    public List<Post> findAll() {
        return postRepository.findAll();
    }

    public Optional<Post> findById(Long id) {
        return postRepository.findById(id);
    }

    @Transactional
    public void update(Long id, String title, String content) {
        Post post = postRepository.findById(id).orElseThrow();
        post.update(title, content);
    }

    public void delete(Long id) {
        postRepository.deleteById(id);
    }
}
```

# 1. Spring 계층 구조

## 1.1 계층 구조란?
- **소프트웨어를 역할에 따라 분리한 구조**
- **책임 분리(SRP)**와 **유지보수성** 향상이 목적
![](https://velog.velcdn.com/images/emprimula/post/808e346e-1605-45f9-b443-3b8e626b3fc6/image.webp)
```
<SpringBoot>가 클라이언트의 요청을 받으면 위와 같은 순서로 처리>
1. 클라이언트의 요청
2. Controller: 요청의 유효성을 검증하고, 적절한 Service를 호출 => 결과를 다시 응답 형태로 클라이언트에게 반환
3. Service: 핵심 로직 구현 파트, Controller로부터 받은 데이터를 적절하게 가고 => Repository를 호출하여 데이터베이스 조작
4. RepositoryL 데이터베이스에 접근하여 데이터를 조작
```

- 스프링에서는 일반적으로 3계층 구조 사용
1. `Presentation Layer` -> `Controller`
	- **Controller**: 외부 요청을 받고 응답 반환
2. `Business Logic Layer` -> `Service`
	- **Service**: 비즈니스 로직 처리
3. `Data Access Layer` -> `Repository`
	- **Repository**: DB와의 데이터 접근 처리(JPA 사용)
    
## 1.2 각 계층의 역할

### 프레젠테이션 계층 (Controller 클래스)
- 사용자의 요청을 처리, 요청에 대한 응답 데이터 반환
- 클라이언트와 서버 간의 **인터페이스 역할**을 담당하며, HTTP 요청 및 응답 처리
- `@RestController` or `@Controller` 어노테이션으로 API 엔드 포인트 정의

> 1. 화면으로 사용자가 요청한 걸 받고, 프로그램 내의 반환값을 다시 사용자한테 돌려주는 역할을 하는 건지?
-> 맞음! **브라우저 or Postman 같은 클라이언트의 요청 => 컨트롤러가 받고 => 응답을 돌려 주는 것**이 주 역할 
<br>
>2. API 엔드 포인트가 뭘 의미하는 것인지?
-> **접속 주소(url)**
	- @RequestMapping("/api/posts"): 여기에서의 엔드 포인트가 `/api/posts`가 됨
    - @PostMapping // POST /api/posts
	- @GetMapping("/{id}") // GET /api/posts/1
    - 각각이 **REST API의 엔드 포인트**기 된다
    - **이 url로 이 메서드를 호출하면 동작해요**라는 의미



### 비즈니스 로직 계층 (Service 클래스)
- 핵심 비즈니스 로직 처리
- 요청을 검증하고 데이터 로직 수행
- 필요한 경우에 데이터 접근 계층과 통신
- `@Service` 어노테이션으로 구현

>1. 핵심 비즈니스 로직? 실제로 구현한 코드를 말하는 것인지?
- 핵심 로직 = **애플리케이션이 해결해야 할 본질적인 문제 처리 코드**
- ex) "게시글 등록", "회원가입", "댓글 좋아요 증가" 같은 동작
- postRepository.save(post); : **실제 DV에 저장하는 로직**도 실제 비즈니스 흐름의 일부
<br>
> 2. 데이터 로직 수행은 뭔지 필요할 때 DB를 가져오는 것을 데이터 접근 계층과 통신한다고 말하는 것인지?
- 맞음! 보통 서비스 계층에서 DB에서 데이터를 가져오거나 조작해야 할 일 존재
- 그럴 때 **Repository를 호출**해서 DB 작업을 시킴
- Post post = postRepository.findById(id).orElseThrow(); : 이런 게 **데이터 로직 수행**

### 데이터 접근 계층 (Repository 클래스)
- 데이터베이스와 상호작용해 데이터를 저장하거나 조회
- ORM(JPA, Hibernate), JPQL, SQL을 통해 데이터 조작을 수행
- `@Repository` 어노테이션으로 구현
- DAO or Repository를 사용

> 1. 실질적으로 데이터베이스를 조작하는 계층을 말하는 건지?
- 맞음! `Repository`는 **DB 쿼리 수행**이 주 역할
- CRUD(Create, Read, Update, Delete)를 이 계층에서 직접 처리
<br>
> 2. DAO가 무엇인지? DAO나 Repository를 사용한다는 게 무슨 뜻인지?
- **DAO(Data Access Object)**: 전통적인 이름 -> **DB 접근만** 전담하는 객체
- **Repository**: Spring Data JPA에서는 DAO 대신 씀
	- `@Repository`를 붙이고 `JpaRepository`를 상속 받으면 자동으로 DB 코드 생성
    - **Repository를 사용하겠다** => **DB 조작 로직을 직접 작성하지 않고, JPA가 알아서 처리하게 위임하겠다**
    
## 1.3 궁금증 => Domain?

### Q1. Post, User, File 같은 도메인을 나누는 기준은?

> ** 도메인은 "행위"가 아니라, "개념" 기준 **

- `Post`, `User`, `File` => **비즈니스의 중심이 되는 개념**
- **데이터 + 그것이 하는 일(행동)**을 묶은 단위

#### 도메인의 기준
| 도메인 이름 | 기준        | 예시                                     |
| ------ | --------- | -------------------------------------- |
| `Post` | 게시글이라는 실체 | 제목, 내용, 작성일 등의 속성과 "수정", "삭제" 등의 행동 포함 |
| `User` | 사용자라는 실체  | 이메일, 닉네임, 비밀번호 등                       |
| `File` | 업로드된 파일   | 파일명, 용량, 확장자, 저장 경로 등                  |

> **데이터베이스의 테이블 기준이자 핵심 비즈니스 개념**
-> 실무에서는 도메인을 먼저 도출한 후 거기에 맞는 API와 계층 구조를 짠다고 함

### Q2. 스프링의 계층 구조와 도메인 중심 설계(Domain-centric)은 어떻게 다를까?
> ** 계층 구조와 도메인 중심 설계는 다른 레벨의 이야기 **

#### 계층 구조 = 기술적인 구조
- Controller/Service/Repository로 기능을 **역할에 따라 나누는 것**
- 비즈니스 도메인이 뭔지 **관심 없음**
- `PostService`, `UserService` 같은 클래스는 그냥 **기능 담당자**

#### 도메인 중심 설계(Domain-Centric Design) = 비즈니스 중심 설계
- 도메인 중심으로 애플리케이션 구조를 설계
- 각 도메인의 **규칙, 행동 책임**을 먼저 고민
- DTO, Service 등을 도메인에 맞춰 붙임

> **DTO?**
> Data Transfer Object
- 계층 간 데이터 교환을 위한 순수 데이터 객체
- 주로 `Controller -> Service -> Repository` or 클라이언트와 서버 간 통신에서 사용

# 2. HTTP & REST

## 2.1 HTTP
- **Hypertext Transfer Protocol**
- 웹에서 데이터를 주고받기 위한 약속(통신 규칙)

### 클라이언트-서버 모델
- 클라이언트: 요청(request)를 보냄 
	-ex) 브라우저, Postman 등
- 서버: 요청을 처리하고 응답(response)를 돌려 줌

### 요청-응답 구조
```diff
[요청]
- 메서드 (GET, POST 등)
- URL
- 헤더
- 바디 (선택적)

[응답]
- 상태 코드 (200, 404, 500 등)
- 헤더
- 바디 (JSON 등)
```

## 2.2 HTTP 메서드(REST API 기반)

| 메서드        | 의미        | 예시                         |
| ---------- | --------- | -------------------------- |
| **GET**    | 리소스 조회    | `/api/posts/1` (게시글 1번 보기) |
| **POST**   | 리소스 생성    | `/api/posts` + 본문(JSON)    |
| **PUT**    | 리소스 전체 수정 | `/api/posts/1` + JSON      |
| **PATCH**  | 리소스 부분 수정 | 자주 생략됨                     |
| **DELETE** | 리소스 삭제    | `/api/posts/1`             |

## 2.3 REST

### API
- **Application Programming Interface**
- **프로그램 간 통신을 위한 약속**
- 한 시스템이 다른 시스템과 **정해진 방식대로 요청/응답**할 수 있게 해 줌
- ex) 프론트엔드(React)가 백엔드(Spring)에게 글 목록을 요청할 경우
	- `/api/posts`로 `GET` 요청을 보냄
    - 백엔드는 JSON으로 목록을 응답
    - 이 통신 형식이 **API**
- **'인터페이스'란 서로 다른 시스템 간의 소통 약속**
	- **어떤 경로(url)에,** 어떤 방식으로(GET/POST 등), 어떤 데이터 형식(JSON 등)으로 요청/응답할지를 정해 놓음

> **HTTP랑 API랑 둘 다 통신 약속 같은데 뭐가 다른 걸까?**

#### API VS HTTP: 둘은 뭐가 다를까?

| 구분     | API                                                          | HTTP                                                    |
| ------ | ------------------------------------------------------------ | ------------------------------------------------------- |
| **정의** | Application Programming Interface: 프로그램 간 **기능을 주고받기 위한 약속** | HyperText Transfer Protocol: 웹에서 **요청과 응답을 주고받는 통신 규칙** |
| **역할** | "어떻게 요청하고 응답할 것인지"의 틀 제공 (ex. 어떤 경로에 어떤 메서드로 어떤 데이터를 줄 건지)   | 그 요청/응답을 실제로 **전송하고 주고받는 통신 수단**                        |
| **관계** | API는 **HTTP 위에 올라가는 설계**                                     | HTTP는 **API가 실리는 운송 수단**                                |

#### 🚚 비유!
- **API = 택배 상자 안의 내용물 설계도 => 무엇을 담고 어떻게 열지 약속한 문서**
- **HTTP = 택배차 => 내용물을 목적지까지 전달해 주는 수단**

> 즉,
> **API는 '무엇을 요청하면 어떤 기능이 동작한다'라는 약속 => '기능 설명서'
> **HTTP는 그 약속을 질제로 요청하고 응답하는 방식(문법, 규칙) => '기능 요청서 작성 양식'

### REST
- **REpresentational State Transfer**
- API를 설계하는 방식 중 하나
- **HTTP 기반의 통신에서, 자원의 상태(데이터)를 표현하고 전달**하는 방식
- URL을 자원 중신(`/posts`, `/users`)로 표현하고, HTTP 메서드로 행위(조회, 생성 등)을 구분하여 **직관적이고 일관성 있는 API**를 만드는 것이 목표

#### REST의 원칙(6가지 제약 조건)
- **자원 중심(URI)**: `/posts`, `/users`처럼 명사로 자원 표현
- **행위는 HTTP 메서드로 표현**:  GET, POST, PUT, DELETE 등
- **무상태성(Stateless)**: 서버는 클라이언트의 상태를 기억하지 않고, 요청만 보고 판단

### REST API 구조 예시
| 요청                    | 의미           | 설명                           |
| --------------------- | ------------ | ---------------------------- |
| `GET /api/posts`      | 게시글 목록 조회    | 자원(posts)을 **조회**하는 요청       |
| `POST /api/posts`     | 게시글 생성       | 자원(posts)에 **새 항목을 추가**하는 요청 |
| `GET /api/posts/1`    | ID 1번 게시글 조회 | 특정 자원 조회                     |
| `PUT /api/posts/1`    | ID 1번 게시글 수정 | 특정 자원 **전체 수정**              |
| `DELETE /api/posts/1` | ID 1번 게시글 삭제 | 특정 자원 삭제                     |


# 3. @RequestBody & @ResponseBody

## 3.1 @RequestBody & @ResponseBody

| 어노테이션           | 역할                                |
| --------------- | --------------------------------- |
| `@RequestBody`  | **클라이언트가 보낸 JSON 데이터를 자바 객체로 변환** |
| `@ResponseBody` | **자바 객체를 JSON으로 변환해 응답 본문에 포함**   |

## 3.2 왜 필요할까?
- 기본적으로 스프링은 웹 요청을 받을 때,
	- 폼 방식(form-data)은 자동으로 파라미터 처리 가능
    - 하지만 **JSON 데이터**를 주고받으려면 **객체 <-> JSON 변환** 필요
- 이것을 자동으로 처리해 주는 게 `@RequestBody`, `@ResponseBody`
	- 내부적으로 Jackson이라는 라이브러리가 객체 <-> JSON 변환 담당
   
## 3.3 흐름(요청 <-> 응답)
```scss
[클라이언트] JSON 요청
  ↓                  ↑
@RequestBody     @ResponseBody
  ↓                  ↑
[서버 내부]  자바 객체 ↔ 자바 객체

```

## 3.4 정리

| 항목                | 내용                                    |
| ----------------- | ------------------------------------- |
| `@RequestBody`    | JSON → 자바 객체 (요청 받을 때 사용)             |
| `@ResponseBody`   | 자바 객체 → JSON (응답 보낼 때 사용)             |
| 내부 변환기            | `HttpMessageConverter` + Jackson      |
| `@RestController` | `@Controller + @ResponseBody` (전역 적용) |

> 추가 공부 검색 키워드
>- Jackson ObjectMapper
>- HttpMessageConverter 원리
>- Spring JSON 직렬화/역직렬화

# 4. Entity VS DTO

## 4.1 Entity
- **Entity 클래스는 데이터베이스 테이블과 1:1로 매핑되는 자바 객체**
- 매핑: 클래스의 필드 하나하나가 DB 테이블의 **컬럼**과 연결된다는 의미
- ex) `post` 엔티티가 존재할 경우,
```java
@Entity
public class Post {
    @Id @GeneratedValue
    private Long id;       // -> DB의 id 컬럼
    private String title;  // -> DB의 title 컬럼
    private String content;// -> DB의 content 컬럼
}
```
- 이 `Post` 클래스는 `post` **테이블**과 연결
- 필드들은 각각 **테이블의 컬럼**
- **DB에 저장하거나 불러오는 주체** => `Entity`

## 4.2 DTO(Data Transfer Object)
- **DTO는 데이터를 담아서 전달하기 위한 가방 같은 객체**
- Controller  <-> Service <-> Client 사이에서 **오직 전달 역할만** 함
- ex) `PostRequestDto`가 있는 경우,
```java
public class PostRequestDto {
    private String title;
    private String content;
}
```
- 이 DTO는 DB랑 관련 X
- 그냥 클라이언트가 `title`, `content`를 보내 주면 -> 여기에 담아서 서비스로 넘기는 용도

## 4.3 Entity VS DTO

| 항목    | Entity                 | DTO (Data Transfer Object)            |
| ----- | ---------------------- | ------------------------------------- |
| 목적    | **DB 테이블과 매핑**되는 클래스   | **데이터 전송용** 클래스 (계층 간 전달)             |
| 역할    | 비즈니스 도메인 객체 (핵심 모델)    | 클라이언트 ↔ 서버 간의 데이터 구조 정의               |
| 위치    | `domain`, `entity` 패키지 | `dto` 패키지                             |
| 포함 정보 | DB 필드, 연관 관계, 비즈니스 메서드 | 필요한 필드만 포함 (보통 getter/setter만)        |
| 예시    | `Post`, `User` 등       | `PostRequestDto`, `PostResponseDto` 등 |

## 4.4 왜 Entity를 그대로 쓰지 않을까?

### Entity를 직접 사용하면 생기는 문제
- **API 응답 구조 변경 시** DB 설계를 수정해야 함 (응답에 맞춰야 해서)
- **보안 문제**: 비밀번호 등 민감한 정보 노출 가능성
- **요구사항과 불일치**: 클라이언트가 원하는 필드와 Entity 구조가 다를 수 있음
- **양방향 연관관계**로 인해 JSON 순환 참조 에러 발생 가능

### DTO를 사용했을 때 이점
- 응답/요청에 맞는 **가벼운 객체 정의 가능**
- Entity 변경 없이 API 응답 구조 변경 가능
- Validation 적용 가능
- API 문서화에 용이(Swagger 등)

## 4.5 구조

### 엔티티
```java
@Entity
public class Post {
    @Id @GeneratedValue
    private Long id;
    private String title;
    private String content;
}
```
### DTO: 요청용
```java
public class PostRequestDto {
    private String title;
    private String content;
}
```
### DTO: 응답용
```java
public class PostResponseDto {
    private Long id;
    private String title;
    private String content;
}
```
### 흐름
```typescript
클라이언트 JSON 요청
        ↓
 @RequestBody PostRequestDto
        ↓
 Service 계층 → Post Entity로 변환
        ↓
 Repository 저장
        ↓
 Post Entity → PostResponseDto 변환
        ↓
 @ResponseBody PostResponseDto
        ↓
클라이언트에게 JSON 응답

```
# 5. 트랜잭션 처리 흐름

## 5.1 트랜잭션(Transaction)
- **모든 작업이 전부 성공하거나, 전부 실패해야 한다"는 원자성의 원칙 보장**

### 예시: 게시글 수정 요청
```java
@Transactional
public void update(Long id, String title, String content) {
    Post post = postRepository.findById(id).orElseThrow();
    post.update(title, content);
}
```
- 위 코드에서  `findById()`로 가져온 객체에 `update()`를 적용하고 끝냈는데,
- **만약 도중에 예외가 터지면?**
- 데이터 이상하게 저장될 가능성 생김

** => 그래서 트랜잭션을 걸어 놓으면 **
- 예외가 발생하면 **롤백(rollback)**
- 예외 없이 성공하면 **커밋(commit)**

## 5.2 Spirng에서의 트랜잭션 처리 방법

### @Transactional 어노테이션
```java
@Service
@Transactional
public class PostService {
    ...
}
```
- `클래스에 붙이면`: 전체 메서드에 트랜잭션 적용
- `특정 메서드에만 붙이면`: 해당 메서드만 트랜잭션 적용
=> 지금 **JPA 기반** 개발이기 때문에 트랜잭션 없이 DB 반영 안 될 가능성 있음

### 내부 동작 흐름
1. Controller -> Service 메서드 호출
2. `@Transactional`이 적용된 메서드 실행 시작
3. 내부에서 DB에 대한 변경 발생
4. 성공적으로 종료되면 commit
5. 중간에 예외 발생하면 rollback

### 왜 써야 할까?

| 이유         | 설명                                  |
| ---------- | ----------------------------------- |
| 안정성 보장     | 중간 실패 시 데이터 꼬임 방지                   |
| JPA 쓰려면 필수 | 변경 감지(Dirty Checking)가 트랜잭션 안에서만 동작 |
| 롤백 제어      | 예외 시 rollback 자동 수행 가능              |

# 6. Post 도메인 코드 리뷰

## 6.1 PostController: 프레젠테이션 계층(Controller 클래스)
```java
@RestController //API 전용 컨트롤러 선언
@RequiredArgsConstructor
@RequestMapping("/api/posts")
public class PostController {

    private final PostService postService;

    @PostMapping //HTTP 메서드로 RESTful API 구성
    public ResponseEntity<Post> create(@RequestBody Post post) {
    //@RequestBody Post post => 클라이언트의 JSON 데이터를 객체로 매핑
        return ResponseEntity.ok(postService.create(post));
    }

    @GetMapping //HTTP 메서드로 RESTful API 구성
    public ResponseEntity<List<Post>> findAll() {
        return ResponseEntity.ok(postService.findAll());
    }

    @GetMapping("/{id}") //HTTP 메서드로 RESTful API 구성
    public ResponseEntity<Post> findById(@PathVariable Long id) {
        return postService.findById(id)
                .map(ResponseEntity::ok)
                .orElse(ResponseEntity.notFound().build());
    }

    @PutMapping("/{id}") //HTTP 메서드로 RESTful API 구성
    public ResponseEntity<Void> update(@PathVariable Long id, @RequestBody Post post) {
        postService.update(id, post.getTitle(), post.getContent());
        return ResponseEntity.ok().build();
    }

    @DeleteMapping("/{id}") //HTTP 메서드로 RESTful API 구성
    public ResponseEntity<Void> delete(@PathVariable Long id) {
        postService.delete(id);
        return ResponseEntity.noContent().build();
    }
}
```

- `@RestController` → API 전용 컨트롤러 선언
- `@RequestBody Post post` → 클라이언트의 JSON 데이터를 객체로 매핑
- `@PostMapping`, `@GetMapping` 등 → HTTP 메서드로 RESTful API 구성
- `PostService`를 호출해서 처리 위임 → Controller는 로직 처리 안 함

👉 역할 요약: "HTTP 요청을 받고 응답하는 것만 담당, 로직은 Service에게 위임"

## 6.2 PostService: 비즈니스 로직 계층 (Service 클래스)
```java
@Service
@RequiredArgsConstructor
public class PostService {

    private final PostRepository postRepository;

    public Post create(Post post) {
        return postRepository.save(post);
    }

    public List<Post> findAll() {
        return postRepository.findAll();
    }

    public Optional<Post> findById(Long id) {
        return postRepository.findById(id);
    }

    @Transactional
    public void update(Long id, String title, String content) {
        Post post = postRepository.findById(id).orElseThrow();
        post.update(title, content);
    }

    public void delete(Long id) {
        postRepository.deleteById(id);
    }
}
```
- `@Service` → 비즈니스 로직을 담당하는 계층임을 선언
- `@Transactional` → 수정 시 트랜잭션 보장 + JPA 변경 감지 활성화
- `postRepository.findById(...).orElseThrow()` → 예외 처리로 안정성 확보
- 엔티티 내부 `post.update(...)`를 통해 필드 수정

👉 역할 요약: "비즈니스 처리와 트랜잭션 책임. Repository 호출은 여기서 한다"

# 6.3 PostRepository: 데이터 접근 계층 (Repository 클래스)
```java
public interface PostRepository extends JpaRepository<Post, Long> {
}

```
- `JpaRepository` 상속 → Spring Data JPA가 구현체 자동 생성
- CRUD 메서드 (`save`, `findAll`, `findById`, `deleteById`) 기본 제공

👉 역할 요약: "DB와 통신하는 계층, JPA가 알아서 SQL 날려줌"

# 6.4 Post: Entity 클래스
```java
@Entity
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Post {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;
    private String content;

    @Builder
    public Post(String title, String content) {
        this.title = title;
        this.content = content;
    }

    public void update(String title, String content) {
        this.title = title;
        this.content = content;
    }
}
```
- `@Entity` → 이 클래스는 DB 테이블과 매핑됨
- `@Id @GeneratedValue(...)` → 기본 키 + 자동 증가
- `@Builder` → 객체 생성 시 가독성 좋게
- `update(...)` → Service에서 변경 감지 시 호출됨

👉 역할 요약: "DB 테이블과 매핑되는 도메인 클래스, JPA가 영속성 관리"
