## inner join과 outer join차이
- inner join : 교집합
- outer join : 특정 테이블을 기준으로 데이터를 보여 줌
- left outer join : 왼쪽 테이블을 기준으로 join -> 왼쪽 테이블 A와 A, B 테이블의 중복 데이터들이 검색됨
- right outer join : 오른쪽 테이블을 기준으로 join -> 오른쪽 테이블 B와 A, B 테이블의 중복 데이터들이 검색됨
- full outer join : 왼쪽 테이블과 오른쪽 테이블의 합집합 -> 만약 A에 데이터가 있지만 B에 데이터가 없다면 B 부분은 null, 반대의 경우는 A 부분이 null

## 데이터베이스 다중화란?

### 다중화(이중화)
- 같은 시스템을 가진 예비 장치 여러 개를 준비해, 시스템 일부에 장애가 발생해도 서비스를 계속 유지할 수 있도록 하는 것
- DB 서버는 데이터를 보존하는 영속(Persistence) 계층이기 때문에 다른 서버에 비해 다중화에 대해 고민해야 할 부분이 많음

#### DB와 다른 서버의 차이
- 데이터를 일시적으로 처리하는 웹/앱 서버와 달리, DB는 데이터를 장기간 보존하는 매체가 필요한데
-따라서, ** DB 서버의 아키텍처는 서버와 저장소를 묶어서 생각해야 함 **
- 항상 갱신되는 데이터 사이에서 다중화를 유지하면서 데이터의 정합성도 의식이 요구됨

> ** 데이터 정합성(Data Consistency) **
- 어떤 데이터들이 값이 서로 일치하는 상태
- 비정규형을 사용해 아노말리(anomaly : 이상현상)가 발생하면 정합성 지켜지지 않음

>** 데이터 무결성(Data Integrity) **
- 데이터 값이 정확한 상태
- 무결성을 지키는 것이 데이터 모델링의 최고 목표


### 클러스터링 : DB 서버의 다중화 
![](https://velog.velcdn.com/images/emprimula/post/300a9c28-41e3-4bfa-bffc-37e127c2e82f/image.png)
- DB 서버는 다중화, 저장소는 한 개
- 데이터가 보존되는 저장소가 하나라서 정합성 신경 X
- db 서버가 2대지만, 2대가 동시 동작하는 것을 허락할지에 따라 Active-Active와 Active-Standby 두 가지로 나뉨

#### 클러스터링
- 여러 개의 DB를 수평적인 구조로 구축하는 방식
- 분산 환경을 구성 -> Single point of failure 같은 문제를 해결할 수 있는 Fail Over 시스템 구축을 위해 사용
- 동기 방식으로 데이터를 동기화

#### 클러스터링 처리 방식
![](https://velog.velcdn.com/images/emprimula/post/ea62d7bf-9f8e-469d-a790-e926dda8e7e4/image.png)
```
0. MySQL의 Clustering 방식 중 Galera 방식
1. 1개의 노드에 쓰기 트랜잭션 수행, COMMT 실행
2. 실제 디스크에 내용을 쓰기 전에 다른 노드로 데이터의 복제를 요청
3. 다른 노드에서 복제 요청을 수락했다는 신호를 보내고, 디스크에 쓰기 시작
4. 다른 노드로부터 신호를 받으면 실제 디스크에 데이터를 저장
```

#### 클러스터링 장단점
**장점**
- 노드들 간의 데이터를 동기화하여 항상 일광성 있는 데이터 얻을 수 있음
- 1개의 노드가 죽어도 다른 노드가 살아 있어 시스템을 계속 장애없이 운영 가능

**단점**
- 여러 노드들 간의 데이터를 동기화하는 시간이 필요하므로 리플리케이션에 비해 쓰기 성능이 떨어짐
- 장애가 전파된 경우 처리가 까다로우며, 데이터 동기화에 의해 스케일링에 한계가 있음

#### Active-Active : 동시 가동
![](https://velog.velcdn.com/images/emprimula/post/763b7628-9415-45a1-9d15-a32ece6bbfea/image.png)
- 복수의 DB 서버가 동작하고 있어 한 대가 동작 불능이 되어도 남은 서버가 처리를 계속하기 때문에 ** 시스템 다운 방지** 가능
- 복수의 DB 서버의 자원(CPU, Memory)을 사용하여 성능을 향상시키지만, 저장소가 병목되기 때문에 생각한 만큼 성능 향상이 되지 않는 경우도 있음


#### Active-Standby : 실제 가동하는 것은(Active), 나머지는 대기(Standby)
![](https://velog.velcdn.com/images/emprimula/post/26ef2aba-937b-490c-97ab-f2f1c17024bf/image.png)
- 보통 Standby 상태의 DB 서버는 사용되지 않다가 Active DB 서버에서 장애가 일어날 경우에 사용
- Standby DB 서버가 Active로 전환되기까지 시간 소모 존재, 이 시간 동안 시스템 다운 상태
- Standby DB는 일정 간격마다 Active DB에 이상이 없는지 조사를 위한 통신(Heartbeat)을 하여 장애 여부를 조사

**Active-Standby 구성 종류**
-Cold-Standby : 평소에는 Standby DB가 작동하지 않다가 Active DB가 다운된 시점에서 작동하는 구성
-Hot-Standby : 평소에도 Standby DB 작동하는 구성
-> 항상 2대의 DB 서버를 사용하고 있기 때문에 전환 시간은 짧지만, 비용이 더 비싸며 실제로 작동하는 것은 Active DB 1대뿐이기 때문에 사치스러운 구성임

### 리플리케이션 : DB 서버와 데이터의 다중화
- DB 서버와 다르게 저장소는 다중화할 수 없음 => 데이터를 다중화하지 않는 단점 존재
- 만약 저장소에 결함이 생겨 부서진다면 데이터를 잃을 수 있음
- 저장소도 보통 내부 컴포넌트는 다중화되어 있음 => BUT, 데이터 센터 전체가 말소된다면 방법 X

#### 리플리케이션
- 위의 상황을 예방하기 위한 클러스터 구성
- DB 서버와 저장소 세트를 복수로 준비하는 것
![](https://velog.velcdn.com/images/emprimula/post/8db4d07f-f5a2-45f9-8f94-a42ad1dc77f0/image.png)
- DB 서버와 저장소가 함께 죽어도 다른 세트로 대체하여 서비스를 지속 가능하다는 부분에서 가용성이 매우 높은 아키텍처

#### 리플리케이션 처리 방식
- 여러 개의 DB를 권한에 따라 수직적인 구조(Master-Slave) 구조로 구축하는 방식
- Master Node : 쓰기 작업만 처리
- Slave Node : 읽기 작업만 처리
![](https://velog.velcdn.com/images/emprimula/post/a693b5eb-e3cb-4c42-a315-07003bfc9926/image.png)
```
0. MySQL 리플리케이션 방식임
1. Master Node에 쓰기 트랜잭션 수행
2. Master Node는 데이터를 저장하고, 트랜잭션에 대한 로그를 파일에 기록 <= BIN LOG
3. Slave Node의 IO Thread는 Master Node의 로그 파일(BIN LOG)를 파일(Replay Log)에 복사
4. Slave Node의 SQL Thread는 파일(Replay Log)를 한줄씩 읽으면서 데이터 저장
```
- 리플리케이션은 Master와 Slave 간의 데이터 무결성 검사(데이터가 일치하는지)를 하지 않는 비동기 방식으로 데이터를 동기화

#### 리플리케이션 장단점

** 장점 **
- DB 요청의 60% ~ 80% 정도가 읽기 작업이기 때문에, 리플리케이션만으로도 충분히 성능을 높힐 수 있음
- 비동기 방식으로 운영되어 지연 시간이 적음

** 단점 **
- 노드들 간의 데이터 동기화가 보장되지 않아 일관성 있는 데이터를 얻지 못할 수 있음
- Master Node가 다운되면 복구 및 대처가 까다로움

## 데이터베이스 최적화 기법에 대해서 어느정도 알고 있는가?

### 데이터베이스 성능 최적화 (Database Perfomance Optimization)
- 데이터베이스 시스템의 효율성을 극대화하여 데이터 저장, 검색 및 처리 속도를 향상시키는 과정
- 성능 최적화는 데이터베이스 응답 시간을 줄이고, 시스템 자원을 효율적으로 사용하며, 사용자 경험을 향상시키는 데에 중요한 역할을 함

> **DBMS가 데이터를 더 빠르고 효율적으로 조회/처리하도록 하는 모든 방법**

#### 데이터베이스 성능 최적화 주요 point

**1) 응답 속도 VS 처리량**
- 응답 속도(Response Time) : 특정 요청이 처리될 때 걸리는 시간
- 처리량(Throughput) : 단위 시간당 처리할 수 있는 요청 개수
- 성능 최적화는 응답 속도 단축과 처리량 증가를 목표로 함

**2) 병목 현상(Bottleneck)**
- 특정 요소(쿼리, 인덱스, 트랜잭션 등)에서 성능이 저하되는 현상
- 주로 디스크 I/O, CPU 사용량, 네트워크 대역폭, 데이터베이스 락 등의 원인

**3) 데이터 접근 방식 개선**
- 최소한의 데이터만 조회
- JOIN 연산 최적화
- 트랜잭션 최소화

### 데이터베이스 최적화 기법

#### 1) SQL 쿼리 최적화
- SELECT * 지양 : 필요한 컬럼만 조회 => 불필요한 데이터 로딩 방지
```
-- 비효율적인 쿼리
SELECT * FROM users;

-- 최적화된 쿼리
SELECT id, name, email FROM users;

```

- 서브쿼리(Subquery) 대신 JOIN 활용 : 서브쿼리는 실행 성능이 낮음 => JOIN 사용
```
-- 비효율적인 쿼리 (서브쿼리)
SELECT name FROM users WHERE id IN (SELECT user_id FROM orders);

-- 최적화된 쿼리 (JOIN 활용)
SELECT users.name FROM users JOIN orders ON users.id = orders.user_id;

```
> 서브쿼리 대신 조인 활용하라는 소리에서 그냥 궁금해진 건데 JOIN을 사용하면 성능이 안 좋아진다는 말이 있는데 JOIN을 서브쿼리가 성능이 나쁘기 때문에 대신 사용하라는 말이 뭔가 모순적으로 들림 => 따로 찾아봐야 할 듯? ❓
- WHERE절 최적화
(1) LIKE '%검색어%'보다 Full-Text-Search 또는 B-Tree 인덱스 활용
(2) OR 대신 UNION 또는 IN 사용하여 최적화

#### 2) 인덱스(Index) 활용
(1) 인덱스
- 데이터 검색 속도 향상시키는 자료구조
- 인덱스가 많으면 INSERT/UPDATE 성능 저하
(2) 유형
- B-Tree 인덱스 : 범위 검색 최적화
- Hash 인덱스 : = 연산에 유리
- Full-Text 인덱스 : 텍스트 검색 최적화
- Composite Index(복합 인덱스) : 다중 컬럼 검색 최적화
(3) 인덱스 활용 예시
```
-- 특정 컬럼에 인덱스 추가
CREATE INDEX idx_users_email ON users(email);

-- 복합 인덱스 활용 (name과 age를 함께 검색할 경우)
CREATE INDEX idx_users_name_age ON users(name, age);

```
#### 3) 데이터베이스 설계 최적화
(1) 정규화 (Normalization)
- 중복 데이터를 최소화 하여 무결성 유지
(2) 반정규화 (Denormalization)
- 조회 성능 최적화를 위해 중복을 허용하여 데이터를 구조화
(3) 파티셔닝(Partitioning)
- 대용량 테이블을 작은 단위로 분할하여 성능 향상
#### 4) 캐싱(Caching) 활용
- 동일한 쿼리를 반복 실행하면 성능 저하 발생 => 캐싱으로 해결
- 애플리케이션 레벨 캐싱 : Redis, Memcached
- 데이터베이스 쿼리 캐싱 : MySQL Query Cache)
#### 5) 트랜잭션(Transaction) 최적화
- 트랜잭션 짧고 빠르게 실행
- AUTOCOMMIT을 비활성화하여 불필요한 트랜잭션 방지
#### 6) 분산 처리 및 샤딩(Sharding)
- 데이터가 많아지면 단일 DB에서 처리 불가 => 분산 저장 필요
- 수직 샤딩 : 데이터 분할
- 수평 샤딩 : 데이터를 여러 서버에 나눠 저장

## 샤딩(Sharding)

### Sharding 
- 데이터를 여러 DB에 분산하여 저장하는 방식
- 일괄적 관리가 힘든 거대 DB나 네트워크를 작게 나눠서 저장하고 관리하는 방법
- 특정 DB의 장애가 전면 장애로 이어지지 않게 하는 역할도 함
![](https://velog.velcdn.com/images/emprimula/post/a7a8ae6d-d7d6-45e7-ad4d-1a7af69130aa/image.png)
![](https://velog.velcdn.com/images/emprimula/post/4a42a390-5eb8-4a2b-bb6f-725281cd708e/image.png)

### 핵심 목표
- 용량 한계 극복
- 성능(속도) 개선
- 장애 범위 최소화

### 수평적 파티셔닝 VS 샤딩
- 샤딩은 수평 파티셔닝 일종으로 볼 수 있음
**BUT,**
- 수평적 파티셔닝 : 동일한 DB 서버 내에서 테이블을 분할하는 것
- 샤딩 : DB 서버를 분할
** 즉, 샤딩은 DB 서버의 부하를 분산할 수 있는 것, 데이터베이스 차원의 수평 확장(sacle-out)이라고 볼 수 있음**
![](https://velog.velcdn.com/images/emprimula/post/d7d92f35-5e47-4dcc-8637-37a5ea0b88ad/image.png)

### 샤딩 장단점
**장점**
- 수평 확장 가능
- 스캔 범위를 줄여 쿼리 반응 속도를 빠르게 함
- 장애가 샤드 단위로 발생함

**단점**
- 프로그래밍 복잡도 증가 : 데이터 쪼개고, 찾고, 합치는 로직 직접 짜야 함
- 데이터 재분배 어려움 : 샤드 추가/삭제 시 기존 데이터 위치 변경 필요
- 쿼리 제약 : JOIN, 트랜잭션 기능 쓰기 어려움
- 장애 관리 어려움 : 특정 샤드에 장애 나면 해당 데이터만 다운 (데이터 조각남)
- 되돌리기 어려움 : 한번 샤딩 구조로 가면 원래 단일 DB로 쉽게 못 돌아옴

> 단점으로 인해 샤딩은 마지막 선택지
1. 데이터베이스 서버의 **Scale-Up** (서버 성능 업그레이드)
2. **Read** 부하가 클 경우 **Cache 사용 및 Database Replication**
3. 테이블 일부 컬럼만 주로 사용할 경우 **Vertical Partitioning**

### 샤딩 종류

- PK(Primart Key) : 각 데이터의 주민등록번호
- 라우팅 : "이 데이터는 어느 샤드(DB)에 저장해야 하는지 결정"하는 과정

### 1. 모듈러 샤딩(Modular Sharding)
- 데이터를 "PK 번호 끝자리"로 나눠 담는 방식
![](https://velog.velcdn.com/images/emprimula/post/4b0611d2-9f5d-4f18-92a7-a144d0785b3b/image.png)
- 레인저 샤딩에 비해 ** 데이터가 균일하게 분산 **
- 서버 추가 시, 기존 데이터 재분배 필요 (PK 끝자리 분배 룰이 바뀌니까)
- 데이터가 일정 수준에서 예상되는 데이터 성격을 가진 곳에 적용할 때 어울림
- 데이터가 균일하게 분산된다 => 트래픽을 안정적으로 소화하면서도 DB 리소스를 최대한 활용할 수 있음을 의미

**비유**
- PK 끝자리로 반 편성하는 느낌 : "출석번호 끝자리가 1이면 A반, 2면 B반"

### 2. 레인지 샤딩
-  데이터를 "PK 범위"로 나눠 담는 방식
![](https://velog.velcdn.com/images/emprimula/post/6a02c596-7659-4f86-a8ec-5a2ef420ee2a/image.png)
- 데이터 추가 시 순차적으로 저장되어 관리 쉬움
- 모듈러 샤딩에 비해 기본적으로 증설에 재정렬 비용이 들지 않음
- 일부 DB에 데이터가 몰릴 수 있음 => 과부하 (Hotspot 문제)
- 데이터가 급격히 증가할 여지가 있다면 좋은 선택
- 활성 유저가 몰린 DB로 트래픽이나 데이터량이 몰릴 수 있음 => 몰리는 DB는 분산시키고 트래픽이 저조한 DB는 통합시키는 과정이 필요 
=> 따라서 적절한 Range 기준을 잡는 것이 중요

**비유**
- 학년별로 반 편성하는 느낌 : "1학년은 1반, 2학년은 2반"

### 3. 디렉토리 샤딩
- "주소록 테이블"을 하나 만들어서, 각 데이터마다 "이 데이터는 어느 샤드에 있어요!"라고 기록하는 방식
![](https://velog.velcdn.com/images/emprimula/post/052a0eae-9edf-4f16-b428-da8eacfb65f2/image.png)
- 데이터 분산 규칙 자유롭게 변경 가능
- 샤드 추가/삭제 시 유연함
- 매번 "주소록 조회"해야 해서 성능 좀 손해 

**비유**
- 전화번호부에서 친구 주소 찾는 느낌 : “철수는 1동 302호, 영희는 2동 501호”

```
1. 팁 요약
✅ 샤딩은 "필요할 때만" 하는 고난이도 기술
✅ 모듈러는 PK 끝자리로 분산 = 균등하지만 재분배 어려움
✅ 레인지는 범위별 분산 = 관리 쉽지만 쏠림 위험
✅ 디렉토리는 주소록 테이블로 위치 관리 = 유연하지만 매번 조회 오버헤드
✅ 샤딩 전에 반드시 "캐시", "Scale-Up", "리플리케이션" 먼저 고려!

2. 흐름 정리 
✅ 샤딩은 데이터 너무 많아서 1서버로 감당 안 될 때 선택
✅ 하지만 복잡도+유지관리 부담 커서 최후의 수단
✅ 종류는 크게 3가지 (모듈러, 레인지, 디렉토리)
✅ 각각 분산 규칙/장단점 다름
✅ 데이터 특성 따라 적합한 방법 선택해야 함
✅ 샤딩 이후엔 되돌리기 어려움 = 설계 시 신중해야 함

```

## 사용해본 DB들의 장단점 🔺
- MySQL이랑 PostgreSQL만 써 봤는데 장단점까지... 잘 못 느끼겠어서 일단 보류

### MySQL
- 장점 : 오픈 소스, 쉬운 설정, 읽기 성능 우수, 다양한 인덱스 지원
- 단점 : 복잡한 쿼리에서 성능 저하 발생 가능, 대량 데이터에서 확장성 문제 발생 가능

### PostgreSQL
- 장점 : 강력한 트랜잭션 기능, JSON 데이터 지원, 복잡한 쿼리 최적화 강점
- 단점 : 설명이 복잡하고 학습 곡선이 높음

** => 이건 걍 이론적인 관점이고 내가 DB를 사용한다면 둘이 어떤 점을 비교해서 사용해야 할까? **

### 성능 (Performance)
- MySQL : 읽기 성능이 Good (읽기 위주 시스템에 적합)
- PostgreSQL : 쓰기 성능 Good + 복잡한 트랜잭션과 다중 쿼리 처리 Good

### 트랜잭션 & 데이터 정합성 (ACID & Consistency)
- MySQL :InnoDB 엔진이 ACID를 보장하지만, 일부 제약 존재
- MVCC(다중 버전 동시성 제어) 사용 -> 강력한 트랜잭션 처리 성능 제공

### 확장성 (Scalability)
- MySQL : 수평 확장 용이, 대형 트래픽 서비스에서 MySQL Replication 활용 가능
- PostgreSQL : 수직 확장 용이, 수평 확장은 어려움, 복제 기능은 있지만 MySQL보다 설정이 복잡함

### 데이터 유형 & JSON 지원
- MySQL : JSON 데이터를 지원하지만 제약이 많음 
- PostgreSQL : JSONB 타입을 지원 -> 훨씬 유리함

### 복잡한 쿼리 최적화
- MySQL : 복잡한 조인이나 서브쿼리에서 성능 저하 발생 가능
- PostgreSQL : 쿼리 옵티마이저가 강력하여 복잡한 SQL 처리 최적화 가능

** 내가 혼자 해 보는 프로젝트 스케일에선 MySQL이 제일 편하고, 차이를 느끼기도 쉽지 않아 보여서 MySQL을 자주 써 보게 된 것 같음**

## 캐시와 디비 성능차이 
- 개발하며 데이터를 저장하는 방식에는 크게 캐시와 DB가 있음

### 저장소 구분(메모리 기반 VS 디스크 기반)

#### 메모리 기반 저장소 => 캐시
- RAM 같은 메모리 장치를 사용하여 데이터를 저장
- 머릿속에 정보를 담아 놓는 느낌 => 필요할 때 즉시 꺼내 쓸 수 있어 매우 빠름
- BUT 휘발성 (전원 끄면 데이터 날아감)

** 특징 **
- 빠른 데이터 접근 : 메모리는 데이터 접근 속도가 매우 빨라, 고성능이 요구되는 환경에서 자주 사용
- 휘발성 : 임시 데이터 저장 or 빠른 접근이 필요한 데이터 캐싱에 사용
- 비용 : 메모리는 비싸서 대량 데이터 오랫동안 저장 용도 X

#### 디스크 기반 저장소 => DB
- HDD, SSD 같은 디스크 장치를 사용하여 데이터를 저장
- 책장에 책을 꽂아 놓는 느낌 => 정보 영구 보관 가능, 필요한 정보 찾는 시간은 더 걸림

** 특징 **
- 데이터 영속성 : 중요 정보 장기간 보관 적합
- 상대적으로 느린 접근 속도 : 대량 데이터 처리, 복잡한 쿼리에 많은 시간 소요
- 비용 효율적 : 상대적으로 저렴

### 원리
- 메모리 기반 캐시 시스템 => 메모리가 전기 신호를 사용해 데이터에 직접 접근해서 빠름
- 디스크 접근 방식은 물리적인 움직임이 필요해서 비교적 느림
- 자주 사용되는 데이터 => 메모리 기반 캐시에 저장하여 빠르게 접근
- 변경 X 데이터, 영구적 저장 필요 데이터 => 디스크 기반 DB로 관리

#### 메모리 기반 => 캐시 시스템
- 데이터를 RAM에 저장
- RAM은 컴퓨터의 주 메모리, CPU가 직접 접근할 수 있는 고속 휘발성 저장소

** 특징 **
- 데이터 접근 속도 : 전기 신호 사용 데이터 저장 및 접근 => 매우 빠름
- 휘발성 : 전원이 공급되는 동안만 유지
- 직접 접근 : 메모리의 어떤 부분에서도 직접 접근하여 즉시 데이터를 읽거나 쓸 수 있음

#### 디스크 기반 => 데이터베이스
- 데이터를 HDD, SDD 같은 디스크에 저장
- 디스크는 데이터를 영구적으로 저장할 수 있는 비휘발성 저장소

** 특징 **
- 데이터 접근 속도 : HDD는 회전하는 디스크와 이를 읽고 쓰는 헤드를 이용해서 데이터를 저장 => 물리적인 움직임 / SSD는 반도체를 사용하여 데이터를 저장 => HDD보단 빠르지만 RAM보단 느림
- 비휘발성 : 영구 저장
- 순차적/랜덤 접근 : HDD => 순차적 접근 최적화, 랜덤 접근은 상대적으로 느림 / SSD => 랜던 접근 최적화, RAM보단 느림

## 캐시 왜 사용하는지 

### 캐시가 필요한 이유
**1) 데이터 조회 속도 향상**
- DB를 직접 조회하면 디스크 I/O가 발생해서 느려짐
- 자주 조회되는 데이터는 캐시에 저장하면 DB 부하 없이 빠르게 조회 가능
**2) DB 부하 감소**
- 고객이 몰리는 서비스(트래픽 폭증)에서 DB 부하를 줄이기 위해 캐시 활용
✔ 캐시를 쓰지 않으면?
- 수많은 사용자가 동일 DB 쿼리 실행 => DB 과부하 발생 & 서버 응답 속도 느려짐
✔ 캐시를 사용하면?
- 자주 조회되는 데이터는 캐시에서 제공 => DB 부하 감소 & 빠른 응답 가능
**3) 비용 절감**
- DB 서버를 확장(Scaling up) 하는 것은 비용이 큼
- 캐시 서버(Redis, Memcahed)를 추가하면 저렴한 비용으로 성능 향상 가능

>**의문점** 🔺
 "캐시는 메모리를 사용하므로 비싸다" vs "캐시는 비용을 절감할 수 있다" 이 두 가지가 모순으로 보임
 => 1차 조사
> 캐시는 비싸지만 전체 비용을 줄일 수 있다!
✅ RAM은 비싸지만, DB 확장을 줄이면 전체 비용을 절감할 수 있음.
✅ 캐시는 DB 부하를 줄여서 서버 비용을 아끼는 효과가 있음.
✅ 클라우드 환경에서는 네트워크 비용도 줄여서 더 큰 비용 절감이 가능함.
✅ 결과적으로, "캐시 비용 < DB 확장 비용"이므로 캐시를 활용하면 경제적임!

**4) 네트워크 응답 시간 단축**
- DB 서버가 원격지(클라우드)일 경우, 캐시를 사용하면 네트워크 비용 절감
- CDN 캐시(CloudFront, Akamai 등) 사용하면 이미지, 정적 파일 빠르게 제공

**추가로 궁금한 거** 🔺

> ** 1. Cache 사용 전략 **
- Write-Through Cache (DB와 동시에 캐시 저장)
- Write-Back Cache (캐시에 먼저 저장 후 나중에 DB 저장)
- Lazy Loading (DB 조회 시 캐시에 저장)
- Cache Eviction Policy (LFU, LRU, FIFO)

>** 2. Redis & Memcached 비교 **
- Redis: Key-Value + 데이터 구조 지원(List, Set, Hash)
- Memcached: 순수 Key-Value 저장, 메모리 최적화

>** 3. DB Index와 Cache 비교 **
- DB Index는 데이터 조회 속도를 빠르게 하지만, 캐시만큼 빠르지는 않음.
- 캐시는 DB 자체를 거치지 않음 → 속도 차이가 큼.

## 정규화와 비정규화를 알고 있는가? 🔺

### 정규화(Normalization)
- 데이터 중복 최소화, 무결성을 보장하기 위한 DB 설계 기법
- 장점 : 데이터 중복 방지, 저장 공간 절약, 데이터 무결성 유지
- 단점 : JOIN이 많아질 수 있어 읽기 성능 저하 가능

**1NF -> BCNF까지 다시 읽어 봐야 할 듯 (기억이 안 남)**

### 비정규화(Denormalization)
- JOIN을 줄이고 조회 성능을 높이기 위해 일부 데이터 중복을 허용하는 설계 방식
- 장점 : 읽기 성능 향상, 빠른 조회 가능
- 단점 : 데이터 중복으로 인해 저장 공간 증가, 데이터 정합성 유지 어려움

### 언제 사용?
- 쓰기(INSERT, UPDATE)가 많으면 정규화
- 읽기(SELECT)가 많으면 비정규화

## RDB랑 NOSQL 차이를 아는지? 🔺
=> 뭔가 차이는 알겠는데 와닿지 않는 느낌? 

### RDB (관계형 데이터베이스)
- Oracle, MySQL, MS-SQL, PostgreSQL, MariaDB 등
- 사전에 엄격하게 정의된 DB 스키마를 요구하는 table 기반 데이터 구조를 가짐
- 스키마를 사전에 정의해야만 함
- 데이터 중복이 없기 때문에 UPDATE가 많을 때 유리

### NoSQL (Not Only SQL)
- Mongodb, cassandra, hbase 등
- 비관계형 데이터베이스로, table 형식이 아닌 비정형 데이터를 저장할 수 있도록 지원
- 사전에 스키마를 정의하지 않아도 저장될 수 있음
- UPDATE가 적고 조회가 많을 때 유리

### 차이점
1. 데이터 저장(Storage)
- RDS : 관계형 데이터베이스로 SQL 언어를 이용해 데이터를 테이블에 저장하며, 미리 작성된 스키마를 기반으로 정해진 형식에 맞게 데이터를 저장해야 함
- NoSQL : Key-Value, document, wide-column, graph 등의 방식으로 데이터 저장

2. 스키마(Schema)
- RDS : 고정된 형식의 스키마 필요, 처리할 데이터 속성별로 열(column)에 대한 정보를 미리 정해야 함, 스키마는 나중에 변경할 수 있지만, DB 전체를 수정하거나 오프라인으로 전환해야 할 수 있음
- NoSQL : 관계형 데이터베이스에 비해 동적으로 스키마 형태 관리 가능, 행을 추가할 때 즉시 새로운 열 추가 가능, 개별 속성에 대해 모든 열에 대한 데이터를 반드시 입력하지 않아도 됨

3. 쿼리(Query)
- RDS : 테이블 형식과 테이블 간의 관계에 맞춰 데이터를 요청해야 함, 구조화된 쿼리 언어를 사용하는 이유
- NoSQL : 데이터 그룹 자체 조회하는 것에 초점, 구조화되지 않은 쿼리 언어로도 데이터 요청이 가능한데 이것을 UnQL이라고도 함

4. 확장성(Scalability)
- RDS : 수직적으로 확장 -> 높은 메모리, CPU를 사용하는 확장이라고도 함, DB가 구축된 HW 성능을 많이 이용하기 때문에, 비용이 많이 든다. 여러 개의 서버에 걸쳐 DB 관계를 정의할 수 있지만, 매우 복잡하고 시간이 많이 소모됨
- NoSQL : 수평적으로 확장 => 저렴한 비용으로 서버를 증설할 수 있으며, 클라우드 서비스를 이용하는 확장이라고도 함. NoSQL 데이터베이스를 위한 서버를 추가적으로 구축 => 많은 트래픽을 보다 편리하게 처리할 수 있음. 저렴한 범용 HW나 클라우드 기반 인스턴스에 NoSQL 데이터베이스를 호스팅할 수 있어 상대적으로 비용이 저렴

```
           [RDB]                         [NoSQL]
-----------------------------------------------
- 정형 데이터                     - 비정형 데이터
- 트랜잭션 강함                  - 유연한 구조
- SQL 질의 강함                  - 빠른 성능
- 관계형 데이터 관리          - 수평 확장 유리
- 결제/거래 시스템			 - 실시간 채팅 메시지
- 사용자 정보 관리				- 소셜미디어 피드
```

## Index(인덱스) 🔺

### Index(인덱스)
- DB 테이블에 대한 검색 속도 향상시키는 자료구조로, WHERE 절을 통해 활용
- 책의 색인 같은 역할
- 만약 index를 사용하지 않은 컬럼을 조회한다면, 전체를 탐색하는 Full Scan을 수행해야 함
- 전체를 비교하기 때문에 처리 속도가 느려짐

### 인덱스 특징
- 인덱스는 항상 최신의 정렬 상태 유지
- 인덱스도 하나의 데이터베이스 객체
- 데이터베이스 크기의 약 10%의 저장 공간 필요

### 인덱스의 관리
- DBMS는 인덱스를 항상 최신 정렬 상태로 유지해야 빠르게 원하는 값 탐색 가능
- 따라서, 인덱스가 적용된 컬럼에 INSERT, UPDATE, DELETE가 수행된다면 아래와 같은 연산을 추가적으로 해 주어야 하며 그에 따른 오버헤드 발생
- INSERT : 새로운 데이터에 대한 인덱스 추가
- DELETE : 인덱스의 데이터를 실제로 지우지 않고 사용 안 함 표시를 함
- UPDATE : DELETE(기존 값 사용 안 함 표시) -> INSERT(변경된 값 삽입)
> UPDATE, DELETE의 경우도 WHERE절을 사용할 때 빨라지지 않을까?
>- UPDATE : WHERE절로 처리할 대상을 찾기 위한 조회 성능은 향상
>- DELETE : <br> (1) 사용하지 않는 인덱스 적용 -> 불필요한 처리량 증가 <br> (2) 사용 안 함 표시로 페이지 낭비 및 인덱스 조각화 심해짐

### 인덱스 장단점
** 장점 **
- 테이블을 조회하는 속도와 그에 따른 성능을 향상시킬 수 있음
- 전반적인 시스템의 부하를 줄일 수 있음

** 단점 **
- 인덱스를 관리하기 위해 DB의 약 10%에 해당하는 저장 공간 필요
- 인덱스를 관리하기 위해 추가 작업 필요
- 인덱스를 잘못 사용할 경우 오히려 성능이 저하되는 역효과 발생 가능

### 인덱스 종류

**클러스터(Cluster)**
- 무리, 군집
- 무리를 이루다 

** 클러스링 인덱스 **
- 실제 데이터와 같은 무리의 인덱스
- 실제 데이터가 정렬된 사전

** 논클러스링 인덱스**
- 실제 데이터와 다른 무리의 별도의 인덱스
- 책에서 맨뒤에 붙어있는 찾아보기 페이지 같은 느낌

```
우리가 모르는 사이에 자동으로 인덱스를 사용하고 있었음
CREATE TABLE member (
	id			int 			primary key, => 클러스터링 인덱스
    name 		varchar(255),
    email 		varchar(255) 	unique => 논클러스터링 인덱스
);
```

#### 클러스링 인덱스

- 추가 방법
```
방법1)
ALTER TABLE member
ADD CONSTRAINT pk_id **PRIMARY KEY**(id);
방법2)
ALTER TABLE member MODIFY COLUMN id int **NOT NULL**;
ALTER TABLE member ADD CONSTRAINT nuq_id **UNIQUE(id)**;
```

**특징**
(1) 실제 데이터 자체가 정렬
(2) 테이블당 1개만 존재 가능
(3) 리프 페이지가 데이터 페이지
(4) 아래의 제약 조건 시 자동 생성
- primary key(우선 순위)
- unique + not null

#### 논클러스링 인덱스(보조 인덱스, 세컨더리 인덱스)
- 추가 방법
```
방법 1)
ALTER TABLE member
ADD CONSTRAINT unq_name UNIQUE(name);
방법 2)
CREATE UNIQUE INDEX unq_idx_name
ON member(name);
방법 3)
CREATE INDEX idx_name
ON member(name);
```
**특징**
(1) 실제 데이터 페이지는 그대로
(2) 별도의 인덱스 페이지 생성 -> 추가 공간 필요
(3) 테이블당 여러 개 존재
(4) 리프 페이지에 실제 데이터 페이지 주소를 담고 있음
(5) unique 제약조건 사용시 자동 생성
(6) 직접 index 생성시 논클러스터링 인덱스 생성

### 인덱스 적용 기준
> 어떤 컬럼에 인덱스를 적용해야 할까?

#### 카디널리티(Cardinality)
- 그룹 내 요소의 개수

**어떤 컬럼에 인덱스를 적용해야 할까?**
- 카디널리티가 높은 것 = 중복도가 낮은 것

#### 적용 기준
(1) 카디널리티가 높은 컬럼
(2) WHERE, JOIN, ORDER BY절에 자주 사용되는 컬럼
- 인덱스는 추가 공간 필요
- 조건절이 없다면 인덱스 사용 X
(3) INSERT/UPDATE/DELETE가 자주 발생하지 않는 컬럼 (성능 저하에 대한 영향이 있을 수 있음)
(4) 규모가 작지 않은 테이블

## 인덱스 해시테이블, B+ 트리 차이

#### 용어

1. 페이지 : 데이터가 저장되는 단위

2. Full Table Scan
**특징**
- 순차적 접근
- 접근 비용 감소

** Full Table Scan 사용**
- 적용 가능한 인덱스가 없는 경우
- 인덱스 처리 범위가 넓은 경우
- 크기가 작은 테이블에 엑세스하는 경우

3. B Tree
- 트리 높이가 같음
- 자식 노드를 2개 이상 가질 수 있음
- 기본 데이터베이스 인덱스 구조

4. 페이지 분할
- 페이지에 새로운 데이터를 추가할 여유 공간이 없어 페이지에 변화가 발생
- DB가 느려지고 성능에 영향을 줌

5. 리프 페이지 = 데이터 페이지
- 실제 데이터가 저장된 곳


### Index의 자료구조
- 인덱스를 구현하는 방법에 대표적인 방법으로 해시 테이블과 B+ Tree 방식이 존재함

#### 해시 테이블(Hash Table)
- (Key, Value)로 데이터를 저장하는 자료구조 중 하나로, 빠른 데이터 검색이 필요할 때 유용함
- Key값을 이용해 고유한 index를 생성하여, 그 index에 저장된 값을 꺼내오는 구조

![](https://velog.velcdn.com/images/emprimula/post/d913e2bc-bf22-4ae0-be00-a76dc6713ec7/image.png)
- 해시 테이블 기반의 DB 인덱스는 (데이터=컬럼의 값, 데이터의 위치)를 (Key, Value)로 사용하여, 컬럼의 값으로 생성된 해시를 통해 인덱스를 구현
- 시간 복잡도 : O(1) -> 매우 빠른 검색 지원
- 해시 테이블이 사용되는 경우는 제한적 => 해시가 등호(=) 연산에만 특화
- 해시 테이블 내의 데이터들은 정렬되어 있지 않으므로 특정 기준보다 크거나 작은 값을 빠른 시간 내에 찾을 수 없음
- 해시 함수는 값이 1이라도 달라지면 완전 다른 해시 값을 생성하는데, 이러한 특성에 의해 부등호 연산이 자주 사용되는 DB 검색을 위해서는 해시 테이블이 적합 X
- 따라서, 데이터베이스 인덱스는 B+ Tree를 일반적으로 사용

#### B+ Tree
- DB의 인덱스를 위해 자식 노드가 2개 이상인 B-Tree를 개선시킨 자료구조
- 모든 노드에 데이터(Value)를 저장한 B-Tree와 다른 특성을 가짐

- leaf 노드(데이터 노드)만 인덱스와 함께 데이터(Value)를 가지고 있고, 나머지 노드(인덱스 노드)들은 데이터를 위한 인덱스(Key)만을 가짐
- leaf 노드를 제외하고 데이터를 담지 않아 메모리를 더 확보할 수 있어, 더 많은 key들을 담을 수 있음
- 하나의 노드에 더 많은 key들을 담을 수 있기 때문에 트리의 높이는 더 낮아짐 => cahe hit를 높힐 수 있음
- leaf 노드들은 LinkedList로 연결되어 있음
- 데이터 노드의 크기는 인덱스 노드의 크기와 같지 않아도 됨

- DB의 인덱스 컬럼은 부등호를 이용한 순차 검색 연산이 자주 발생될 수 있음 
- B-Tree의 leaf 노드들을 LinkedList로 연결하여 순차 검색을 용이하게 하는 등 B-Tree를 인덱스에 맞게 최적화함 (B Tree 대신 쓰는 이유)
- B+ Tree는 O(log2n)의 시간복잡도를 갖지만 해시테이블보다 인덱싱에 더욱 적합한 자료구조가 됨

## 복합 인덱스(Composite Index) 🔺 

### 복합 인덱스(Composite Index)
- 두 개 이상의 컬럼을 포함하는 인덱스
- 주로 SQL 문장에서 WHERE절의 조건 컬럼이 2개 이상 AND로 연결되어 함께 사용되는 경우에 많이 사용
- OR로 조회되는 경우 결합 인덱스 사용 X

#### 복합 인덱스 장점
- 검색 속도 개선 : 여러 개의 컬럼을 동시에 검색할 수 있기 때문에
- 데이터 정렬의 효율성 : 인덱스를 생성할 때 여러 개의 컬럼을 사용하면 정렬을 할 때 더 효율적
- 인덱스 용량 절감 : 여러 개의 컬럼을 함께 사용하면 인덱스의 용량이 줄어든다
- 쿼리 최적화 : 여러 개의 컬럼을 함께 사용하기 때문에, 쿼리가 여러 개의 조건을 가지고 있을 때 최적화된 실행 계획 수립 가능

#### 복합 인덱스 컬럼 선택
=> 어떤 컬럼을 선택하는 게 복합 인덱스를 사용하기 좋을까?
(1) WHERE절에서 AND 조건으로 자주 통합되어 사용되면서, 각각의 분포도보다 두 개 이상의 컬럼이 통합될 때 분포도가 좋아지는 컬럼들
(2) 다른 테이블과 조인와 연결고리로 자주 사용되는 컬럼들
(3) ORDER BY에서 자주 사용되는 컬럼들
(4) 하나 이상의 키 컬럼 조건으로 같은 테이블의 컬럼들이 자주 조회될 때

#### 복합 인덱스 사용 주의점
- 인덱스를 생성하는 컬럼의 개수가 많아질수록 인덱스의 성능이 떨어질 수 있음
- 인덱스 생성 순서 고려해야 함
- 인덱스 생성 순서는 WHERE절에서 먼저 사용되는 컬럼을 앞쪽에 위치시키는 게 좋음

#### 복합 인덱스 사용법
(1) 인덱스를 생성할 테이블과 컬럼 선택
(2) 인덱스를 생성할 컬럼 순서 결정 => 검색 조건에서 자주 사용되는 컬럼을 먼저 위치시키는 것이 좋음
(3) 복합 인덱스를 생성
(4) 필요한 기능에서 쿼리문의 사용
