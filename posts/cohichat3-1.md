# 협업 속에서 성장하기 - 팀워크와 개발 프로세스

> 3주차라고는 했지만, 서투른 탓에 거의 2.5주 동안 겪었던 이야기가 되었다. 기한을 일주일 넘게 못 맞춘 건데 기다려 주신 코헤 님께 너무너무 감사했다....

기간 자체도 길고, 고민이 많았기 때문에 지연된 것이라 분량이 매우 많다. 그래서 이번 회고록은 게시글을 3개로 나눠 작성하게 되었다.

- **1부: 협업과 성장 (팀워크 & 프로세스)** ← 지금 여기
- 2부: 좋은 프로그램 만들기 (테스트 & 품질)
- 3부: 3부: 설계와 구현 이야기 (기술 선택의 고민들)

## 1. 포맷터와 린터의 필요성

### 문제 상황: 코드 스타일은 그냥 말로만?

이전 프로젝트에서는 "컨벤션 규칙 굵직한 것만 지키자"고 말로만 넘어갔다. 문서도 없었고, 코드 리뷰에서 컨벤션을 검수하지도 않았다. 이번 프로젝트에서 Lint를 적용해 보자는 의견을 들어 그 부분을 맡게 되면서, **이전에 많은 것들을 고민하지 않고 진행했음**을 깨달았다.

### 왜 이런 일이 발생했을까?

- **Why 1**: 왜 컨벤션이 지켜지지 않았을까? → 말로만 약속했기 때문
- **Why 2**: 왜 말로만 약속했을까? → 자동화 도구의 필요성을 못 느꼈음
- **Why 3**: 왜 필요성을 못 느꼈을까? → 코드 품질 자체를 고민해 보지 않음
- **Why 4**: 근본 원인 → **협업 환경에서의 코드 품질 관리를 간과**

### 고민 과정: 대기업 컨벤션 규칙? 커스텀 컨벤션 규칙?

코드 컨벤션이 필요한 건 인지했으나, 어떤 컨벤션을 따를 것부터 고민해야 했다. 처음에는 어디부터 어디까지 정해야 하는 것인지, 남들은 어디까지 정하는 것인지 감이 잡히지 않아 **보편적인 대기업 컨벤션 규칙을 가져와서 사용하면 되지 않나** 하는 생각을 했다. 

하지만 우리 서비스는 규모가 매우 작은 서비스고, 팀원도 둘뿐이었다. 대기업 컨벤션 규칙은 **과하게 빡빡한 규칙**이라는 생각이 들었다. 그래서 **우리 프로젝트에 적합한 정도의 컨벤션 규칙을 직접 작성**하였다.

📌 **작성한 문서**: [코드 컨벤션 Wiki](https://github.com/CheHyeonYeong/cohi-chat/wiki/%EC%BD%94%EB%93%9C-%EC%BB%A8%EB%B2%A4%EC%85%98)

### 해결: 포맷터와 린트 도입

다음으로 고민한 것은 "이 코드 컨벤션을 어떻게 해야 잘 지킬 수 있을지"에 대한 고민이었고, 코헤 님께서 포맷터와 린트에 대해 말씀하셔서 그것을 우리 프로젝트에 적용해 보기로 했다.

- **포맷터**: IntelliJ의 `codestyle`
- **린트**: `checkstyle`

직접 작성한 적용 가능 규칙을 `.xml` 파일로 작성해 적용시킨 후, 자동으로 컨벤션 규칙 검사를 할 수 있게 하였다. 물론 이것으로 모든 규칙을 지킬 수는 없었지만, **인텔리제이 컴파일 시점에서 놓칠 수 있는 많은 컨벤션 규칙을 빨간 밑줄로 표시**하여 규칙을 잘 지키고 코드의 품질을 효율적으로 높일 수 있음을 체감했다.

### 배운 점

**Keep**: 커스텀 컨벤션 작성, 자동화 도구 도입(포맷터와 린터) 
**Problem**: 처음부터 자동화를 고려하지 않음, 협업 관점 부족  
**Try**: 다음 프로젝트는 초기부터 포맷터/린터 필수 설정

> "협업에서는 자동화할 수 있는 건 자동화해야, 더 중요한 논의에 집중할 수 있다."

## 2. 좋은 PR은 무엇인가?

### 문제 상황: 거대한 PR의 참사

나는 자동화되어서 지킬 규칙도 신경 안 써도 되고, Member 도메인 안에서 구현해야 하는 기능이 **아주 단순한 CRUD와 인증/인가**라고 생각해서 **아무런 생각 없이 Member 도메인을 통으로 구현한 후 PR을 올렸다**. 

근데 이러면 안 됐고, 코헤 님께서 왜 PR이 늦게 올라오는지 의문을 가지는 이유도 그때서야 깨달았다. 애초에 **PR 단위에 대해 생각해 본 적이 없이** 던져 버리니까 작은 참사로 끝날 수 있던 부분이 큰 참사가 되어 돌아왔다. 기존 일정에 비해 **일주일 넘게 오버가 된 이유는 다 이 말도 안 되는 PR을 보낸 발상이 구른 스노우볼**이었던 걸로 생각한다.

### 왜 이런 일이 발생했을까?

- **Why 1**: 왜 일정이 밀렸을까? → PR 리뷰가 느려짐
- **Why 2**: 왜 리뷰가 느려졌을까? → PR이 너무 커서 리뷰하기 힘듦
- **Why 3**: 왜 PR이 컸을까? → PR 단위를 고민하지 않음
- **Why 4**: 왜 고민하지 않았을까? → "단순 CRUD"는 하나로 묶여도 되는 작은 단위라 생각
- **Why 5**: 근본 원인 → **작은 단위로 쪼개는 습관 부재**

### 거대한 PR의 문제점

**양 자체가 많으니 피드백도 늦어질 수밖에 없다.** 심지어 부족한 점이 많은 코드였기 때문에, 피드백의 양도 많아질 수밖에 없었다. 양도 많은데 퀄리티도 낮으니 **생산성 저하가 두 배**로 된 것이다. 

또한 한 PR에서 복합적인 기능을 담당하게 되다 보니 **PR의 목적성도 길을 잃었다**. 그로 인해 원래 예정된 일주일의 기간을 넘고 2.5주가 걸리게 되었다. 만일 PR 자체가 작아졌다면 빠르게 PR의 문제점, 코드 퀄리티의 문제점, 설계의 문제점을 빠르게 체크해서 이렇게까지 길어지지 않았을 것이다. 

처음 올린 PR이 잘못되었고, 그 PR을 쭉 가져가려고 하다 보니 **초반에 버린 시간이 많았다**고 생각했다.

### 고민 과정: 좋은 PR이란?

위의 문제가 많은 PR로 일주일을 고생(?)했더니 그다음으로 생각하게 된 게 **그렇다면 좋은 PR은 무엇인가**에 대해 고민하게 되었고, 작은 PR에 대한 게시글을 몇 개 찾아봤다.

📚 **참고 자료**:
- [뱅크샐러드: 뱅크샐러드 Code Review 문화](https://blog.banksalad.com/tech/banksalad-code-review-culture/)
- [라인 엔지니어링: 효과적인 코드리뷰](https://engineering.linecorp.com/ko/blog/effective-codereview)

이런 게시글들을 보고 방향성을 잘못 잡았다고 생각했다. 그러고 PR도 규칙 같은 것을 새로 정해서 **300자~400자 사이로 구체적으로 잡든가**, PR 정보를 더욱 자세하게 적는다든가, 언제까지 PR 리뷰를 해 줘야 한다든가 하는 글들을 봤다. 

처음에는 "PR 규칙을 이렇게 빡빡하게 정해야 하나?" 싶어서 코헤 님께도 슬쩍 얘기해 보았는데, **300자~400자 같은 규칙은 생각보다 빡빡하다**고 말씀해 주셨고, 이 빡빡한 규칙이 우리 프로젝트에 맞는가에 대해 다시 고민해 보게 되었다. 

포맷터/린터 때처럼, **무조건 남의 규칙을 가져오는 게 아니라 우리에게 맞게 커스텀**해야 한다고 생각했다.

### 해결: PR 양식 개선

먼저 PR 양식을 바꾸게 되었다. 기존 양식은 체크리스트가 너무 많았다. 체크하는 것과 글로 적는 것이 뒤섞여 혼란스러웠다.

**기존 양식의 문제점**:
- 체크리스트 과다 → 기력 낭비
- 의도와 고민을 상세하게 쓰는 것이 더 중요한데 묻힘
- 개요, 변경사항, 참고사항이 흩어져 있음
- 테스트 방법과 의도는 중간에, 참고사항은 밑에 있고, 개요는 맨 위에, 그 밑에는 변경사항이 있는데 중간에 체크리스트가 혼란스럽게 함

**새로운 양식**:
```markdown
**관련 이슈** #41

### ✅ 뭘 만들었는지
-

### 🤔 왜 이렇게 결정했는지 (고민 지점)

### 🧪 테스트는 어떻게 했는지
-

### 📝 회고 / 참고사항
```

**코멘트 중요도 표시**:
- `???`: 반드시 수정 필요 (진짜 왜 안 하심 미치셨음?)
- `??`: 중요한 것 같은데? 잘 모르겠지만 좀 더 고민해 보시고 리뷰어의 판단에 전적으로 운전수 맘대로 하슈
- `?`: 참고만 하세요. 고치게나.. 말게나.

### 배운 점

**Keep**: 의도와 고민을 명확히 작성하는 문화  
**Problem**: 거대한 PR, 목적성 상실, 느린 피드백  
**Try**: 작은 단위로 쪼개기, 1 PR = 1 Feature/Fix

> "좋은 PR = 리뷰어가 30분 안에 이해할 수 있는 크기"

## 3. 협업에서의 자율성과 일정 지연

### 문제 상황: 자율성을 줬는데 일정이 밀렸다

이번 프로젝트에서는 TDD를 도입하기로 했고, **TDD를 문서화하고 공부해서 팀원에게 가이드라인을 제시**해야 하는 건 내 담당이 되었다.

📌 **작성한 문서**: [테스트 전략 Wiki](https://github.com/CheHyeonYeong/cohi-chat/wiki/%ED%85%8C%EC%8A%A4%ED%8A%B8-%EC%A0%84%EB%9E%B5)

하지만 **TDD 학습과 기능 구현이라는 두 가지 큰 목표가 동시에 주어지다 보니**, 팀원의 이해도 차이로 일정이 지연됐다. 자율성을 주고 싶었지만 프로젝트는 계속 늦어졌다.

> TDD 도입 과정과 테스트 전략에 대한 자세한 내용은 **2부 "좋은 프로그램 만들기"**에서 다루겠다.

### 왜 일정이 지연됐을까?

- **Why 1**: 왜 일정이 밀렸을까? → 예상보다 구현 시간이 오래 걸림
- **Why 2**: 왜 오래 걸렸을까? → 기술 스택 이해 부족 + 범위 설정 미흡
- **Why 3**: 왜 이해가 부족했을까? → 사전 학습 시간 부족 + 초기 방향 설정 없음
- **Why 4**: 왜 학습 시간이 부족했을까? → 일정에 여유를 안 뒀음
- **Why 5**: 근본 원인 → **이해도 차이를 고려한 일정 계획 부재 + 초기 피드백 시스템 부재**

### 문제의 본질: 현재 방식

1. 팀장: "이거 해보세요" 던짐
2. 팀원: 알아서 범위 정하고 진행
3. 결과: "어? 생각한 거랑 다르네?" 발생

### 개선 방향

**타르트님 제안을 바탕으로:**
- 과제 부여 직후(당일 혹은 익일) **초기 계획 및 범위 설정에 대한 짧은 피드백 시간**
- Member 도메인 구현 시처럼, **설계 방향과 학습 우선순위를 미리 공유**
- 큰 목표가 동시에 주어질 때는 **우선순위를 명확히**

### 배운 점

**Keep**: 자율성 부여 자체 (주도적 학습 유도)  
**Problem**: 
- 이해도 파악 없이 동일 일정 부여
- 막혔을 때 도움 요청 문화 부족
- 초기 방향 설정 없이 진행
- 복수의 큰 목표 동시 부여

**Try**:
- 초기 기술 스택 체크리스트 공유
- 과제 부여 직후 초기 계획 및 범위 설정 피드백 시간
- 1-2일에 한 번씩 진행 상황 체크인
- 막혔을 때 즉시 공유하는 문화
- 필요시 페어 프로그래밍/멘토링

> "자율성 ≠ 방치"  
> 적절한 체크포인트와 도움 요청 문화가 함께 있어야 건강한 협업이 된다.

## 4. 코드 리뷰와 코드래빗

### 문제 상황: 뭘 리뷰해야 하지?

PR은 해결됐는데, 경험이 부족해서 **코드 리뷰 자체에 뭔 얘기를 해야 하나** 싶었다.

### 해결: 코드래빗 도입

부족한 리뷰 역량을 AI로 보충하기로 했다. 코드래빗이 기본적인 컨벤션, 잠재적 버그, 개선 포인트를 먼저 잡아주니 **리뷰에 집중할 수 있는 여력**이 생겼다.

### 배운 점

**Keep**: AI 도구 적극 활용  
**Problem**: 리뷰 경험 부족  
**Try**: 코드래빗 + 사람 리뷰 병행, 리뷰 스킬 향상

## 5. 의문을 가지는 태도

### 문제 상황: "일단 돌아가면 되지"

코드 리뷰를 할 때 모든 내용에 대해 다 설명할 수 없었다. PR 리뷰를 통해 **그냥 기능 동작을 최우선**으로 해서 코드 한 줄 한 줄 설명할 수 있다거나 DTO를 만들 때 왜 `record`를 썼는지 `class`를 써야 하는지 등 그런 하나하나에 대한 고민을 안 해 보았다.

위에서부터 쭉 말한 것처럼 **설계에 대한 의문 자체도 가지지 않고** 파이썬 코드를 그대로 마이그레이션하려고 했다. 파이썬 코드를 분석하지 않고 **자바의 특성을 이용할 태도 자체가 안 됐다**.

### 왜 이런 일이 발생했을까?

- **Why 1**: 왜 설명을 못했을까? → 한 줄씩 고민하지 않음
- **Why 2**: 왜 고민하지 않았을까? → "일단 돌아가면 되지" 마인드
- **Why 3**: 왜 그런 마인드였을까? → 빠른 구현에 집중
- **Why 4**: 근본 원인 → **설계보다 기능 구현을 우선시**

### 배운 점

**Keep**: PR 리뷰를 통해 문제 발견  
**Problem**: 
- 코드 한 줄 한 줄 설명할 수 없음
- 기술/라이브러리 선택 시 "왜?"를 생각 안 함
- 설계에 대한 의문 부재
- 언어의 특성을 고려하지 않고 단순 마이그레이션

**Try**:
- 한 줄씩 "왜?"를 설명해 보기
- 기술/라이브러리 쓸 때 "왜?"를 생각하기
- 기능 구현보다 **설계부터 철저히 고민**
- 해당 언어의 특성을 살려서 구현하기

> "기능 구현에 초점을 맞추는 게 아니라, 설계부터 의문을 가지고 철저하게 고민해야 한다."

## 시리즈 1 종합 회고

### Keep (계속할 것)
- 포맷터/린터로 자동화
- 작은 PR, 명확한 의도 작성
- 코드래빗 + 사람 리뷰 병행
- 의문을 가지는 태도
- 팀원의 성장 과정 함께 발견

### Problem (개선 필요)
- 초기 세팅(포맷터/린터) 부족
- 거대한 PR로 시간 낭비
- 일정 계획 시 이해도 고려 미흡
- 자율성 = 방치로 오해
- 설계보다 기능 구현 우선
- 초기 방향 설정 피드백 시스템 부재
- 복수의 큰 목표 동시 부여

### Try (다음엔)
- 프로젝트 시작 시 포맷터/린터 필수 설정
- PR은 작게, 의도는 명확하게
- 이해도 기반 일정 계획 + 초기 방향 설정
- 과제 부여 직후 초기 계획 및 범위 피드백 시간
- 1-2일 단위 체크인 문화
- 설계부터 철저히 고민하는 습관
- 큰 목표는 우선순위를 명확히 하여 순차적으로
