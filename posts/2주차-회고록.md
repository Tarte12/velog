#### Java 21 (LTS)
- 안정적이고 레퍼런스가 많음
- OpenJDK 도커 이미지도 많음
- Lombok, Google Calendar API, IntelliJ 호환 확인

#### Java 25 (LTS)
- Virtual Thread 개선 (21에서는 핀잉 문제가 있었는데 이것을 개선)
- LTS X
- Spring Boot 3.5.5부터 지원
- 너무 최신이라 테스트 부족한 느낌

> **결론**: 우리가 만드는 커피챗 예약 시스템에서 예상 트래픽을 DAU 10명 내외로 잡고 있기 때문에 Virtual Thread를 사용하지 않을 것 같아 Java 21가 적합하다고 판단했다.

## 2.2 포매터랑 린터 개념 정리 및 BE 적용
> 코드 품질 관리를 위해 포매터와 린터를 적용하기로 했고, 이를 위해 개념을 정리하고 코드 컨벤션 규칙을 세운 후 적용하는 시간을 가졌다.

### 왜 포매터/린터를 도입하자고 했을까?
코드 품질 관리를 위해 **코드 컨벤션을 팀 차원에서 강제할 필요**가 있었고, 이를 위해 포매터/린터를 도입할 필요성을 느꼈다.

사람마다 IDE/스타일이 다르면 코드 품질이 통일이 되지 않고, 자동화가 가능하다면 자동화하는 방향으로 잡았다.

### 코드 컨벤션부터 고민한 이유

**고민 흐름**
1. 포매터/린터를 사용하려면 적용할 규칙이 필요
2. 그래서 먼저 코드 컨벤션을 정의해야 한다고 판단
3. 선택지 2가지:
- 대기업/오픈소스 컨벤션 그대로 가져오기
- 프로젝트에 맞게 직접 정의

**결론**
- 대기업 컨벤션은 팀 규모가 크고 레거시·다언어·장기 운영 전제를 깔고 있어 우리 프로젝트에서는 과도하게 깐깐한 느낌이 있다고 판단했다.
→ 필요한 규칙만 추려 직접 컨벤션을 정의하기로 했다.


### 포매터 vs 린터 개념 정리

#### 포매터 (Formatter)
- 역할: 코드의 ‘형태’를 자동으로 맞춤
- 예: 들여쓰기, 줄바꿈, 공백, 따옴표 스타일
- 특징: 논쟁의 여지를 제거하고 사람이 신경 쓸 필요 X
- 대표 도구:
	- BE: IntelliJ Code Style (java 다른 언어는 몰루)
	- FE: Prettier

#### 린터 (Linter)
- 역할: 코드의 ‘의미/위험’을 검사
- 예: 사용하지 않는 변수, 잠재적 버그, 컨벤션 위반
- 특징: 에러/경고의 근거를 제공하고, 팀의 코드 품질 기준을 강제할 수 있음
- 대표 도구:
	- BE: Checkstyle
	- FE: ESLint
    
#### BE 적용 과정과 자동화 

1. IntelliJ Code Style로 기본 포매팅 통일
2. Checkstyle:
	- 직접 정의한 컨벤션 기반으로 XML 작성
    - 자동화되게 설정

#### FE 적용 시도와 실패
> 일단 BE라도 올려 놨는데 얜 아직 실패를 해서 슬퍼 ㅜㅜ

- Prettier, ESLint 도입 및 설정 파일 작성까지는 완료
- 그러나:
	- IDE 적용 문제
	- 설정 충돌
	- 팀 전체에 동일하게 강제할 수 없는 상태
- 결과:
	- PR에 적용 시 혼란만 커질 가능성
	→ 의도적으로 PR 범위에서 제외
