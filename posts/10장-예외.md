# ITEM 69 예외는 진짜 예외 상황에만 사용하라
- 문제 상황: 예외를 if문, for문처럼 로직에 사용
=> try-catch문은 JVM 최적화를 막고, 흐름에 쓰인 예외 때문에 실제 버그가 숨겨져 디버깅이 어려워질 수 있음

### JVM 최적화

#### JVM은 어떻게 동작할까? 
- 가정: `ArrayIndexOutOfBoundsException` 발생
1. 예외 객체 생성
2. 현재 스레드의 스택 프레임을 거슬러 올라가며
	- 어디에서 발생했는지
    - 어떤 메서드들이 호출되었는지
3. Stack Trace 정보 수집
4. 가장 가까운 `catch` 블록 탐색
5. 제어 프름을 그 지점으로 점프
- 결론: 이 과정은 단순 if문, for문과 차원이 다른 문제

#### 왜 JVM은 최적화를 안 할까?
=> JVM은 예외를 "자주 발생하는 정상 흐름"으로 가정하지 않음
- 예외 = 비정상 상황
- JVM 설계 철학의 전제 "드물게 발생해야 한다"
- 그래서 핫패스(hot path) 최적화 대상 X

### 버그 은닉
```java
try {
    while (true) {
        range[i++].climb();
    }
} catch (ArrayIndexOutOfBoundsException e) {
}
```
#### JVM 입장에서:
- `ArrayIndexOutOfBoundsException`이
	- 어디에서
    - 왜
    발생했는지 `catch`가 구분하지 않음
#### `catch` 입장에서:
- "아, 이 예외는 루프 종료 신호구나"
실제로는:
	- `climb()` 내부 버그거나
    - 다른 배열 접근 실수일 수 있음
하지만 JVM에서는 의도를 모르기 때문에 버그가 조용히 묻힐 수 있는 상황 발생

결론: 정말로 예외 처리를 해야 하는 부분에서만 예외 처리를 해야 함

# ITEM 70 복구할 수 있는 상황에는 검사 예외를, 프로그래밍 오류에는 런타임 예외를 사용하라

#### 에러(Error): 시스템에 비정상적인 상황이 발생했을 경우를 의미
#### Checked Exception: 컴파일 시점에 반드시 예외 처리를 해야 하는 예외
- 호출하는 쪽에서 복구할 것이라 여겨질 때 사용
- RuntimeException을 상속하지 않아 꼭 처리해야 함
- try-catch문으로 처리하거나 throws 키워드를 사용하여 더 바깥으로 전파하도록 강제하게 되는데, 메서드를 호출했을 때 발생할 수 있는 유력 결과임을 API 사용자에게 알려주는 것
#### Unchecked Exception
	- RuntimeException 상속받아 런타임에 발생하며 명시적으로 처리하지 않아도 괜찮음
    - 대부분 프로그래머의 실수로 발생 => 예외 처리가 아니라 코드를 고쳐야 하는 문제

# ITEM 71 필요 없는 검사 예외 사용은 피하라

- API를 제대로 사용해도 발생할 수 있거나 개발자가 의미 있는 조치를 할 수 있다면 => 검사 예외를 사용하자
- 사용자가 예외 상황에서 복구할 방법이 없다면 => 비검사 예외를 던지게 만들자

# ITEM 72 표준 예외를 사용하라
- 표준 예외가 있다면 그것 먼저 사용하자

|예외|주요쓰임|
|---|---|
|IllegalArgumentException|허용하지 않는 값이 인수로 건네졌을 때 (null은 따로 NullPointerException으로 처리)|
|IllegalStateException|객체가 메서드를 수행하기에 적절하지 않은 상태일 때|
|NullPointerException|null을 허용하지 않는 메서드에 null을 건넸을 때|
|IndexOutOfBoundsException|인덱스가 범위를 넘어섰을 때|
|ConcurrentModificationException|허용하지 않는 동시 수정이 발견됐을 때| 
|UnsupportedOperationException|호출한 메서드를 지원하지 않을 때|

# ITEM 73 추상화 수준에 맞는 예외를 던지라

하위 계층에서 발생한 예외를 그대로 상위 계층에 노출하면 => 사용자는 **내부 구현을 알아야 의미를 이해할 수 있는 예외**를 마주하게 됨
이 문제는
- 내부 구현이 외부 API를 오염시키고
- 구현이 바뀌면 클라이언트 코드가 깨질 수 있고
- 디버깅 책임이 잘못된 계층으로 전가되는
**설계 문제**로

> 이 문제를 해결하기 위한 핵심 기법이 **예외 번역(Exception Traslation)**

#### 예외 번역(Exception Traslation)
- 상위 계층에서 저수준 예외를 잡아 자신의 추상화 수준에 맞는 예외로 바꿔서 던지는 것
```java
try {
    // 저수준 추상화를 이용한다.
} catch (LowerLevelException e) {
    // 추상화 수준에 맞게 번역한다.
    throw new HigherLevelException(...);
}

```

#### 예외 연쇄(Exception Chaining)
- 예외를 번역할 때 저수준 예외가 디버깅에 도움이 될 때 사용
- 저수준 예외(원인)를 고수준 예외에 실어 보내는 방식
- 별도의 접근자 메서드(Throwable의 getCause 메서드)를 통해 저수준 예외를 꺼내서 볼 수 있음
```java
try {
    // 저수준 추상화를 이용한다.
} catch (LowerLevelException e) {
    // 저수준 예외를 고수준 예외에 실어 보낸다.
    throw new HigherLevelException(e);
}
```
# ITEM 74 메서드가 던지는 모든 예외를 문서화하라
- 검사 예외는 항상 따로 선언하고, 각 예외가 발생하는 상황은 javadoc의 `@throw` 태그로 문서화
- 메서드가 던질 수 있는 예외를 `@throw` 태그로 문서화, 비검사 예외는 메서드 선언의 throws 목록에 넣지 말자

# ITEM 75 예외의 상세 메시지에 실패 관련 정보를 담으라
- 실패 순간 포작을 위해 발생한 예외에 관여된 모든 매개변수와 필드 값을 실패 메시지에 담아야 함
	- 민감한 정보는 담으면 안 됨

# ITEM 76 가능한 한 실패 원자적으로 만들라

#### 실패 원자적
- 호출된 메서드가 실패하더라도 해당 객체는 메서드 호출 전 상태를 유지하는 특성 의미

#### 메서드를 실패 원자적으로 만드는 방법
1. 불변(Immutable) 객체로 설계하기
- 생성 시점에 고정되어 절대 변하지 않기 때문에 실패 원자적
2. 로직 수행 이전 매개변수의 유효성을 검사하기
- 객체 내부 상태 변경 전 잠재적 예외의 가능성 대부분을 걸러냄
3. 실패 가능성이 있는 모든 코드를 객체 상태를 바꾸는 코드보다 앞에 배치하기
- 로직을 수행하기 전 인수의 유효성을 검사하기 어려울 때 사용할 수 있음
4. 객체의 임시 복사본에서 작업을 수행한 후 성공적으로 완료되면 원래 객체와 교체
- 데이터를 임시 자료 구조에 저장해 작업하는 것이 더 빠를 때 적용하기 좋음

#### 실패 원자성을 무조건 지켜야 할까?
항상 실패 원자성을 지킬 수 있지는 않음
- 비용이 크거나 복잡도가 아주 크거나 Error의 경우 실패 원자성을 지키지 않아야 함

# ITEM 77 예외를 무시하지 말라
예외가 선언된 API는 그 메서드를 사용할 때 적절한 조치를 해야 한다는 뜻으로 `catch` 블록을 비우면 예외가 존재할 이유가 없음
- 만일 그래도 예외를 무시해야 한다면 `catch` 블록 안에서 그 이유를 주석으로 남기고 예외 변수의 이름도 변경하여야 함
