# TDD란 무엇인가?

> TDD는 "테스트를 많이 작성하는 기법"이 아니라, **프로그래밍을 진행하는 순서와 사고 흐름에 대한 워크플로**

IF 프로그래머가 시스템의 동작을 변경해야 할 경우 
=> TDD는 다음과 같은 새로운 시스템 상태를 만들도록 돕기 위해 고안

- 기존에 잘 작동하는 기능은 여전히 잘 작동한다
- 새로 추가한 동작은 예상대로 동작한다
- 다음 변경을 안전하게 받아들일 수 있는 구조다
- 이 사실을 **프로그래머와 동료 모두가 확신**할 수 있다

> 즉, **변경에 대한 두려움을 줄이는 방법론**

# 핵심 개념: 인터페이스와 구현을 분리해서 생각하자

> TDD를 이해하기 위해 반드시 두 가지를 구분해야 함

**1. 인터페이스 설계**
- 어떤 동작이 
- 어떤 입력을 받고 
- 어떤 결과를 내야 하는가

**2. 구현 설계**
- 그 동작을 내부적으로 어떻게 구현할 것인가

# TDD 워크플로

## 1. 테스트 목록 작성

> 진정하고 **코드 아닌 테스트 목록부터 만들자**

- 기본 동작은?
- 예외 상황은?
- 실패 시나리오는?
- 기존 기능이 깨지면 안 되는 경우는?
=> 여러 상황을 고민해 보는 **행동 분석**의 단계

## 2. 단 하나의 테스트만 작성

> 목록 중 **딱 하나만 선택**해 실제 실행 가능한 테스트로 만들자

- 준비(Arrange)
- 실행(Act)
- 검증(assert)
_Tip: 어설션부터 역으로 설계하면 좋음_
이 단계에서 드러나는 설계는 대부분 **인터페이스 설계**에 해당

**실수**
- 어설션 없는 테스트 
- 테스트 목록 전체를 한번에 코드로 옮김 -> 재작업 폭탄

### 어설션?

> "이 테스트에서 반드시 참이어야 하는 조건"

**쉽게 말해서**
- **기대값과 실제값을 비교하는 선언**
- "이게 맞지 않으면 테스트는 실패해야 한다"

```java
assertEquals(5, calculator.add(2, 3));
```
- 의미: `calculator.add(2, 3)`의 결과는 반드시 5여야 함
- 역할: 검증(statement)
	- 기대값(5)
    - 실제값(calculator.add(2, 3))
    - 비교(같은가?)

**테스트 코드 기본 구조**
- 보통 3단 구조: **Arrange - Act - Assert**
```python
@Test
void add_two_numbers() {
    // Arrange (준비)
    Calculator calculator = new Calculator();

    // Act (실행)
    int result = calculator.add(2, 3);

    // Assert (검증)
    assertEquals(5, result);
}
```

## 3. 테스트를 통과시켜라

> 테스트가 실패했다면, **"테스트가 통과하도록" 테스트 코드를 작성하자**

**실수**
- 어설션을 삭제해서 테스트를 "통과한 것처럼" 만들기 <= 이걸 실수라고 할 수 있는 거임?
- 실제 계산 결과를 그대로 테스트 기대값에 복붙(이중 검증 파괴)
- 테스트 통과와 리팩토링 동시 수행 
	- 먼저 실행되도록 만든 다음, 제대로 작동하도록 만들어라 <= 나중에 머리가 고마워한다고 함

만일 테스트를 통과시키는 과정에서 새 시나리오가 보이면 **테스트 목록에만 추가**하도록 함
=> 해당 테스트가 이미 완료한 작업을 무효화할 경우 계속 진행할지 처음부터 다시 시작할지 결정 필요
 

## 4. 선택적 리팩토링
여기부터 **구현 설계**를 다룸
- 중복 제거
- 가독성 개선
- 구조 정리

**실수**
- 너무 많이 리팩토링
- 너무 이른 추상화

## 5. 테스트 목록이 빌 때까지 반복

> 코드 동작에 대한 두려움이 지루함으로 바뀔 때까지 계속 테스트하고 코딩하자
