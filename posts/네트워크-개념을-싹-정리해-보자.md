# Section 4) L3

## IPv4 주소의 기본 구조
- IP => IPv4 => 32 bit = 8 bit x4
![](https://velog.velcdn.com/images/emprimula/post/a2ba00da-2c04-44a0-b8c2-70648beb09ef/image.png)
- IP주소 => 8bit씩 4자리 수
- 0.0.0.0 ~ 255.255.255.255까지 사용 가능 범위 => 2^32, 총 43억 개
- IP주소(32bit) = Network ID(앞 24bit) + Host ID(뒤 8bit)
- 사용할 수 없는 주소
	- Host ID = 0 (Subnet Mask가 되어 버림)
    - Host ID = 255 (Broadcast 주소가 되어 버림)
=> 그래서 Host ID는 총 254개 사용 가능

## L3 IP Packet
- Packet = 단위 데이터
- **Packet** = **L3 IP Packet**으로 외워라
- **Header/Payload**로 나뉘며 상대적인 분류
	-> Header = 송장(출발지 -> 도착지)
    -> Payload = 데이터(내용물)
- 최대 크기는 **MTU**
- L3 IP Packet의 최대 크기는 MTU (Maximum Transmition Unit)로, 1500 bytes
![](https://velog.velcdn.com/images/emprimula/post/48f7b3a3-4712-4476-8ece-185cabd61181/image.png)

## Encapsulation과 Decapsulation
![](https://velog.velcdn.com/images/emprimula/post/4db0a6ea-1926-4461-a548-8e056c135185/image.png)
### Encapsulation(캡슐화)
- 포장, 단위화
- Payload에 단계별로 Header를 붙여 하나의 Payload를 만드는 행위
- Payload #3 (전송 계층)
	-> 응용 계층에서 받은 메시지를 **TCP 헤더**를 붙여 캡슐화하면 해당 데이터는 **Segment**로 네트워크 계층으로 전달됨
- Payload #2 (네트워크 계층)
	-> 전송 계층에서 받은 세그먼트에 **IP 헤더**를 붙여 캡슐화하면 해당 데이터는 **Packet**으로 데이터링크 계층으로 전달됨
- Payload #1 (데이터링크 계층)
	-> 네트워크 계층에서 받은 패킷에 **Ethernet 헤더**를 붙여 캡슐화하면 데이터는 **Frame**으로 물리 계층에 전달됨
    -> 데이터링크 계층에서는 헤더뿐만 아니라 트레일러도 페이로드 다음에 붙게 됨
### Decapsulation(역캡슐화)
- 캡슐화의 반대 작업 => Header와 Payload 분리
- 데이터링크 계층
	-> 물리 계층에서 받은 Frame의 헤더와 트레일러를 구분해 나오는 Packet을 네트워크 계층에 전달
- 네트워크 계층
	-> 데이터링크 계층에서 받은 패킷의 헤더를 구분하여 나오는 Segment를 전송 계층에 전달
- 전송 계층
	-> 네트워크 계층에서 받은 세그먼트의 헤더를 구분하여 나오는 메시지를 응용 계층에 전달
    
## 패킷의 생성과 전달

![](https://velog.velcdn.com/images/emprimula/post/c0376104-5633-45cb-8622-e5e0dba3b48c/image.png)

## IP 헤더 형식
![](https://velog.velcdn.com/images/emprimula/post/564c5a88-fcf6-4cd7-8b75-13a25f3d4ec9/image.png)
- Version(4bit): TCP/IP는 IPv4 사용
- IHL(4bit): IP 헤더의 길이를 32 비트 단위로 나타냄
	-> 대부분의 IP 헤더 길이는 20 byte
- Flags(3bit): IP 라우터에 의해 분열되는 여부 + 원래 데이터의 분열된 조각이 더 있는지 판단 [단편화]
- Fragment offset(13 bit): 8byte 오프셋으로 조각에 저장된 원래 데이터의 바이트 범위를 나타냄 (단편화된 데이터를 다시 붙일 때 필요한 정보) [단편화]
- TTL(8bit): 데이터를 전달할 수 없는 것으로 판단되어, 소멸되기 이전에 데이터가 이동할 수 있는 단계의 수
	-> 1~255 사이의 값을 지정하며 라우터들은 패킷을 저장할 때마다 이 값을 하나씩 감소시킴
- Protocol(8bit): 상위 계층 프로토콜

## 서브넷 마스크와 CIDR
![](https://velog.velcdn.com/images/emprimula/post/3c658349-b100-4e37-b47f-192d2fc71169/image.png)
### Subnet Mask
- IP 주소를 Network ID/Host ID를 나눌 때 사용되는 숫자 조합
	-> 어떤 주소라도 이진 표현으로 변환 후 => AND 연산을 통해 서브넷 마스크를 통과시키게 되면 => **네트워크 ID와 호스트 ID 경계를 찾을 수 있음**
    -> IP주소와 같은 길이의 비트로 구성 -> 이진수(Binary)로 표현했을 때 Network ID = 1, Host ID = 0으로 설정
    -> 1111 1111. 1111 1111. 1111 1111. 0000 0000
	-> 255.255.255.0
- 단일 네트워크의 크기가 너무 큰 경우 => 특정 기기와 통신을 시도할 때 **브로드캐스트 영향이 너무 크기 때문에** 서브넷 마스크를 사용해 네트워크를 쪼개 브로드캐스트 영역을 보다 작은 네트워크(서브넷)으로 나눌 수 있음
	-> 이를 통해 **네트워크를 작은 그룹으로 조직화하고 관리** 가능
    
![](https://velog.velcdn.com/images/emprimula/post/ab419eb6-18ae-4d4a-a34d-8a413cdd915b/image.png)
## CIDR(Classless Inter-Domain Routing)
- 서브넷팅 표기법
- IP 주소 뒤에 슬래시와 비트수를 숫자로 표기
- 필요에 따라 더 작은 서브넷을 생성 or 더 큰 주소 공간 할당 가능
- ex) 192.168.0.10/24
	-> 슬래시 앞 부분은 네트워크 ID, /24는 서브넷 마스크 길이를 의미
	-> 24비트 서브넷 마스크는 첫 24비트가 네트워크 ID이고 나머지 8비트가 호스트 ID임을 의미
	-> 192.168.0.0 ~ 192.168.0.255 까지의 IP주소 범위를 의미하게 되는데, 여기서 네트워크 ID(호스트 ID가 0인것 서브넷마스크), 브로드캐스트 주소를 제외하고 실제로 호스트에 할당할 수 있는 IP 주소 범위는 192.168.0.1 ~ 192.168.0.254가 됨

## Broadcast IP 주소
![](https://velog.velcdn.com/images/emprimula/post/6e637248-800b-4f57-addd-3f5f311cb341/image.png)
- Broadcast는 모든 자리가 다 1로 이루어진 주소이므로 IP주소에선 마지막 8bit의 Host ID부분이 1로 이루어진 주소를 말한다
- 실제로 쓸 수 있는 Host ID는 254개
- ex) 192.168.0.255
	-> Network ID : 192.168.0
	-> Host ID : 255
	-> 해당 Network에서 방송주소로 사용됨
- 브로드캐스팅을 하겠다 = 전체 다 보내겠다' <= 안 할 수 있으면 안 하는 게 무조건 좋음
- 비슷한 거 => Multicast

![](https://velog.velcdn.com/images/emprimula/post/87447163-3cb1-4fbd-aa69-0649acb7a103/image.png)
- 만약 IP주소가 192.168.0.10인 pc가 192.168.0.255로 데이터를 보내게 되면, 해당 패킷이 L2 Distribution에 도착하는 순간 같은 네트워크(192.168.0 대역) 안에 있는 host들에게 전부 퍼지게 됨
- 위 이미지로 보면 pc1이 보낸 데이터를 pc 2,3,4,5,6 추가로 gateway까지 받게 됨

### TTL(Time to live)
- 데이터의 유효 기간을 나타내기 위한 방법
	-> 패킷이 무한으로 순환하는 것을 막는 역할
- 데이터가 라우터를 옮겨다니면 TTL 값이 줄어드는데, 목적지에 도착하지 못하게 되면 라우터가 해당 패킷을 버림

### 단편화(Fragmentation)
- 데이터가 프레임으로 캡슐화할 때 => 데이터의 전체 크기가 MTU보다 작아야 함 => 데이터 링크 계층에 전달되기 전에 작은 크기로 분할
- 단편화된 패킷은 수신측 엔드 포인트에서 조립
- 단편화 발생 경우 => VPN(IPSec)이 적용되었을 때 발생
	- IPSec: 통신 과정 도중, 패킷을 도청 or 위조하는 악성 유저들로부터 패킷을 보호하기 위해 사용하는 보안 프로토콜

2. 그러면 네트워크의 DHCP 서버가 장치가 사용할 수 있는 IP 주소로 응답을 보냄

## ARP

    -> L2에서의 통신에서 사용자는 IP 주소를 목적지로 지정하지만 실제로는 MAC 주소를 이용해 목적지를 찾음

## Ping과 RTT
![](https://velog.velcdn.com/images/emprimula/post/7c35c1d1-8d33-47b7-ba4f-d9ac732fa5e4/image.png)
### Ping
- Ping 유틸리티는 특정 Host에 대한 RTT를 측정할 목적으로 사용됨
	-> 네트워크 연결 상태를 확인하고 대상 호스트까지 왕복 시간을 측정할 때 사용되는 유틸리티
   	-> ICMP 프로토콜을 사용하여 대상에게 Echo Request를 보내고, Echo Reply를 받아 왕복 시간(RTT)을 측정함
- ICMP(Internet Control Message Protocol) 프로토콜 이용

### RTT

- ping을 보냈을 때 나오는 응답 속도 (보통 ms 단위)
- 거리에 비례하지 않고 네트워크 속도에 영향을 받음 <- 하지만 물리적으로 거리가 멀다면 네트워크 속도가 빠르기는 쉽지 않음

## TCP 연결 과정(3-way handshaking)
**Seq 번호 교환 => 정책 교환(MSS-Maximum Segment Size)**
- 둘 중 한 놈의 MMS가 작으면 작은 것에 맞춰서 진행함

![](https://velog.velcdn.com/images/emprimula/post/cd9c06d6-92ff-4b24-840b-5a06d080f86c/image.png)
1. ip header , tcp header만 있고 payload가 없는 단순한 segment가 왔다 갔다 함
2. client가 sequence number를 랜덤으로 생성해서 SYN으로 보내줌
3. server도 자신의 sequence number를 랜덤으로 생성하고 client에게 받은 sn 을 1 증가시켜서 같이 보냄
4. SYN+ACK 를 받은 client는 자신이 연결되었다는것으로 판단 = established
	-> 여기에서 Client만 연결되었다고 생각, Server는 아직 연결 X
5. ACK를 client보내고 Server가 받으면 연결이 되었다고 판단 = established

-> 이 모든 연결은 **Virtual**
 

## TCP 연결 종료 및 상태 변화(4-way handshaking)
![](https://velog.velcdn.com/images/emprimula/post/998c32a1-c048-4afd-b737-11b4d4cdede9/image.png)
0. 연결을 하는 놈이 client 였으니 종료도 client가 하는것이 일반적
1. client 가 FIN + ACK 를 같이 보내서 연결을 끊어달라고 server에게 보냄
2. 받았다고 ACK를 server가 보내고 자신은 CLOSE_WAIT으로 들어가게 됨
3.server의 ACK를 받은 client 는 FIN_WAIT2에 들어가서  server의 FIN+ACK 을 기다리게 됨
4. server가 FIN + ACK를 보내고 LAST_ACK를 기다리는 상태로 변함
5. client는 TIME_WAIT 상태로 들어가게 된다. TIME_WAIT 발생하는곳이 먼저 종료를 요청한 쪽
6. server가 TIME_WAIT가 발생한다면 일반적인 방법이 아님을 알 수 있음
7. client가 TIME_WAIT으로 변경되면서 마지막 ACK를 보내게 됨
8. server가 ACK를 받고 종료

## 굵고 짧게 살펴보는 HTTP

### HTTP
- HTML 문서를 전송받기 위해 만들어진 **응용 프로그램 계층(L7) 계층** 통신 프로토콜
- L5 이상 => Socket 통신
	=> **Stream 데이터**이므로 시작은 있지만 끝을 알기 어려움
    => 이것을 HTTP 프로토콜이 끝을 지정해 줌
- **HTTP는 문자열 구성** => 헤더를 읽어서 이해 가능

#### 헤더의 분류
- 일반 헤더
- **요청 헤더**
- **응답 헤더**
- 엔티티 헤더

- 기본적으로 **클라이언트의 요청과 그에 대응하는 응답**으로 동작
- 리소스를 요청 => 리소스를 응답
- **메서드**: 요청하기 위한 방법 => 보통 GET, POST

### HTTP 응답 코드
- 200 OK: 요청이 정상적으로 처리됨
- 201 Create: 요청에 대한 새로운 자원을 생성하는데 성공함
- 301 Moved permanently
- 302 Found
- 400 Bad request: HTTP 규약에 맞지 않는 요청
- 403 Forbidden: 권한이 없거나 잘못된 파일 실행 접근 시도
- 404 Not found
- 500 Internal server error: 내부 오류때문에 요청을 처리할 수 없음

### HTTP method
- GET
	- 다운로드에 가까움
	- 리소스를 달라고 요청
- POST
	- 리소스를 업로드
	- ID/PW 입력해 로그인
- HEAD
	- 데이터 영역을 떼고 뭐만 보내고 하는 것
- TRACE
- PUT
	- 리소스 새로 업로드
- DELETE
	- 리소스 삭제
- OPTIONS
- CONNECT
