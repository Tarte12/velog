>본 글은 프로젝트 구현 이전, 기획 및 설계 단계에서의 회고이다.

## 계기
팀 프로젝트 마무리 이후, 부족한 부분을 책과 스터디로 보완하고 있었다.
하지만 책과 스터디를 진행하는 것으로는 실제 코드와 구조에서 왜 필요한지 설명하기 어렵다는 한계가 있었다. 특히 `Effective java` 스터디 관련 내용은 '아는 것'과 '써 본 것'의 간극이 컸다.

이 시점에 `기획에서 출시까지 FastAPI 개발 백서` 책 기반 프로젝트로 커피챗 예약 프로그램을 만들어 보자고 코헤 님께서 제안을 주셨고, 그동안 공부한 걸 적용해 볼 수 있다고 생각해 참여하게 되었다. 

## 진행 흐름
프로젝트는 FastAPI 기반 예제 코드를 분석한 뒤,
1) 기존 코드의 오류 수정 과정을 거치고
2) 이를 Java 기반으로 마이그레이션하는 방향으로 설정했다.

1주차 회의에서는 다음과 같은 기준을 명확히 하는 것에 집중했다.
- 프로젝트 범위 및 목표 정리
- 협업 방식(브랜치 전략, 리뷰 방식)
- 프로젝트 진행 방식 및 역할 분담

## 좋았던 점

### 1. 컨벤션 규칙
이전 개인 프로젝트에서는 컨벤션을 거의 의식하지 않았고, 팀 프로젝트에서도 최소한의 규칙만 정해 진행했다.

이번 프로젝트에서는 커밋 메시지 규칙, PR 규칙, 코드 리뷰 기준 등을 기획 단계에서 미리 논의했는데, 이 과정을 통해 컨벤션은 단순한 형식이 아니라 **변경 이력을 설명 가능하게 만드는 장치**라는 점을 인식하게 되었다.

아직 실제 적용 단계는 아니지만, 이후 프로젝트에서도 구현 이전에 협업 규칙을 먼저 정하는 습관이 필요하다고 느꼈다.


### 2. Java 마이그레이션
Java로의 마이그레이션을 기획하면서, 스터디에서 다뤘던 개념들이 실제 설계 단계에서 어떤 판단 기준이 될 수 있는지를 고민해볼 수 있었다.

`Effective Java`의 경우 실무 경험이 없어 책에서 말하는 내용이 추상적으로 느껴졌는데,
이번 프로젝트를 통해 적용 가능한 지점과 그렇지 않은 지점을 구분해볼 수 있을 것이라 기대했다.

또한 프로젝트와 병행 중인 스터디들과 설계 관점에서의 교집합을 공유하며 논의할 수 있다는 점도 이번 기획의 장점으로 느껴졌다.

### 3. 코드 리뷰
기존 프로젝트도 코드 리뷰의 필요성은 느끼고 있었지만, 스스로 코드에 대한 피드백을 하는 데 한계를 느끼고 있었다.

이번 프로젝트에서는 코드 리뷰를 전제로 한 협업 방식을 기획 단계에서부터 논의했고, 이를 통해 리뷰는 단순한 오류 지적이 아니라 코드를 설명 가능한 상태로 만드는 과정이라는 관점을 인식하게 되었다.
