# 1️⃣ 생성자 대신 정적 팩터리 메서드를 고려하라
## 📘 핵심 개념
클래스의 인스턴스를 얻는 방법:
1. `new` 생성자를 직접 호출
2. **정적 팩터리 메서드(`static factory method`)** 사용

```
LocalDate today = LocalDate.now(); 
// 시스템 시계의 현재 날짜(LocalDate) 반환
LocalDate birth = LocalDate.of(1999, 12, 5);
// 지정된 연/월/일 값으로 LocalDate 객체 생성
```
- `LocalDate`(Java 8 날짜 API) 객체를 만드는 두 가지 정적 팩터리 메서드

## ⚙️ 내부 원리
- new는 바이트코드에서 invokespecial 명령으로 컴파일됨
  -  **컴파일 타임에 호출할 생성자가 완전히 고정**
  -  항상 **새 인스턴스(new object)** 생성
→ 캐싱이 불가능하고,
→ 다형성(polymorphism)도 불가능

- 반면 정적 팩터리 메서드는 `invokestatic` 명령으로 호출됨
  - **런타임**에 반환 타입을 선택 가능
  - `invokestatic` => **정적(statci) 메서드를 호출하라** 명령어
  - **JVM이 직접 생성자를 호출 X => 메서드 내부 로직에 위임**
→ 이미 만들어진 인스턴스 리턴 가능
→ 필요하면 새 객체 만들 수 있음

이 덕분에 팩터리 메서드는
- **(1) 인스턴스를 캐싱해 재사용 가능**
	- `new`는 JVM이 **무조건 새 객체를 Heap에 올림**
    - 정적 팩터리 메서드는 "이미 만들어진 게 있나?"를 **메서드 로직 안에서 판단**
    - 생성의 책임이 메서드로 옮겨옴
    → **"생성하지 않겠다"**는 선택지를 가질 수 있음
    => **인스턴스 캐싱/풀링/Flyweight 패턴** 구현 가능
- (2) 하위 타입 객체를 반환해 다형성을 보장 가능
  - `new`는 **컴파일러가 구체적인 생성자 타입을 알아야** 호출 가능
  → 따라서 항상 선언된 클래스 그 자체를 생성
  - 반면 정적 메서드는 **리턴 타입만 명시**하면 됨
  → 내부에서 실제 어떤 하위 타입을 만들지는 런타임에 결정 가능

### 캐싱(Caching)
> **이미 만든 것을 다시 쓰는 것**
- 프로그램이 한 번 만든 객체/데이터를 **메모리에 저장하고**,
- 같은 요청이 들어오면 **새로 만들지 않고 재사용하는 기법**

#### 💡 요점
- 캐싱은 객체 생성을 줄여 메모리와 CPU를 절약하는 방법
- new는 항상 새로운 객체를 만들기 때문에 이런 캐싱이 불가능


### 다형성(Polymorphism)
> ** 같은 타입으로 여러 형태의 객체를 다룰 수 있는 능력**
- 상위 타입(인터페이스나 부모 클래스) 하나로
- 여러 하위 타입(구현체)의 객체를 **동일한 방식으로 다룰 수 있는 성질**

#### 💡 요점
- 다형성은 “타입을 고정하지 않고 유연하게 반환”할 수 있는 성질
- 정적 팩터리 메서드는 바로 이 런타임 선택권을 제공
- (생성자는 항상 고정된 클래스만 반환하기 때문에 불가능)

# 2️⃣ 생성자에 매개변수가 많다면 빌더를 고려하라
## 📘 핵심 개념
- 객체 생성 시 필드가 많을수록 가독성과 안정성이 무너짐 
### **1. 점층적 생성자 패턴**:  파라미터 순서 혼동
#### 특징
- **생성자 호출 순간 객체가 바로 만들어짐**
- 모든 필드가 한번에 초기화됨
- 불변(immutable) 구조 가능
#### 단점
- 매개변수 많으면 가독성 ↓
- 선택적 인자가 많으면 오버로딩 폭증
- 필드 순서 실수 위험

### **2. JavaBeans 패턴**: `setter` 호출 중간에 불변식(invariant) 깨짐
#### 특징
- 파라미터 순서 문제 X
- 직관적이고 IDE 자동완성 편리
#### 단점
- 객체 생성은 즉시 일어나지만, 완성은 나중에
→ 생성 시점에는 불완전한 상태의 객체가 존재
(servingSize, servings 등 필수 필드가 비어 있음)
- 불변 불가능
- 스레드 안전하지 않음
> ✅ 요약: “객체를 바로 만든 뒤 setter로 채워 넣는다.”
(즉, 즉시 생성 + 점진적 완성 + 불완전 상태 존재)

### **3. 빌더 패턴: 불변성 + 가독성 + 확장성 확보**
```
NutritionFacts cocaCola = new NutritionFacts.Builder(240, 8)
    .calories(100)
    .sodium(35)
    .carbohydrate(27)
    .build();
```
### 특징
- `new`는 Builder 내부에서 build() 시점에 단 한 번만 호출
- 그전까지는 Builder 객체(값 누적용)가 존재할 뿐, 실제 NutritionFacts는 없음
- 최종 객체는 **완전한 불변 상태로 한 번만 생성**
> ✅ 요약: “필요한 값만 모아두고, 완성 시점에 한 번만 생성한다.”
(즉, 지연 생성 + 완성 시점 제어 + 불변성 확보)

| 패턴            | 객체 생성 시점      | 객체 상태            | 불변성  | 특징                |
| ------------- | ------------- | ---------------- | ---- | ----------------- |
| **점층적 생성자**   | 생성자 호출 즉시     | 완전               | ✅ 가능 | 한 번에 생성하지만 가독성 나쁨 |
| **JavaBeans** | new 시점에 바로 생성 | 불완전 → setter로 완성 | ❌ 불가 | setter 중간 상태 존재   |
| **Builder**   | build() 호출 시점 | 완전               | ✅ 가능 | 값 누적 후 한 번만 생성    |


## ⚙️ 내부 원리
- 빌더 패턴은 내부적으로 “값 누적용 객체”를 하나 더 만든 뒤,
build() 시점에 **불변 객체를 한 번만 생성**

이 방식은
- 중간 상태가 존재하지 않아 일관성 유지
- 불변 필드로 인해 thread-safe
- 가독성과 유지보수성 향상
즉, **객체 생성의 원자성(atomicity) 을 확보**하는 구조

## 🧠 메모리 관점
- 생성자 다중 호출 대신, 빌더 내부의 임시 객체에 값이 누적됨
- `build()` 시점에서 한 번에 객체를 생성 → `Heap allocation` 횟수 최소화.

> 빌더는 “객체 생성의 트랜잭션”이다 — 완성 전에는 생성 X

# 3️⃣ private 생성자나 열거 타입으로 싱글톤임을 보증하라
## 📘 핵심 개념
- 싱글톤(Singleton)은 인스턴스가 하나만 존재해야 하는 패턴
- ex)
- DB 커넥션 풀
- 로깅(LogManager)
- 설정(ConfigManger)
- 캐시(CacheManager)
- **"전역 상태를 관리하는 유일한 객체""** 느낌
```
public enum Elvis {
    INSTANCE;
    public void sing() { ... }
}
```
### 일반적인 구현: private 생성자 + static 필드
```
public class Logger {
    private static final Logger INSTANCE = new Logger(); // 단 하나
    private Logger() {} // 외부에서 new 못 함

    public static Logger getInstance() {
        return INSTANCE;
    }
}
```
1. `private` 생성자 -> 외부에서 `new Logger()` 못함
2. `static` 필드 -> JVM 클래스 로딩 시 딱 한 번만 생성
**JVM이 클래스를 로드할 때 인스턴스를 한 번만 만들고 재사용**

#### 문제 1) 리플렉션(Reflection)으로 생성자 호출 가능
```
Constructor<Logger> c = Logger.class.getDeclaredConstructor();
c.setAccessible(true);
Logger another = c.newInstance(); // 🚨 새로운 인스턴스 생성 가능
```
#### 문제 2) 직렬화/역직렬화 시에도 새 객체 생성 가능
```
ObjectInputStream in = new ObjectInputStream(...);
Logger another = (Logger) in.readObject(); // 🚨 다른 객체가 됨
```
**언어 차원에서 "단 하나"라는 보장이 완전하지 않음**

### 그래서 등장한 대안: Enum 싱글톤
```
public enum Logger {
    INSTANCE;

    public void log(String msg) {
        System.out.println(msg);
    }
}
```
#### 특징
- `Logger.INSTANCE`를 호출하면 항상 같은 인스턴스가 반환
- JVM이 `enum`을 로드할 때 딱 한 번만 생성하고, 리플렉션과 직렬화 모두 차단함

** enum 자체가 “언어 차원의 싱글톤 보장장치”**

## ⚙️ JVM 관점
### (1) 클래스 로딩 시점
- `enum`은 내부적으로 `public static final` 상수처럼 동작
- 클래스가 로딩될 때, 각 `enum` 상수(`INSTANCE`)가 딱 한 번만 메모리에 올라감

### (2) 리플렉션 차단
- 자바 리플렉션 API로 `enum`의 생성자를 호출하면 `IllegalArgumentException` 발생
→ 언어 자체에서 막아둠

### (3) 직렬화 안전
- `enum`은 `readResolve()`를 자동으로 구현한 것처럼 동작해서, 역직렬화 후에도 같은 객체가 유지됨

## 🧠 설계 의미
- `private` 생성자 + `static` 필드로 구현할 수도 있지만,
- `Enum` 싱글톤은 **언어 수준에서 단일성을 보장**하기 때문에 Good

# 4️⃣ 인스턴스화를 막으려거든 private 생성자를 사용하라
## 📘 핵심 개념
- `Math`,` Collections`, `Objects` 같은 유틸리티 클래스는 상태가 없음
- 즉, 인스턴스를 만들 이유가 없음
```
public class MathUtils {
    private MathUtils() {
        throw new AssertionError();
    }
}
```
## ⚙️ 메모리 관점
**객체 생성**은 단순히 “Heap에 올리는 행위” X
- Class Metadata 로드
- Object Header 생성
- Heap 영역에 메모리 할당
까지 포함된 **고비용 작업**
- 상태가 없는 클래스에서 객체를 생성하는 건 단순 낭비

### 질문
#### 1) 왜 상태가 없으면 인스턴스 안 만들어도 됨?
- **객체를 만드는 것 => 내부에 '상태'를 저장하기 위함**
- 상태가 없다면 기능만 있는 거니까 저장할 값 X
#### 2) 유틸리티 클래스는 왜 상태가 없음?
- **유틸리티 클래스(Utility Class)** 는 프로그램 전역에서 공통적으로 사용되는 **순수 기능(method)** 들만 모아둔 클래스
#### 3) 프로그래머가 임의로 만드는 "상태 없는 작업"?
- 상태 없는 메서드는 보통 입력 → 계산 → 출력으로 끝나는 순수 함수(pure function) 형태
#### 4) 왜 private 생성자를 사용해서 인스턴스화를 막을 수 있음?
**동작 원리**
- private 생성자는 클래스 내부에서만 호출 가능
- 외부(new MathUtils())에서 호출하려 하면 컴파일 에러 발생
- static 메서드만 쓰기 때문에 객체 생성 자체가 불필요
- “사람이 잘못 써도 객체를 만들 수 없게 막아두는 안전장치”

# 5️⃣ 의존 객체 주입(Dependency Injection)을 사용하라
## 📘 핵심 개념
- 객체가 스스로 자원을 생성하면, 코드의 결합도가 높아짐
```
public class SpellChecker {
    private final Dictionary dictionary;
    public SpellChecker(Dictionary dictionary) {
        this.dictionary = dictionary;
    }
}
```
- **객체가 스스로 자원을 만들지 말고 외부에서 주입**
- 외부에서 주입받으면 **유연성, 테스트성 향상**

## ⚙️ 설계 원리
- `new`를 내부에서 호출하면 의존 대상이 코드에 박힘
- DI는 **제어의 역전(Inversion of Control)** => 객체 스스로 의존 대상을 만들지 않음
- 런타임 시점에 다른 구현체로 교체 가능

## 🧠 실무 대응
- Spring의 `@Autowired`, `@Bean`이 DI를 자동화
- 인터페이스 기반 설계 → 교체 가능한 의존성 구조
- DI는 단순 편의성 X -> 객체 지향의 **개방폐쇄 원칙(OCP)** 수단

# 6️⃣ 불필요한 객체 생성을 피하라
## 📘 핵심 개념
- **불변 객체는 재사용해도 안전함**
- 동일한 값은 새로 만들지 말고 캐싱
```
String s = new String("hello");    // ❌ 새로운 객체
String s = "hello";                // ✅ 상수 풀 재사용
```

## ⚙️ JVM 관점
- `String Constant Pool`, `IntegerCache`, `Boolean.TRUE` 등
→ 동일한 값을 가진 객체를 JVM이 **자동 캐싱**
- `new`를 사용하면 이 캐시를 우회해 매번 새 객체 생성

# 7️⃣ 다 쓴 객체 참조를 해제하라
## 📘 핵심 개념
- **GC는 만능이 아님!**
- 참조가 남아 있으면 객체는 회수되지 않음
```
public Object pop() {
    Object result = elements[--size];
    elements[size] = null;  // 🔥 참조 해제
    return result;
}
```

## ⚙️ 내부 원리
- JVM의 GC는 **Reachability Analysis **기반
- "도달 가능한 객체'만 살려 놓음
- `Stack`, `Map`, `List` 등에 참조가 남아 있으면 GC는 회수하지 않음

# 8️⃣ finalizer와 cleaner 사용을 피하라
## 📘 핵심 개념
** finalizer/cleaner는 불확실하고 느리며, 보안상 위험함**

- 실행 시점을 **GC 타이밍에 의존** → 불확실
- 내부적으로 **Finalizer Thread**가 별도로 큐를 감시
- 악용 시 객체 회수 지연(DoS 공격 가능)

## 🧩 권장 방식
- `close()` 메서드 제공 (명시적 자원 회수)
- `try-with-resources` 문과 함께 사용

# 9️⃣ try-finally보다는 try-with-resources를 사용하라
## 📘 핵심 개념
**AutoCloseable 자원은 try-with-resources로 자동 해제하라**

```
try (BufferedReader br = new BufferedReader(new FileReader(path))) {
    return br.readLine();
}
```

## ⚙️ 내부 원리
- 컴파일러가 자동으로 `finally { br.close(); }` 생성
- `suppressed exception` 처리까지 자동
- `try-finally`보다 간결하고, 예외 처리 정확도 높음
